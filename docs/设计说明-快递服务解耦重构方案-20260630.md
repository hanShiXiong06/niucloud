# 设计说明 · 快递服务解耦重构方案（hsx_recycle 插件内）

> 类型：重构设计（**不动代码，先对齐方案**）。确认后再按 §六 分步实施。
> 范围：仅 `addon/hsx_recycle` 插件**内部**的服务分层重构。**不拆插件、不入侵核心框架、不改框架表**。
> 目标：把"快递"做成一条**边界清晰、自洽、低耦合**的独立服务；同时把被多业务共用的第三方能力沉淀为**一层纯基础设施**。回收订单"一键寄件 + 状态回写"的体验**一行不降级**。
> 配套：《二开规范_开发文档》《二开约束_代码业务与版本管理》《研发流程规范》。

---

## 一、一句话结论

**业务该各自独立，基础设施该共享一份。**

- 快递 / 设备查询 / 打印 / 地址解析 → 各自独立服务，互不引用（高内聚、低耦合，出问题各背各的锅）。
- 它们脚下的"第三方通道能力"（Provider 加载 + 配置中心 + API 日志 + 成本统计）→ **共享一层基础设施，不复制**。复制三份不是解耦，是用复制制造三处耦合，且违背框架"基类 + Loader 工厂"的既有约定（支付/短信/打印都这么做）。

> 这正面回答了"是不是每个都该成独立服务？"——**业务是，基础设施不是**。

## 二、现状盘点（事实，作为重构基线）

### 2.1 好消息：解耦的"缝"已经存在

| 既有资产 | 说明 | 结论 |
|----------|------|------|
| `CoreThirdPartyService::call($serviceType,$method,$params,$siteId)` | 统一派发入口：Provider 加载 → 配置中心取配置 → 备用 Provider 兜底 → API 日志 → 成本统计 → 余额 | **已是干净的基础设施缝**，被 express / device_query / address_parse / device-erp-sync / printer 共用 |
| `getProvider()` 内 `class_exists($providerClass)` 守卫 | Provider 类缺失只 `Log::warning` 不 fatal | 已有防御，残留配置不会崩 |
| `event('RecycleExpressEvent', [...])` + `RecycleExpressEventListener` | 快递推送/下单已抛事件，监听器写 `RecycleOrderLog` | 联动**已一半事件化** |

### 2.2 乱在哪（三个真正的味道）

1. **基础设施与业务 Provider 混在一个命名空间**
   `app/service/core/third_party/provider/` 下同时堆着：`address_parse`、`delivery`、`device_query`、`express_order`、`express_query`。
   → "third_party" 既指基础设施框架（`BaseProvider`/`CoreThirdPartyService`/配置/日志/成本），又装着各业务的具体 Provider（快递的安国·易速、设备的 3023、地址的腾讯）。**这是"看不清谁的锅"的根因。**

2. **配置服务是个"什么都知道"的胖服务**
   `RecycleThirdPartyConfigService` 里既有通用配置读写，又混入 `getPrinterConfig()` / `isPrinterConfigComplete()` / `getServiceMap()` / 各业务 `getDefaultConfig()`——基础设施层却内嵌了各业务的知识。

3. **快递自身代码散落两处、命名带 Recycle**
   - `app/service/core/ExpressOrderService.php`（868 行，挂在 core 根目录）
   - `app/service/core/express/RecycleExpressService.php`（576 行）、`YisuExpressPushService.php`（343 行）
   → 一条业务线被切成"根目录一块 + express 子目录一块"，且核心类叫 `RecycleExpressService`。**散 + 命名混 = 你感觉它糊成一团的直接来源。**

### 2.3 快递 ↔ 回收：仅剩两处硬耦合

| # | 位置 | 性质 | 现状 | 目标 |
|---|------|------|------|------|
| 1 | `YisuExpressPushService::syncRecycleOrderDelivery()` 第 341 行 | 快递**直接写**回收订单物流状态（`RecycleOrder::update`） | 直接改回收的表 | 改为抛领域事件，**回收侧监听器**自己写自己的表 |
| 2 | `RecycleExpressService` 第 150/319/385 行、`ExpressOrderService` | 快递**直接读** `RecycleOrder` 带出寄/收件地址 | 直接 `use RecycleOrder` | 走一个窄读取契约（`RecycleOrderAddressProvider` 接口），快递只依赖接口不依赖回收模型 |
| 3 | `RecycleExpressEventListener` 写 `RecycleOrderLog` | 写订单日志 | **已事件化**（监听 `RecycleExpressEvent`） | 保持，归位到回收侧 listener |

> 按《二开约束》§2.1.4：插件内/插件间协作应走**事件**或**约定契约**，不应让一条业务线直接读写另一条业务线的模型。当前同插件内虽不违规，但正是这两处直读直写让快递"自洽不起来"。

## 三、目标分层（抽象模型）

```
┌─────────────────────────────────────────────────────────────┐
│  业务服务层（各自独立，互不引用）                              │
│                                                               │
│   快递 Express        设备查询 DeviceQuery   打印 Printer  地址 Address │
│   ├ 下单/查询/对账     ├ 机型/参数查询         ├ 模板/打印    ├ 地址解析  │
│   ├ 自己的 Provider    ├ 自己的 Provider       ├ ...          ├ 自己 Provider│
│   └ 自己的配置 schema  └ 自己的配置 schema                              │
└───────────────┬───────────────┬───────────────┬───────────────┘
                │ 只通过窄接口 call() 向下依赖                    │
┌───────────────▼───────────────────────────────────────────────┐
│  基础设施层 Infrastructure（不认识任何业务，一份，共享）        │
│   Provider 加载/派发 · 配置中心读写 · API 日志 · 成本统计 · 余额/健康检查 │
│   = 现在的 CoreThirdPartyService（瘦身后）+ BaseProvider          │
└───────────────────────────────────────────────────────────────┘

   快递 ⇄ 回收：只通过【事件】+【窄读取契约】，不互相引用模型
```

**判定基准**：一个类如果"既知道怎么调通道、又知道快递业务规则"，就是分层没切干净——通道知识下沉基础设施，业务规则留在业务服务。

## 四、目录与类边界（before → after）

> 全部在 `addon/hsx_recycle/app/` 内移动/重命名，**不出插件**。命名空间仍 `addon\hsx_recycle\app\...`。

### 4.1 基础设施层（瘦身 + 正名）

| 现状 | 目标 | 动作 |
|------|------|------|
| `service/core/third_party/CoreThirdPartyService.php` | `service/core/integration/IntegrationGateway.php`（暂名，可保留原名） | 只留：派发 `call()`、Provider 加载、日志、成本统计、余额、健康检查。**剥离**任何业务默认值 |
| `service/core/third_party/provider/BaseProvider.php` | `service/core/integration/provider/BaseProvider.php` | 基类随基础设施走 |
| `RecycleThirdPartyConfigService` 中通用部分 | `service/core/integration/IntegrationConfigService.php` | 只留通用配置读写；`getPrinterConfig` 等**业务方法移交各业务服务** |

### 4.2 业务服务层（各归各家，把 Provider 收回各业务名下）

| 业务 | 目标目录 | 收纳内容 |
|------|----------|----------|
| 快递 Express | `service/core/express/` | 合并散落的 `ExpressOrderService` + `RecycleExpressService` + `YisuExpressPushService`，统一更名去掉 `Recycle` 前缀（如 `ExpressOrderService` / `ExpressPushService`）；`provider/express_order/*`、`provider/express_query/*`、`provider/delivery/*` 迁入 `express/provider/` |
| 设备查询 DeviceQuery | `service/core/device_query/` | `provider/device_query/Provider3023.php` 迁入；其配置 schema 自带 |
| 地址解析 Address | `service/core/address/` | `provider/address_parse/*` 迁入 |
| 打印 Printer | `service/admin/printer/` | 从配置服务接回 `getPrinterConfig` 等打印专属逻辑 |

### 4.3 快递↔回收的契约与事件（保体验、断直连）

| 新增 | 位置 | 作用 |
|------|------|------|
| 事件 `ExpressDeliveryStatusChanged` | 快递服务 `event(...)` 抛出 | 取代 `syncRecycleOrderDelivery` 直接写回收订单 |
| 监听器 `ExpressDeliveryStatusListener` | `app/listener/express/`（回收侧） | 接事件后由**回收自己**更新 `RecycleOrder` 物流状态 + 写 `RecycleOrderLog` |
| 接口 `RecycleOrderAddressProvider` | `app/service/core/express/contract/` | 快递取寄/收件地址只依赖此接口；实现类读 `RecycleOrder`，快递不再 `use RecycleOrder` |

> 注：保留现有 `RecycleExpressEvent` 兼容期并行，迁移完成再下线，避免一刀切。

## 五、守住的红线（重构期间不踩）

1. **不入侵核心**：全部在 `addon/hsx_recycle/` 内，不碰 `core/`、主工程 `app/`、框架配置（《二开约束》§一）。
2. **不改框架表 / 不动历史 SQL**：本次是**代码搬迁 + 命名 + 事件化**，不涉及表结构变更。若某步需要新增字段，单独走 `update_<版本>.sql` 并升 `info.json`（§3.1）。
3. **`site_id` 隔离照旧**：迁移不改变任何 `where('site_id', ...)` 与服务端注入逻辑。
4. **提交纪律**：每步一个 `refactor(hsx_recycle): ...` 提交，scope 标插件，核心与业务不混提（《研发流程规范》§2）。
5. **体验不降级**：每步完成后，回收订单"一键寄件 + 状态回写 + 订单日志"必须可跑通（验收点见 §六）。

## 六、分步重构计划（小步、可独立验证、可回滚）

> 原则：**每步都让代码处于可运行、可回滚状态**；先并行兼容、再切换、最后清理。一把梭是这类重构最大的坑。

| 步 | 动作 | 风险 | 验证点 | 可回滚 |
|----|------|------|--------|--------|
| **0** | 建立基线：跑通现有"下单→推送→回写订单→订单日志"主流程，记录现状行为 | 无 | 截图/日志留底 | — |
| **1** | 基础设施正名：抽出 `IntegrationGateway`（瘦身版 CoreThirdPartyService），保留旧类为**薄转发**兼容 | 低 | 各业务调用面不变、`call()` 行为一致 | 删新增、还旧类 |
| **2** | Provider 归位：把 express/device/address 的 Provider 迁入各业务 `provider/` 目录，更新 `getProviderClass()` 解析路径 | 中（路径解析） | 每个 Provider 能正常加载、`class_exists` 不告警 | git revert 该步 |
| **3** | 配置服务瘦身：通用配置留基础设施，`getPrinterConfig` 等业务方法移交对应业务服务 | 中 | 打印/快递/设备各自配置读写正常 | revert |
| **4** | 快递代码归拢：`ExpressOrderService` 从 core 根迁入 `express/`，与 `RecycleExpressService`/`YisuExpressPushService` 合并去 `Recycle` 命名；路由/控制器引用同步更新 | 中高（引用面广） | 快递下单/查询/对账接口全绿 | revert |
| **5** | 断直写：新增 `ExpressDeliveryStatusChanged` 事件 + 回收侧监听器，替换 `syncRecycleOrderDelivery` 的直接 `RecycleOrder::update` | 高（联动核心） | **回收订单物流状态、订单日志与步0一致** | 监听器与直写并行一版，对比无差再删直写 |
| **6** | 断直读：引入 `RecycleOrderAddressProvider` 接口，快递取地址改走接口，移除快递对 `RecycleOrder` 的 `use` | 中 | 寄/收件地址带出与步0一致 | revert |
| **7** | 清理兼容层：下线旧 `third_party` 转发类、旧 `RecycleExpressEvent`（确认无引用后） | 低 | 全量回归 + grep 无残留引用 | revert |
| **8** | 收尾：更新本文 + 插件 `docs/`，必要时升 `info.json` 修订号 | 低 | 文档与代码一致 | — |

**每步统一验收清单**（对齐《研发流程规范》§五）：
- 快递主流程（下单/查询/对账）跑通；
- 联动：回收订单一键寄件 → 物流状态回写 → 订单日志，行为与步0一致；
- 多租户：两个 `site_id` 验证不串号；
- `php think queue:work` 下推送任务正常消费；
- grep 确认本步该断的引用已断、不该动的没动。

## 七、风险与回滚总纲

| 风险 | 缓解 |
|------|------|
| 步4/5 引用面广，易漏改 | 每步 grep 全量引用清单；改完静态检查（`php -l`）+ 跑回归 |
| 状态回写行为漂移 | 步5"事件 + 直写"并行一版做 A/B 比对，确认零差异再删直写 |
| Provider 路径解析改错导致通道失效 | `class_exists` 守卫已兜底（只告警不崩）；逐 Provider 验证 |
| 中途要停 | 每步独立提交且自洽，可停在任意步，系统始终可运行 |

## 八、不做什么（划清边界）

- **不拆成独立插件**：快递仍在 `hsx_recycle` 内，只是服务自洽。
- **不复制基础设施**：通道能力共享一份，杜绝"为解耦而复制"。
- **不改表结构 / 不动历史升级脚本**：本次纯代码层重构。
- **不入侵核心框架**：全程在 addon 业务区。
