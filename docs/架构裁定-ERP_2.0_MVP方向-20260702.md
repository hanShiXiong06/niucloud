# 架构裁定 · ERP 2.0 MVP 方向（2026-07-02）

> 性质：架构方向裁定书。本文是给执行 Agent 的**唯一方向依据**，与旧文档冲突时以本文为准。
> 前置审计：已通读 docs/ 全部 ERP 相关文档、git 历史、以及当前未提交的 253 个文件变更（ERP 2.0 重构现场）。

---

## 一、总裁定：续建 2.0，不再推倒

经代码级审计，当前未提交的 ERP 2.0 重构**方向正确、质量合格**，裁定为：**在 2.0 现有代码上补齐缺口，禁止再次推倒重来。**

审计确认的事实（不是文档宣称，是读码结论）：

**已经真实做出来的：**
- 21 张 2.0 新表（`sql/install.sql` 已净化，无旧表），8 个新 Service，旧 1.0 后端（23 个 service、31 模型）已整体删除，无新旧混杂。
- 采购闭环完整：开单 → 生成资产（一物一码）→ 生成应付 → 财务确认付款 → 核销 + 资金流水（`ErpPurchaseService` / `ErpFinanceService`）。
- 销售闭环完整：选库存 → 出库 → 生成应收 → 财务确认收款 → 核销 + 毛利计算（`ErpSaleService`）。
- 折账（offset）独立实现完整，成本调整实现完整。
- 三本流水（账目 account_ledger / 资金 money_ledger / 资产 asset_ledger）在写入点真实落笔；全部写操作有事务；金额 decimal(12,2)。
- 前端 `admin/src/addon/hsx_erp/views/erp/` 七个页面（工作台/采购/销售/应收/应付/仓库/资金账户）完整可操作，动线清晰。

**审计实锤的缺口（MVP 必须补，见第三节）：**
1. **无纠错闭环**：采购退货、销售退货、单据作废/红冲全部缺失。这是 1.0 走查报告（6/30）就点名的第一硬伤，2.0 仍未解决。
2. **无库存页**：前端没有独立的"库存/设备档案"页面。"货在哪里一眼看到"是核心诉求，目前只能从销售开单的选机弹窗侧面看库存。
3. **事件层是死桩**：`event.php` 为空，`publishOutbox`/`recordInbox` 零调用方；回收（hsx_recycle）和商城（phone_shop）的监听器还在监听 1.0 的旧事件（`ErpDomainEvent`、`ErpAssetCostAdjusted`、`erp.asset.sold.v1` 等），**这些事件已无人发出**——跨插件联动目前全部静默失效（有 class_exists 守卫，不会报错，但也不会发生任何事）。
4. 字典防漂移护栏（1.0 教训：枚举与中文字典各写各的 → 界面漏英文）未在 2.0 建立。

## 二、定死的架构规则（执行 Agent 不得偏离）

1. **财务留在 ERP 内部。** 旧文档《插件独立与集成架构.md》中"财务拆独立插件"的方向**作废**。应收/应付/结算/折账/资金账户是 ERP 的核心枢纽，不外拆。（理由：MVP 要闭环，拆财务会把一个闭环变成两个插件间的分布式事务。）
2. **一物一码是唯一库存主线。** `erp_asset` 每台设备一条记录，二手机、新机同等对待（都有 IMEI/SN）。**所有账必须挂设备**：应收应付带 asset 维度，流水精确到台——这是"颗粒度到每台设备"的落点，现有 schema 已支持，不得退化。
3. **配件（数量型库存）本期不做，但定死扩展点**：未来在 `purchase_item`/`sale_item` 上加 `item_type`（device/accessory）+ `qty`，数量型库存另建 `erp_sku_stock` 表，**不复用 erp_asset**。执行 Agent 现在唯一要做的是：不要写出"假设明细必有 IMEI"的硬编码校验逻辑之外的耦合（校验本身保留）。
4. **维修/整备在 MVP 中 = 成本追加。** 不做整备工单。设备维修花的钱走"成本调整"（已实现），`refurbish_cost` 字段留给二期工单。对外维修业务（给客户修机收钱）不在本插件范围。
5. **跨插件联动只走事件，且 MVP 内先把"出口"埋上。** 规则：
   - 外部插件永远不写 ERP 表；ERP 永远不 use 回收/商城的类。
   - ERP 在核心写入点（采购入库、出库售出、退货、收款/付款确认、成本调整）调用 `ErpIntegrationService::publishOutbox()` 落 outbox 记录——**本期只落表，不做投递**。事件名沿用 2.0 方案：`erp.purchase.created / erp.asset.in_stock / erp.asset.sold / erp.sale.returned / erp.purchase.returned / erp.payment.confirmed / erp.receipt.confirmed / erp.offset.confirmed`。
   - 回收/商城的旧监听器**本期不改不删**（反正静默），打通是 MVP 验收后的独立阶段：届时做 outbox 投递器 + 双侧适配器（回收→inbox 采购事件、outbox→商城下架/订单）。
   - 幂等键规范不变：`event_id + source_plugin + source_type + source_id`。
6. **错账不涂改，红冲再重记。** 一切纠错通过反向流水/调整流水，禁止 UPDATE 历史流水、禁止物理删除已确认单据。
7. **所有钱的动作必须过财务确认队列**（2.0 已实现的模式，保持）。业务人员发起，财务确认后才核销、才落资金流水。
8. **枚举即字典**：每个写入库的枚举值必须在 `ErpDict` 有中文映射；取词统一走字典，缺失时显示"未知(原值)"而非裸英文；恢复 1.0 的护栏扫描脚本思路，防再漏。

## 三、MVP 补齐清单（按优先级，做完即可上线试用）

### P0-0 前后端能力对齐 —— 后端已实现但前端没接出（2026-07-02 实测新增）
> 来源：用真实账号在界面上走"一进一出"实测发现。后端能力是好的，前端没接出来，还留下"文案承诺了、按钮没做"的空头文案，是 1.0"不知道点哪"病根的原样重演。这类活便宜（后端现成），但对"用户能不能用上"是决定性的。

- **折账（offset）前端补全**【进行中，Claude 亲做，作为"前端接后端能力"的范式】：
  - 现状：后端 `finance/offset` 完整可用（实测能折），但前端 `api/erp.ts` 无 offset 函数、`views/` 无任何折账入口；`payable/list.vue:7` 文案却写着"付款和折账都以往来主体为入口"——说了没做。
  - 做法：应付页每行供应商操作列加"折账"按钮（同时有剩余应付+剩余应收才可点）；弹窗并列该主体的应付明细与应收明细，勾选后可折金额=min(勾选应付剩余, 勾选应收剩余)，默认填满；提交 `finance/offset`。后端零改动。
  - 验收：用韩世雄(party_id=1)现存的应付3500 + 应收3700，界面上折3500→应付清零、应收剩200→再收200→两清。

- **按供应商整体付款 `confirm_party_payment`**：后端有，前端未接。可作为便宜活派执行 Agent，照折账范式接出。

- **结算明细视图（"这台机的钱怎么结的" —— 2026-07-02 实测新增，Claude 亲做）**：
  - 现状：`erp_settlement` 表完整记录每笔结算的**方式**（付款/收款/**折账**）+ **账户名**（现金/微信/支付宝/银行卡）+ 金额+经手人+时间，但**后端无任何查询接口**（表只进不出），前端无展示。
  - 缺口本质：现有两本流水都只有半张脸——账目流水(`account_ledger`)有业务动作但**不带账户**；资金流水(`money_ledger`)有账户但**只记现金、折账不出现**。没有任何视图能回答"应收3700=折账3500+微信200"。这正是验收十二问里"能否和银行卡/微信/支付宝对上"那一问答不了的原因。
  - 做法：后端加"结算明细查询"接口（`erp_settlement` + `settlement_link`，可按往来单位/设备/时间筛，返回方式+账户+金额+关联单）；前端把它作为**第三本流水**呈现（与账目/资金流水并列），并在 P0-2 设备档案页的"一机一生"时间线里按设备展示结算记录。

### P0-1 纠错闭环（最大缺口，无此不能上生产）
- **采购退货**：按付款状态三分支——未付款：冲销应付+资产退回；已付款：生成应收退款+资产退回；部分付款：混合。全部写账目流水+资产流水。
- **销售退货**：资产回在库（或回整备），应收作废/生成应付退款（已收款时），写流水。
- **单据作废（void）**：未发生资金往来的采购单/销售单可作废，反向冲流水；`status` 里的 void 必须有人写它。
- **应收/应付调整**：显式入口（不只藏在"调成本"里），追加调整流水。

### P0-3 收款侧对称化 —— 逐台收款 + 多账户收款（2026-07-02 实测新增，需专门设计）
> 来源：用户实测付款侧后提问"收款是不是也该逐台、多账户、多次"。核对结论：付款侧做了全套，收款侧没有。三点缺口性质不同，需单独设计后再动手，不在折账这种"接前端"的量级。

- **逐台收款（要动数据模型）**：应付在库里是"一台一笔"(`purchase_asset`)，所以付款页能逐台点开；应收在库里是"一张销售单一笔"(`source_type=sale` 整单合计)，没拆到台，所以收款只能对整单收。要做到像付款那样逐台/逐型号收款，需把应收从"按单"改为"按台"生成——牵扯 `ErpSaleService::create` 生成应收的方式、以及未来商城对接回填。属中等工程，非"接个按钮"。
- **多账户收款（后端+前端都缺）**：`confirmReceipt`/`confirmPayment` 目前只接单个 `capital_account_id`，一次收付只进出一个账户。商城对接契约文档已设计 `payments[]`（账户+方式+金额数组）但代码未实现。**此项的正主是 ERP↔商城打通**，届时连着一起设计，避免现在单独在 ERP 后台做后返工。
- **多次分批收款**：✅ 已支持（partial 状态可继续收），无需改。
- 排期：折账(P0-0)之后；逐台收款与 P0-1 退货可一并考虑（都触及应收生成方式）；多账户收款并入商城对接阶段。

### P0-2 库存管理页（"货在哪"）
- 新增 `views/erp/stock/`：资产列表（状态/仓库/库位/型号/IMEI 筛选）+ **设备档案详情**（一台机器的一生：采购单→成本调整→销售单→关联应收应付→三本流水时间线）。后端资产查询接口已基本具备，主要是前端组装 + 一个设备详情聚合接口。
- 这一页是"监管追溯"模块在 MVP 的最小形态，也是老板视角的核心页面。

### P1-1 事件出口埋点
- 按第二节规则 5，在各 Service 写入点调用 `publishOutbox`。工作量小（每个写入点一行），但决定了后续打通回收/商城时**不用再改核心代码**。

### P1-2 工作台补角色视角
- 现有工作台已有待付款/待收款/库存概览。补齐：今日收支、应收应付余额合计、库存台数+库存金额（2.0 方案第一阶段范围内的最后几项）。

### P1-3 字典护栏
- 补全 2.0 各枚举的中文 map + 护栏脚本（扫代码写入的枚举值 vs 字典，缺失报警）。

### 明确不做（二期再议，禁止本期夹带）
- 整备工单、盘点、调拨、配件/数量型库存、多维报表引擎、KPI 看板扩展、AI 助手、移动端 ERP、回收/商城实际打通、员工绩效薪酬。

## 四、MVP 验收标准（唯一验收口径）

**剧本验收**（拿一台真机走一生，每步查账）：
1. 采购开单 → 资产在库、应付生成且金额对、挂在这台设备上
2. 财务确认付款 → 应付核销、资金账户扣款、流水可查
3. 成本调整 → 总成本变化有流水、应付联动正确
4. 销售出库 → 应收生成、资产状态 sold、毛利=售价−总成本
5. 财务确认收款 → 应收核销、资金账户进账
6. 销售退货 → 资产回在库、账目反向冲、流水完整
7. 采购退货（另一台）→ 三种付款状态各验一次
8. 折账 → 同一往来单位应收应付互抵，不产生现金流水

**十二问验收**（沿用 2.0 方案）：这台机器从谁买的/成本多少/调过几次为什么/付了多少还欠多少/现在在哪个仓/卖给谁/卖多少/收了多少还欠多少/有没有折账/利润多少/每笔钱谁确认的/能不能和银行卡微信支付宝对上。任一问在系统里点不出来即不通过。

**三处对账**：应收应付明细 ⟺ 往来汇总 ⟺ 资金账户流水，随时抽查必须相等。

## 五、产品/UX 方向（治"功能堆叠"的病根）

1. **菜单就是业务动线，最多 8 项**：工作台 / 采购 / 库存 / 销售 / 应收款 / 应付款 / 账目流水 / 基础设置。不再按"服务"或"功能"加菜单；新能力优先长在既有页面的动作里（按钮/抽屉），而不是新菜单。
2. **工作台是唯一入口**：每个角色进来先看到自己的待办卡（财务：待确认收/付/折账；采购：进行中采购单；老板：今日收支+库存家底），点卡片直达处理页。用户永远知道"下一步点哪"。
3. **每个页面回答一个问题**：采购页="货怎么进来的"、库存页="货在哪"、销售页="货怎么卖的"、应收/应付="谁欠谁"、流水="钱怎么动的"。页面内不混业务域。
4. **"为什么"前置**：账目列表默认展示 来源单号+设备+经手人，不让用户点三层才知道这笔账是哪台机器。

## 六、工程动作（执行顺序）

1. **立即提交 checkpoint**：当前 253 个未提交变更先落一个 commit（或 `erp-2.0` 分支），旧代码在 git 历史里，不需要留工作区副本。这是所有后续工作的前提——现在任何一次误操作都可能丢掉整个重构。
2. 按第三节顺序开工：P0-1 纠错闭环 → P0-2 库存页 → P1 三项。每项独立提交、每项跑一遍第四节剧本对应段落。
3. 每个执行 Agent 接任务时只给它：本文 + 对应任务段落 + 相关文件路径。不要把全部历史文档喂给它（旧文档存在方向冲突，已由本文收口）。
