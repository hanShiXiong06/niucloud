# 阶段 1 · 数据模型 + 升级迁移方案（待评审）

> 目标：在已 fork 成型的 `phone_shop`（基于 shop 1.6.1）上，定下二手机数据模型，并解决"老 phone_shop(1.3.3) 线上数据平滑升级、不丢"的核心问题。
> 原则：先纸面对齐，确认后再建表/写迁移。

---

## A. 升级迁移策略（保住线上老数据 —— 最关键）

**问题**：当前 `install.sql` 是 `DROP TABLE IF EXISTS` + `CREATE TABLE`（53 张表）。直接在有老数据的库上"安装"，会先 DROP 掉老 `phone_shop_*` 表 → **线上数据全丢**。

**方案（推荐：智能 install/upgrade 钩子）**：改造 `Addon.php` 的 `install()` / `upgrade()`：
1. 检测库里是否已存在老 `phone_shop_goods` 等表：
   - **存在（老用户升级）** → 走"迁移路径"：只 `ALTER TABLE` 加列、转换字段、补默认值，**绝不 DROP**。
   - **不存在（全新装）** → 正常跑 install.sql（DROP-CREATE 无害）。
2. 迁移逻辑放在专门的迁移类里（参考框架 `app/upgrade/vXXX/Upgrade.php` 的 `handle()` 套路），用 ALTER + 数据回填。

> 备选：把 install.sql 的 DROP 去掉、改 `CREATE TABLE IF NOT EXISTS` + 独立迁移脚本。但智能钩子更稳，老用户/新用户一套逻辑都覆盖。

## B. 现有字段对齐（老 phone_shop → 新 shop 结构）

对比已做完，三张核心表差异如下：

### goods 表
| 老列 | 处理 |
|---|---|
| `attr_id`(单值) | → 新 `attr_ids`(多值)：迁移时 `attr_ids = "[" + attr_id + "]"` |
| `memory_group`(内存) | **保留**：ALTER ADD 回新表（二手机要用） |
| `source`(来源) | **保留** |
| `goods_no`(联动下架键) | **保留**（联动下架虽停用，数据先留） |
| `goods_url` | **保留** |
| `is_proxy`(代理) | **保留休眠**（代理作废，但不删老数据） |
| shop 新增 19 列（attr_ids/goods_video/form_id/限购/统计等） | ALTER ADD，给老行填默认值 |

### order 表
- shop 新增 6 列（`shop_remark`/`relate_order_id`/`relate_source`/`buyer_ask_delivery_time`/`form_record_id`/`user_delete_time`）→ ALTER ADD 默认值。
- 老订单"商家留言"列（老库里是 `<prefix>phone_shop_remark`）→ 迁移进新 `shop_remark`。

### goods_sku 表
- 新老结构**一致**，无需迁移（最省事）。

## C. 二手机二开 · 净新增字段（为阶段 2 铺路）

这些是老/新 shop 都没有、二手机业务要新增的：

### goods 级
- `condition_grade` 成色等级（如 全新/99新/95新…，或走 label/attr，待定）
- `is_online_sellable` 是否允许上用户端自行购买（线上自购开关，tinyint）

### goods_sku 级（一物一码核心）
- `erp_asset_id` **关联 ERP 设备资产唯一 ID**（一物一码关联键，回收侧 `downstream_erp_asset_id`）
- `is_unique` 一物一码标记（1=整机单台，库存恒 1；0=标品多件）
- `imei` = 复用现有 `sku_no`（仅搜索/展示，不唯一）
- `device_snapshot`（可选）质检结果/成色快照 json，下架后留痕

### order 级（挂账 + 混合支付）
- `payment_mode` 支付方式：`online`(微信线上) / `offline_credit`(线下挂账) / `offline_cash`(线下现结)
- `is_credit` / `credit_status` 挂账状态（挂账成立 / 已结清 / 已冲销退货）
- `buyer_type` 买家类型：`c`(散客) / `b`(同行)
- `source_device_id` 关联 ERP 设备（整机订单精确到机）
- `staff_id` 开单销售员（极速开单留痕）
- `settle_status` 结清状态（应收核销/折账用）

## D. 内存维度（待决策）

- 老 phone_shop 有 `phone_shop_memory_group` / `phone_shop_memory_spec` 表 + `goods.memory_group` 列。
- 新 fork(shop) **没有**这些表（shop 用通用 `goods_spec` 规格系统）。
- **两种实现**：
  - (a) **沿用老的独立内存表** → 迁移老数据直接、二手机语义清晰。
  - (b) 用 shop 的 `goods_spec` 规格系统承载内存。
- **建议 (a)**：把 memory 两张表纳入新 install.sql + 保留 `goods.memory_group` 列，迁移最平滑。
