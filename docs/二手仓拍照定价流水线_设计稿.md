# 二手仓「拍照 → 定价 → 上架」流水线 · 设计稿（待评审）

> 目标：给仓库加一个「是否必须拍照」开关。开启的仓，设备进仓前必须先拍照，再由销售/库管定价，凑齐「价格+图片+质检」三要素后推送商城「待上架货源」，由中台员整理上架。关闭的仓，设备不拍照、直接在 ERP 定价即可销售。
> 角色拆分：拍照员、定价员(=库管=销售)、中台员三类人各看各的任务队列，把重复性信息整理从销售手里解放出来。

---

## 0. 一句话认知（已与需求方对齐）

- 仓库配置 `require_photo`（是否必须拍照）是**独立开关**，按**目的仓**判定进仓门槛：
  - 开 → 进此仓（无论入库还是调拨进来）**必须先拍照**，走拍照定价流水线。
  - 关 → 进此仓**永不**要求拍照；ERP 直接定价即可卖；同行/直接发走走现有「现结/价格回填」。
- 「待拍照」做成**独立状态**：拍照阶段设备**逻辑上还没在库**（已指派到该仓、待拍照），**拍完才真正入仓**。
- 拍照/定价/整理分别绑给**三个角色**，各有任务队列；操作支持**整筐批量**与**单台**两种。

---

## 1. 现状（读码确认，避免重复造）

- `erp_warehouse.business_type`：mall/peer/consignment/scrap/hold（=销售流向），**已有**。
- 商城销路设备入库/整备后，ERP 已发 `erp.asset.ready_for_photo.v1`，注释写明「委托中台拍照定价，定价回流转可售」，**已有**。
- 质检 JSON：`erp_asset.check_snapshot`（来源质检快照，JSON），回收入库时 `ErpInboundService` **已经在接** `device.check_snapshot`，模型按 JSON 存。→ **质检数据已在 ERP，不必跨组件实时读**。
- 现状链路：**hsx_device_asset(中台)** `DeviceAssetService::price()` 做拍照+定价 → 发 `DeviceAssetPriceCompleted` → **phone_shop(商城)** 落 `phone_shop_device_intake`（待上架货源）→ 人工建品上架。契约见 `docs/二手商城_货源入库_事件payload契约.md`。

## 2. ★ 架构决策（已定稿）：双路 + 单一出口，device_asset 保留

**不把 device_asset 揉进 ERP。** 经评估，device_asset 的真身是"**自动化拍照设备对接 + 小程序工单（拍照/定价派单）**"——photo_task / media / price_order 三张表正是为此服务，它是一个面向硬件和小程序 App 的、有边界的工单子系统，不该被溶解。

采用**双路结构，共用单一出口事件**：

- **正规路（有回收 + 拍照设备 + 小程序）**：
  回收质检 → ERP 入库（require_photo 仓）→ device_asset 生成拍照工单 → 拍照员（设备/小程序）拍 → 定价员定价 → 三要素齐 → `DeviceAssetPriceCompleted` → 商城「待上架货源」。
- **轻量路（无回收，手工入库）**：
  ERP 手工建档时**内联补**图片 + 价格 + 简单质检 + 基本信息 → 三要素齐 → ERP **直接发** `DeviceAssetPriceCompleted` → 商城「待上架货源」（**不生成工单**）。

> 两条路终点相同：`DeviceAssetPriceCompleted` → phone_shop `待上架货源`。商城侧零改动、零感知。

**职责边界：**
- `device_asset`：硬件拍照设备对接、小程序角色派单、拍照/定价工单（重型、正规流程）。
- `hsx_erp`：仓库 `require_photo` 配置、`待拍照` 状态、手工入库轻量内联三要素、对外发出口事件。
- `phone_shop`：`待上架货源` 整理上架（已有页面，不动）。

> 为什么不揉：device_asset 虽与 ERP 耦合，但它对接硬件+小程序，是独立演进的集成面；揉进来要迁 6 张表+搬 4 页+保留对外事件，收益不抵成本。保留它、ERP 走轻量内联路，职责更清、改动更小。

> 落地顺序：**先做"轻量路"**（手工入库内联三要素 → 推商城），它不依赖任何工单/硬件改造，能最快跑通"无回收也能上架"。正规路（require_photo 门槛 + 待拍照状态 + 工单角色队列）随后分期。

## 3. 仓库 / 库位配置（新增字段）

`erp_warehouse` 增：
- `require_photo` tinyint(0/1)：是否必须拍照进仓。默认 0。
- `photographer_uid` int：默认拍照员（仓库级）。
- `pricer_uid` int：默认定价员/库管（仓库级）。

`erp_warehouse_location`（库位）增（可选覆盖，量大时按库位分人）：
- `photographer_uid` int：本库位拍照员（>0 时覆盖仓库级；如苹果库位/安卓库位分人）。
- `pricer_uid` int：本库位定价员（>0 时覆盖仓库级）。

> 取人规则：先看库位级，没配再回落仓库级。

---

## 4. 状态机（新增「待拍照」）

现有库存状态：`pending_in 待入库 / in_stock 在库 / refurbishing 整备中 / pending_pricing 待定价 / available_for_sale 在售 / locked / outbound / lost`。

新增：`pending_photo 待拍照`（已指派到该仓、待拍照、**逻辑未在库**）。

**进"要拍照的仓"的设备走这条线：**

```
回收质检完成 / ERP建档 / 调拨入此仓
        │  目的仓 require_photo = 1
        ▼
   【待拍照 pending_photo】 ── 拍照员队列（逻辑未在库）
        │  拍照员逐台或整筐上传图片并确认
        ▼
   入仓在库 +【待定价 pending_pricing】 ── 定价员=库管队列
        │  定价员定价（此刻三要素齐：价格 + 图片 + 质检JSON）
        ▼
   推送商城「待上架货源」（DeviceAssetPriceCompleted）
        │  中台员在 phone_shop 配分类/品牌/内存、确认价、勾图
        ▼
   【上架·在售 available_for_sale】 ── 商城可见可卖
        │  行情波动
        ▼
   销售【调价】（在售可改价，回写商城）
```

**进"不拍照的仓"的设备**：跳过 pending_photo，按现有逻辑 `待定价/可售`；同行/直接发走走「现结 / 价格回填」。

## 5. 进仓门槛规则（入库 & 调拨统一）

判定只看**目的仓 `require_photo`**：

| 场景 | 目的仓 require_photo | 行为 |
|---|---|---|
| 入库 / 调拨进 A 仓 | 1 | 先置 `待拍照`，拍完才入库在库 |
| 入库 / 调拨进 B 仓 | 0 | 直接入库在库，可直接 ERP 定价卖 |
| 商城仓 → 同行仓(不拍照) | 0 | 直接调拨进，之前拍没拍过都无所谓 |
| A 仓(拍照) → B 仓(拍照) | 1 | 进 B 仍需拍照（可能只是 1-2 台，单台拍） |

> 即：拍没拍过不看来源，只看"你要进的这个仓要不要"。

## 6. 三个角色 · 任务队列

| 角色 | 是谁 | 看什么队列 | 干的活 |
|---|---|---|---|
| 拍照员 | 仓库/库位绑定 | **待拍照**（按其负责的仓/库位过滤） | 每台拍清楚、传图、确认；可整筐批量确认 |
| 定价员 | =库管=销售（仓库/库位负责人） | **待定价**（拍完流转过来的） | 定价；三要素齐后自动推商城；后续行情调价 |
| 中台员 | 商城 phone_shop 操作员 | **待上架货源**（已有页面） | 配三级分类/品牌/内存/成色、确认价、勾图、上架 |

队列即"我的活儿来了"：拍照员只看待拍照、定价员只看待定价、中台员只看待上架货源。

## 7. 三要素 & 质检 JSON 透传

- **三要素 = 价格(定价员) + 图片(拍照员) + 质检JSON(回收 check_snapshot)**。
- 质检 JSON 已在 `erp_asset.check_snapshot`（结构不固定、含颜色标识等）。定价完成推送时，按 `DeviceAssetPriceCompleted` 契约把 `qc_info`(=check_snapshot 原样)、`images`、`sale_price/peer_price/cost_price`、`model/memory/color/...` 一并带给商城。
- 商城端用**低代码组件**渲染 qc_info（不在 ERP 解析质检结构）。
- **待回收方确认**：回收发入库事件时，`device.check_snapshot` 是否塞了**完整**质检 JSON（含颜色标识）。需求方提供回收质检返回样例，对齐字段后即可全程透传。

## 8. 事件流（方案 A）

ERP 内部（操作事件脊柱）：
- `erp.asset.assigned_to_photo.v1`：设备指派到"要拍照的仓" → 置 `待拍照`，进拍照员队列。
- `erp.asset.photographed.v1`：拍照完成（含图片URL）→ 入库在库 + 置 `待定价`，进定价员队列。
- `erp.asset.sales_priced.v1`：定价完成 → 三要素齐。

ERP → 商城：
- 沿用 `DeviceAssetPriceCompleted`（`device_asset.price.completed.v1`）：定价完成即派发，payload 按现契约补齐 `images/qc_info/cost_price/...`；phone_shop 按 `erp_asset_id` 幂等落"待上架货源"。

商城 → ERP（留口，暂不做）：
- 调价回流：商城/销售调价 → 通知中台/ERP（契约后议）。

## 9. 边界与例外

- **关拍照的仓**：无 `待拍照`，ERP 直接定价→可售；同行直接发走→现结/价格回填（现有能力，不新做）。
- **调拨单台拍照**：B 仓要拍照但只来 1-2 台 → 支持单台进 `待拍照`、单台拍、单台流转。
- **整筐批量**：质检完一筐进同一仓 → 批量进 `待拍照`；拍照员可"整筐标记完成"批量流转给定价员。
- **调价**：在售设备销售可改价，回写商城（走调价回流口）。
- **不拍照也能卖**：require_photo=0 的仓，定价即可售，跟商城无关。

## 10. 分期落地建议

- **P0**：仓库配置 `require_photo` + 仓库级 `photographer_uid/pricer_uid`；新增 `待拍照` 状态；进仓门槛判定（入库路径先做，调拨次之）。
- **P1**：拍照员队列 + 拍照（传图/确认/批量）；定价员队列 + 定价（复用现有定价，补三要素齐校验）；定价完成推 `DeviceAssetPriceCompleted`(补齐 payload)。
- **P2**：库位级角色覆盖（按品牌/品类分人）；调拨进仓的拍照门槛；调价回流。
- **依赖**：回收 `check_snapshot` 完整性确认（需样例）。
