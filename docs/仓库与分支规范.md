## 一、分支模型（正式 / 预发 / 测试 / 开发）

代码**单向向上流动**，越往上越稳定，禁止跳级与逆向直推：

```
feature/*  fix/*        ← 开发者各自的功能/修复分支
      ↓ 合并(PR)
   dev        集成开发分支（日常开发汇集地，可能不稳定）
      ↓ 提测
   test       测试分支（QA 验证，对应测试环境）
      ↓ 验收通过
   release    预发布分支（封板待发，对应预发/灰度环境）
      ↓ 发布
   main       正式分支（线上生产代码，受保护，只进不改）
                  ↑
            hotfix/*  线上紧急修复（从 main 切出，修完合回 main 并回流 dev）

   official-base   官方框架基线（只读保留，用于跟踪 niucloud 官方升级，不参与日常流转）
```

| 分支 | 角色 | 环境 | 谁能写 | 稳定度 |
|------|------|------|--------|--------|
| `main` | 正式/生产 | 生产 | 仅经 release/hotfix 合入 | 最高（受保护） |
| `release` | 预发布/封板 | 预发/灰度 | 仅经 test 合入 | 高 |
| `test` | 测试 | 测试 | 仅经 dev 合入 | 中 |
| `dev` | 集成开发 | 开发 | feature/fix 合入 | 低（允许不稳定） |
| `feature/<插件>-<功能>` | 功能开发 | 本地 | 开发者 | — |
| `fix/<插件>-<问题>` | 缺陷修复 | 本地 | 开发者 | — |
| `hotfix/<问题>` | 线上急修 | 本地→生产 | 开发者 | — |
| `official-base` | 官方基线 | — | 仅同步官方 | 只读 |

> **正式分支命名**：当前仓库历史用 `main`，本规范沿用 `main` 作为正式分支（不另起 `master`，避免双正式分支混淆）。

## 三、日常流转流程（强制）

### 3.1 开发一个功能/修复

```bash
git checkout dev && git pull            # 基于最新 dev
git checkout -b feature/hsx_recycle-express   # 切功能分支
# ...开发，按《研发流程规范》小步约定式提交...
git push -u origin feature/hsx_recycle-express
# 在 GitHub 发起 PR: feature/* -> dev，至少 1 人 Review 合并
```

### 3.2 提测（dev → test）

```bash
git checkout test && git pull
git merge --no-ff dev                   # 把待测内容并入 test
git push origin test                    # 部署测试环境，QA 验证
```

### 3.3 验收封板（test → release）

```bash
git checkout release && git pull
git merge --no-ff test
git push origin release                 # 部署预发/灰度
```

### 3.4 上线（release → main）

```bash
git checkout main && git pull
git merge --no-ff release
git tag vX.Y.Z                          # 与插件 info.json 版本对应
git push origin main --tags             # 发布生产
```

### 3.5 线上急修（hotfix）

```bash
git checkout main && git pull
git checkout -b hotfix/express-callback
# ...修复...
git checkout main && git merge --no-ff hotfix/express-callback && git push origin main --tags
git checkout dev  && git merge --no-ff hotfix/express-callback && git push origin dev   # 回流，防止下个版本丢修复
```

> 规则：**只能向上一级合并，逐级流转**。禁止 `feature/*` 直接合 `main`；禁止在 `test/release/main` 上直接写业务代码。

## 六、分支保护与权限建议（GitHub 设置）

| 分支 | 建议保护规则 |
|------|--------------|
| `main` | 禁止直接 push；必须 PR；≥1 Review；必须通过 CI；只允许 release/hotfix 来源；管理员也受限 |
