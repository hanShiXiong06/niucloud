# niucloud-admin 二开约束规约（代码业务 · 版本管理 · 禁止入侵核心框架）

> 配套文档：《二开规范_开发文档.md》。本文件是**强制约束**，规范讲「怎么做」，本约束讲「**禁止做什么 / 必须做什么**」，违反即不予合并（PR / 提交驳回）。
> 适用范围：`niucloud`（后端）、`admin`、`web`、`uni-app`、`site-uniapp` **全部工程，一视同仁，无例外**。
> 核心原则一句话：**在 niucloud 基础上做二开，业务一律以插件（addon）承载；严禁入侵、改写核心框架。**

---

## 〇、术语：什么是「核心框架」

以下属于**核心框架（受保护区，禁止修改）**：

| 工程 | 核心框架范围（禁改） |
|------|----------------------|
| `niucloud` 后端 | `core/`、`app/`（含 adminapi/api/service/model/dict/listener/job/command/middleware.php/event.php/provider.php/service.php/common.php 等主工程代码）、`config/`、`route/`、`vendor/`、`think`、安装与升级框架 `app/install`、`app/upgrade` 的既有逻辑 |
| `admin` | `src/`（除 `src/addon/`）、`src/router` 的聚合逻辑、`src/utils/request.ts`、`src/lang/i18n.ts`、`src/components` 公共组件、构建配置 `vite.config.ts`/`publish.cjs` |
| `web` | 根级 `app/`、`composables/`、`stores/`、`middleware/`、`utils/`、`layouts/`、`nuxt.config.ts`（`addon/` 外） |
| `uni-app` | `src/`（除 `src/addon/`）、`src/utils`、`src/locale/i18n.ts`、`pages.json` 主包部分、构建配置 |
| `site-uniapp` | 同 uni-app，**不享受任何例外**：`src/`（除 `src/addon/`）、构建配置等均禁改 |

**业务区（允许开发）**：各工程的 `addon/<插件名>/` 目录，以及后端 `niucloud/addon/<插件名>/`。**二开的全部产出都应落在这里。**

## 一、禁止入侵核心框架（最高优先级）

### 1.1 绝对禁止（红线，任何情况都不允许）

1. **禁止修改 `core/` 下任何文件**（基类、Loader、pay/sms/oauth/printer/util 等）。
2. **禁止修改主工程 `app/` 既有业务代码**（控制器、服务、模型、字典、监听、中间件等）。
3. **禁止修改框架配置与路由聚合**：`config/`、`route/app.php`、`middleware.php`、`event.php`、`provider.php`、`service.php`、各前端的 `vite.config.ts` / `nuxt.config.ts` / `publish.cjs` / `request.ts` / `i18n.ts` 等聚合与构建逻辑。
4. **禁止改动 `vendor/` 及任何第三方依赖源码**（需要补丁时见 §1.4）。
5. **禁止为了图方便而「直接改框架」绕过插件机制**（如把业务路由塞进主工程 `route/`、把业务字段加进框架表结构、把业务监听写进主工程 `app/event.php`）。
6. **禁止删除或重写核心既有的方法签名 / 常量 / 事件名**，即使「看起来没人用」。

> 判定基准：一次改动若发生在「核心框架范围」表所列路径内，默认即为违规，需走 §1.3 例外流程并经评审批准。

### 1.2 必须改用的「非入侵式」手段

需要扩展框架能力时，按下列优先级选择，**不得直接改核心**：

| 诉求 | 正确做法 |
|------|----------|
| 想在框架某动作后加业务逻辑 | 监听**已有事件**（`event('Xxx', ...)`），在插件 `app/listener/` 写监听器 |
| 想扩展支付/短信/存储/打印等通道 | 继承对应 `Base*` 基类，通过对应 `*Loader` 注册，不改 Loader 本体 |
| 想给框架表加业务字段 | **优先新建插件业务表**（带 `site_id`）做关联；确需扩列时，在插件 `Addon::install()` 内用 `ALTER TABLE ... ADD COLUMN`（幂等：先 `SHOW COLUMNS` 判断），并在 `uninstall()` 中清理 |
| 想加后台菜单/权限 | 在插件 `app/dict/menu/{admin,site}.php` 声明，由安装写入，不手改 `sys_menu` 数据或框架代码 |
| 想加路由 | 写在插件 `app/adminapi/route/route.php` / `app/api/route/route.php`，挂标准中间件 |
| 想复用/微调核心服务 | 在插件 `service/core` 内**组合/包装**核心服务（调用而非改写）；需要不同行为则继承后重写子类，不动父类 |
| 想加前端页面/接口/多语言 | 全部放 `<端>/addon/<插件名>/` 下，由动态聚合机制自动加载 |

### 1.3 例外流程（确实无法通过扩展点实现时）

仅当框架**缺少必要扩展点**导致业务无法实现时，方可申请改核心，且必须：

1. 先提 issue/说明，记录「为什么扩展点不够用」；
2. 优先以**向核心提交扩展点**（新增事件、新增 hook、新增可重写方法）的方式实现，而非写死业务逻辑进核心；
3. 改动需独立 PR、单独评审、双人 review，并在 `docs/` 留存变更记录（改了什么、为什么、影响面、回滚方式）；
4. 核心改动**禁止夹带业务逻辑**，只允许「让框架更可扩展」。

### 1.4 第三方依赖（vendor / node_modules）

- 禁止直接改 `vendor/` 与 `node_modules/` 源码。
- 必须打补丁时：后端用 composer patch 机制、前端用 `patch-package` 等可追溯方式，补丁文件纳入版本管理并写明原因。

## 二、代码业务约束

### 2.1 分层与职责（违反即驳回）

1. **Controller 不写业务逻辑**：只做参数接收、调用 service、返回 `success()/fail()`。
2. **业务逻辑下沉 service**：可复用规则放 `service/core`，管理端/前台分别在 `service/admin`、`service/api` 编排。
3. **Model 不写业务**：仅数据映射与查询作用域。
4. **禁止跨插件直接引用对方的 controller/model**；插件间协作走**事件**或**约定好的 service 接口/契约**（参见 `docs/` 内各对接契约文档）。
5. **禁止在控制器/模型里写 SQL 拼接业务流程**；复杂事务封装在 service 内并使用事务包裹。

### 2.2 多租户 / 数据隔离（红线）

1. **新建业务表必须含 `site_id`**（及 `create_time` 等通用字段），并建 `site_id` 索引。
2. **任何业务查询必须带 `site_id` 过滤**（`where('site_id', $this->site_id)`）。`BaseAdminService` 已注入 `$this->site_id`，直接用，**禁止从前端入参信任 site_id**。
3. 写入数据时 `site_id`、操作人（`uid`/`username`）由服务端注入，**不得采信前端传值**。
4. 跨站点数据串号属于**严重事故**，提交前必须自查。

### 2.3 命名与编码（对齐《二开规范》§七）

1. 命名空间一律 `addon\<key>\app\...`；类名 PascalCase 与文件名一致。
2. 后端文件头统一 `declare(strict_types=1);`。
3. 控制器/服务/模型/验证器/字典/监听/任务 命名后缀遵循规范速查表，不得随意命名。
4. **文案禁止硬编码**：前后端一律走 i18n key（后端 `app/lang`，前端 `addon/<key>/lang|locale`）。
5. 输入校验必须经 `Validate`，错误消息用多语言 key；**禁止裸信任前端入参**。
6. 字典/状态值用 `XxxDict` 常量，**禁止魔法数字**散落在业务代码。

### 2.4 安全与稳定

1. 前台接口鉴权用标准中间件（`ApiChannel` + `ApiCheckToken`），是否强制登录用第二参数控制，**禁止自行绕过鉴权**。
2. 后台接口必须挂 `AdminCheckToken` + `AdminCheckRole` + `AdminLog`。
3. 涉及金额/库存/账务的写操作必须事务化、幂等化（防重复提交、防并发），参考 `docs/` 财务/出入库相关设计。
4. **禁止把密钥、token、第三方凭证硬编码**进代码或提交进仓库；走配置/环境变量。
5. 重操作走队列（`Job`）与计划任务（`schedule.php`），**禁止在请求线程里跑长任务**。

### 2.5 资源与产物

1. 前端构建产物（`dist/`、`public/admin` 等）与 `node_modules/`、`runtime/` 按 `.gitignore` 处理，**禁止提交进仓库**（既有约定为准）。
2. 大文件 / 二进制资源放插件 `resource/`，不混入代码目录。

## 三、版本管理约束

### 3.1 插件版本（info.json + SQL）

1. **每次发布必须升 `info.json` 的 `version`**（语义化版本 SemVer：`主.次.修`）。
   - 修复缺陷 → 修订号；新增向后兼容功能 → 次版本；不兼容变更 → 主版本。
2. **数据库变更必须走增量脚本**：
   - 新增/改表只能新增 `sql/update_<新版本>.sql`，**禁止直接改既有 `install.sql` 历史内容**（`install.sql` 仅代表全新安装的最终态，可同步维护，但不可破坏老版本升级链）。
   - 同步维护 `uninstall.sql`（新表要有对应 DROP）。
   - 表名用 `{{prefix}}` 占位；脚本须可重复执行（`CREATE TABLE IF NOT EXISTS` / 加列前判断）。
3. SQL 与 `version` 必须**同一次提交**一起改，保证「版本号 ↔ 升级脚本」一一对应。
4. `Addon.php` 的 `install/uninstall/upgrade` 必须幂等，可重复执行不报错、不重复写数据。

### 3.2 Git 提交与分支

1. **核心框架与业务插件分开提交**：一次 commit 不得同时改「核心框架」与「业务插件」（便于审计与回滚）。核心改动需走 §1.3 独立 PR。
2. 提交信息遵循现有约定（约定式提交，如 `feat(<插件>): ...`、`fix(<插件>): ...`、`checkpoint(<插件>): ...`），**scope 必须标明所属插件**。
3. 业务开发在功能分支进行，经评审后合并，**禁止直接向主干推送未评审的核心改动**。
4. **禁止提交**：`vendor/`、`node_modules/`、`dist/`、`runtime/`、`install.lock`、本地配置、密钥（以 `.gitignore` 为准，新增忽略项需同步更新）。
5. 合并前确保升级链可用：从上一发布版本按 `update_*.sql` 顺序能平滑升级到当前版本。

### 3.3 兼容与回滚

1. 接口/契约变更（跨插件、对外）必须**向后兼容**或提供过渡期；破坏性变更升主版本并在 `docs/` 公告。
2. 每个发布版本应可回滚：保留卸载/降级路径（至少数据层面有清理脚本与说明）。
3. 涉及多插件联动的改动（如回收 ↔ ERP ↔ 商城），需在对应**对接契约文档**同步更新版本与字段说明。

## 四、提交前自检清单（Checklist）

提交 / 发起合并前，逐项确认：

- [ ] 改动全部落在 `addon/<插件名>/` 业务区，**未触碰核心框架范围**（如触碰，已走 §1.3 例外流程并获批）。
- [ ] 未直接改 `core/`、主工程 `app/`、`config/`、`route/app.php`、各前端构建/聚合/请求/i18n 文件。
- [ ] 扩展能力通过事件 / Loader / 监听 / 继承包装实现，未改核心本体。
- [ ] 新表含 `site_id` 且建索引；所有查询带 `site_id` 过滤；`site_id`/操作人由服务端注入。
- [ ] Controller 无业务逻辑；逻辑在 service；无魔法数字、无硬编码文案、入参经 Validate。
- [ ] 接口挂了正确的鉴权中间件；重任务走队列；金额/库存操作事务+幂等。
- [ ] `info.json` 版本已升；`sql/update_<版本>.sql` 已新增且与版本对应；`uninstall.sql`、`Addon.php` 同步且幂等。
- [ ] commit 未混合「核心 + 业务」；scope 标明插件；未提交 vendor/dist/node_modules/密钥。
- [ ] 升级链验证通过（从上一版可平滑升级）；跨插件契约文档已同步。

## 五、违规处理

- 触碰红线（§1.1、§2.2 数据隔离、§3.1 破坏升级链、提交密钥）→ **直接驳回**，必须整改后重新提交。
- 入侵核心未走例外流程 → 驳回并回退相关 commit。
- 反复违规 → 升级评审强度（强制双人 review）。
