# 走查报告 · ERP 账目「一收一付」（PC 端，移动端改造前置）

> 目的：在把 ERP 搬移动端之前，先从**做账用户**视角把 PC 端业务逻辑捋清楚——PC 有问题，移动端一定也有问题。
> 范围：`hsx_erp` 财务中心（应付/应收/结算/对账/资金账户/成本调整）+ 与回收/销售的联动。
> 结论先行：**数据模型很完整，但缺了会计场景的两块硬骨头——「改不了的收款」和「冲不了的错账」**；另有一处「成本调整双头写」需按单向数据流收口。

---

## 一、一收一付：现状（先给该给的肯定）

ERP 已经把买卖账拆成标准的两笔账 + 一次结算：

| 概念 | 落地 | 说明 |
|------|------|------|
| 付款（应付） | `FinancePayable`（`erp_finance_payable`） | 回收/入库/整备/代卖买断/手工建档/采购预付/经营支出产生「我欠谁」 |
| 收款（应收） | `FinanceReceivable`（`erp_finance_receivable`） | 销售/出库/同行/商城/代卖销售/成本下调返还产生「谁欠我」 |
| 结算折账 | `FinanceSettlement` + `FinanceSettlementLink` | 同一往来对象的应付应收相抵（现金/折账/混合，支持设备级、对象级、跨人折账、预付冲抵） |
| 资金账户 | `ErpCapitalLedger` | 现金进出落到具体账户，余额可查 |

每笔账都带：**往来对象（向谁/收谁）、金额（多少）、source_type+source_no+source_device_id（为什么·可溯源到单到机）、occurred_at、remark、status**。状态机：`pending 待结算 / partial 部分 / settled 已结清 / void 已作废`。

> 一句话：「一收一付」的**记账**是齐的，溯源链（账→单→设备）也在。问题出在**改账**和**纠错**。

---

## 二、对照「一收一付」四问，看缺口

你定的核心四问，逐条对账：

| 维度 | 问题 | 现状 | 判定 |
|------|------|------|------|
| 收款 | 收**谁**的钱 | `counterparty_id/name` | ✅ |
| 收款 | 收**多少** | `amount`、`settled_amount` | ✅ |
| 收款 | **为什么**收 | `source_type`(销售/出库/同行…)+`source_no`+`source_device_id` | ✅ 数据有，UI 在对账/明细可见 |
| 收款 | 能不能**调整** | **无任何应收调整入口** | ❌ **缺**（见 §3.2） |
| 付款 | 向**谁**付 | `counterparty_id/name` | ✅ |
| 付款 | **为什么**付 | `source_type`(入库/整备/买断…)+溯源 | ✅ |
| 付款 | 能不能**调整** | 经成本调整 `sync_payable` 改应付，多付转应收 | ⚠️ 有，但入口绕（藏在「调成本」里，见 §3.3） |

## 三、问题清单（按做账用户视角，优先级排序）

### 3.1 【高】缺「反结算 / 红冲 / 作废」——错账无法纠正

全财务模块（`FinancePayable/Receivable/SettlementService`、`Finance/Reconciliation` 控制器）**搜不到任何** `反结算/红冲/撤销/void/reverse/cancel` 的实现。意味着：

- 结算单一旦确认，**没法反冲**。金额折错、对象选错、把不该结的结了 → 只能在账外想办法，账面错误永久留存。
- 自动生成的应付/应收若来源有误（上游录错），**没有作废/红冲入口**（`status` 里有 `void` 常量，但没有任何地方写它）。

> 会计铁律是「错账不涂改，红冲再重记」。当前只能「记」「结」，不能「冲」，做账闭环缺了一半。**这是搬移动端前最该补的。**

### 3.2 【高】收款（应收）不可调，和付款不对称

`FinanceReceivableService` 只有 `getPage / getOutstanding / prepay`，**没有 adjust**。而付款侧能通过「调成本+sync_payable」间接改应付。结果：

- 卖错价、退补差价、同行结算让价 → **应收金额改不动**，只能靠新开一笔冲（但 §3.1 又没有冲红）。
- 正面回答你的疑问：**「收款能不能调整」目前答案是：不能。** 这是明确缺口。

### 3.3 【中】成本调整双头写，未按单向数据流收口

- ERP 调成本 → 抛 `ErpAssetCostAdjusted` → 回收 `ErpCostAdjustedListener` 自动回填 ✅（单向、自动，正确）。
- 但**回收 PC 自己也能调成本**（`RecycleDevice@costAdjust` + 设备详情弹窗），其 `ability()` 只判断「已打款/未退回」，**完全没探测 ERP 是否在场**；调完还靠文案提示用户「请手动改进销存软件成本」——**手动、易错、与 ERP 各调各的**。
- 目标（按你的单向数据流原则）：**装了 ERP → 回收 `ability()` 返回不可调 + 提示「请到 ERP 调整」；没装 ERP → 回收照旧可调。** 探测手段项目里现成（`class_exists` 模式，ERP 探测数据中台就这么干的）。

### 3.4 【中】「调整」入口语义不直观

应付的调整藏在「调成本」动作里（改库存成本顺带 `sync_payable` 改应付，下调多付的部分自动转应收）。逻辑是对的，但对做账的人来说**「我想改这笔应付」找不到直接入口**，得先理解「改成本会联动应付」这层。建议在应付明细处给出显式的「调整/说明」视图，把「这笔为什么变了」讲清楚。

### 3.5 【低】信息呈现：把「为什么」前置

数据里 source 溯源齐全，但列表卡片主要展示金额+方向（应付/应收）。做账时高频要看「这笔是哪台机器、哪张单、经手谁」。对账页（按设备全链路）做到了，但应付/应收**明细列表**和**结算单**里建议把 `source_no/设备/经手人` 更前置，减少点开钻取。

## 四、给移动端的前置结论

把上面映射到「先改 PC、再上移动端」：

1. **先在 PC 补齐纠错闭环**（§3.1 反结算/红冲、§3.2 应收可调）。这是账目「好用」的地基，移动端只是把它搬到手机；地基缺了，移动端照样缺。
2. **成本调整按单向数据流收口**（§3.3）：回收 `ability()` 增加 ERP 探测 → 有 ERP 则禁用并提示去 ERP。移动端我已建的 ERP 成本调整页正是「单一写入口」的落点，回收侧（PC+移动）同步改只读。
3. **入口与信息呈现**（§3.4/3.5）顺带在移动端重做时一并优化——移动端屏幕小，更要求「为什么收/付、能否调」一眼看清。

> 优先级：§3.1 ≈ §3.2 ＞ §3.3 ＞ §3.4 ＞ §3.5。建议移动端改造**等 §3.1/§3.2 在 PC 落地后再大规模铺**，否则会把「改不了/冲不了」的体验原样搬到手机。
