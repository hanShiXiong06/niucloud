# 设计说明 · 商城多站代理铺货与联动

> 版本日期：2026-06-27 ｜ 插件：`phone_shop`（二手商城）
> 目标：恢复并重做老版本的「主站建品 → 子站代理铺货 → 跨站上下架联动」能力，**用干净分层架构替换老版本的屎山实现**。

---

## 1. 背景与目标

老版本有一套「站点代理 + 商品代理 + 跨站上下架同步」的能力，但实现混乱（`site.client` + `phone_shop_site_agent` + `phone_shop_goods_proxy` 三件套 + 散落在 GoodsService 各处的同步调用），因架构太烂被放弃。子站的代理商品当时靠 **Excel 手动导入**（导入时携带 `goods_no`、`source`）。

新版本的现实变化：

- 商品**不再通过 Excel 导入**进商城，全部由 **ERP 入库**生成（尤其主站 `100005`，不存在商城自建商品）。
- 主站 `100005` 是给其他商户开的展示型商城，只有基础上架/展示功能。
- 二手机**一物一码**：同一台真机可铺到多个子站展示，谁先卖谁锁定，其余必须立刻联动下架。

**本次目标**：

1. 主站 `100005` 通过 ERP 建品并上架时，自动把商品**铺货**到订阅它的子站（生成 `goods_no` 相同、`source=100005` 的子站副本）。
2. 主站商品**上架/下架/卖出锁定/退款回库**时，按 `goods_no` **联动**所有子站副本同步状态。
3. 子站代理价 = 主站零售价 + **子站自定义固定加价**（默认 0）。
4. 升级时**字段平滑保持**，老数据不丢、不报错。

## 2. 核心概念与字段语义

| 概念 | 载体 | 说明 |
|---|---|---|
| 站点隔离 | `goods.site_id` 及所有引用表的 `site_id` | 每个站一份数据，沿用框架既有机制，**不打破**。 |
| **来源站** | `goods.source`（**复用现有列，改语义**） | 这条商品来自哪个站。`100005` = 代理主站的货；空 / 本站 id = 自营。 |
| **商品联动键** | `goods.goods_no` | 同一款（同一台真机）跨站共享同一个 `goods_no`，当前列已存在（休眠保留），直接复用。 |
| **引用数据联动键** | `*_no`（新增）：`category_no` / `brand_no` / `memory_no` / `attr_no` | 分类、品牌、内存规格、商品参数的**跨站公共业务键**，与 `goods_no` 同构。跨站关联只认 `*_no`，**绝不跨站共用主键 id**。 |
| 代理订阅关系 + 加价 + 分类订阅 | **新表 `phone_shop_agent`** | 子站订阅主站 + 子站固定加价值 + 是否订阅主站引用数据同步。**替代老的两张表。** |

### 2.1 `source` 语义切换（关键）

- 老语义：来源站点 ID（如 `100005`）。
- 当前语义：`erp`/`manual`（区分商城自建 vs ERP）——**已无意义**，因为新版全部来自 ERP。
- **新语义 = 来源站点 ID**，默认 `''`。
- 安全性已核查：全插件**只有 `DeviceIntakeService:331` 一处写** `source='erp'`，且**没有任何代码读 `source=='erp'/'manual'` 做判断**（其余 `source` 都是 DIY 组件配置 / 订单参数，与 goods 表此列无关）。因此改语义安全，只需改这一处写入。
- 顺带复活了老的「是否代理」语义：以后 `source==100005 ⇒ 代理`，`source!=100005 ⇒ 自营`，原 `is_proxy`（已作废休眠）可彻底退役。

### 2.2 自营 vs 代理判定

```
source == 100005  → 代理商品（代销主站的货，受主站联动）
source == 本站id / 空 → 自营商品（本站 ERP 自入，不受主站联动）
```

ERP 入库写值规则：`DeviceIntakeService` 建品时写 `source = $this->site_id`（自己站）。于是主站 `100005` 入的货 `source=100005`，天然满足「主站货可铺、可联动」；子站自入的货 `source=子站id`，不会误触发主站联动。子站的**代理副本**由铺货服务写 `source=100005`。

### 2.3 引用数据跨站模型（分类/品牌/内存/参数）—— `*_no` 公共键

商品引用的**分类 `goods_category`、品牌 `brand_id`、内存规格 `memory_group`、商品参数 `attr_ids`** 对应的表全部带 `site_id`、**按站隔离**，且 goods 表里存的是这些引用的**主键 id**。所以主站一条货直接复制到子站，它携带的全是**主站命名空间里的 id**，在子站会指向不存在或错误的记录 —— 铺货必须先把引用数据对齐。

**采用与 `goods_no` 完全同构的方案**：给每类引用表加一个跨站公共业务键 `*_no`，跨站只认 `*_no`，**不跨站共用主键 id**。

```
分类：phone_shop_goods_category + category_no
品牌：phone_shop_goods_brand    + brand_no
内存：phone_shop_memory_group   + memory_no（memory_spec 同理可加 spec_no，按需）
参数：phone_shop_goods_attr     + attr_no
```

- 每个站仍 `site_id` 物理隔离、各存各的记录（各有各的主键 id），**双方互不影响**。
- 「A 站的 iPhone15 分类」与「B 站的 iPhone15 分类」通过**相同的 `category_no`** 关联，而不是相同的 `category_id`。
- goods 副本入子站时，引用字段存的是**子站自己的主键 id**（由 `*_no` 翻译得到），子站所有现有查询照旧按 `site_id` 跑，**零改动**。

**为什么这版优于其它思路**：

| 思路 | 问题 |
|---|---|
| 跨站直接引用 A 的 id | 打破 `site_id` 隔离，所有分类查询要改 `site_id IN (0,本站)`，外溢成屎山。 |
| 全部分类塞 0 号站做全局池 | 同上，放弃隔离。 |
| 单独建 主站id↔子站id 映射表 | 多一张表、按名字匹配易错。 |
| **`*_no` 公共键（采用）** | 隔离不动、无需映射表、按编号精确关联、与商品方案同构、互不影响。 |

> 「依附/独立硬开关」（开启即失效、关闭即丢分类）**不再需要**：有了 `*_no` + 站内隔离副本，主站同步来的分类与子站自建分类天然共存、互不顶掉。该开关降级为 `phone_shop_agent.subscribe_category`（是否订阅主站引用数据同步）的**软偏好**，数据永不冲突、永不丢失。

## 3. 反屎山架构原则

老实现的病根：同步逻辑散落在 GoodsService、Order 链路、Listener 各处，互相调用，关系判断与价格计算耦合在一起。本次按以下原则重做：

1. **单一职责的四个服务**，互不内联：
   - `AgentRelationService` —— 只管「谁代理谁 + 加价 + 是否订阅引用数据」关系的增删改查。
   - `RefDataSyncService` —— 只管「主站引用数据（分类/品牌/内存/参数）→ 子站副本」的按 `*_no` 同步。
   - `GoodsDistributionService` —— 只管「主站商品 → 子站副本」的铺货（创建/更新副本，引用字段经 `*_no` 翻译）。
   - `GoodsSyncService` —— 只管「按 goods_no 联动状态」（上架/下架）。
2. **事件驱动解耦**：上下架、卖出、退款等触发点**只发事件**，由监听器调用上面的服务；业务主流程不直接 `new XxxService()` 串调。沿用本仓既有的 `event()` + listener 约定。
3. **关系与价格归一张表**：不再有 per-goods 的 `goods_proxy`。加价是「子站对主站」的一个固定策略，存在 `phone_shop_agent` 上即可。
4. **幂等**：铺货/联动可重复执行不产生脏数据（副本按 `site_id+goods_no` upsert；联动只改「当前状态不一致」的记录）。
5. **失败不阻断主流程**：同步/铺货异常只记日志，不让主站上架失败。

## 4. 数据模型

### 4.1 新表 `phone_shop_agent`（代理订阅关系 + 加价）

```sql
CREATE TABLE `{{prefix}}phone_shop_agent` (
  `id`            int unsigned NOT NULL AUTO_INCREMENT,
  `master_site_id` int NOT NULL DEFAULT 0 COMMENT '主站id(被代理方,如100005)',
  `agent_site_id`  int NOT NULL DEFAULT 0 COMMENT '子站id(代理方,接收铺货)',
  `markup_value`   decimal(10,2) NOT NULL DEFAULT 0.00 COMMENT '子站固定加价(零售价上叠加,默认0)',
  `subscribe_category` tinyint NOT NULL DEFAULT 1 COMMENT '是否订阅主站引用数据(分类/品牌/内存/参数)同步 1是0否',
  `status`         tinyint NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  `create_time`    int NOT NULL DEFAULT 0,
  `update_time`    int NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uniq_master_agent` (`master_site_id`,`agent_site_id`),
  KEY `idx_agent` (`agent_site_id`)
) COMMENT='商城站点代理订阅关系';
```

- 一行 = 「子站 `agent_site_id` 代理主站 `master_site_id`，加价 `markup_value`」。
- 铺货目标 = `master_site_id=100005 AND status=1` 的所有 `agent_site_id`。
- 加价由**子站自己设置**（子站后台编辑自己那行的 `markup_value`）。

### 4.2 `phone_shop_goods` 既有列复用（无需新增）

- `source varchar(30)` —— 改语义为来源站 ID（见 2.1），install.sql 仅改注释。
- `goods_no int` —— 复用，铺货时主站与子站副本写同值。
- `sale_status`（available/locked/sold）—— 复用，承接「卖出锁定」联动。

### 4.3 引用表新增 `*_no` 公共键（4 张表，各加一列）

| 表 | 新增列 | 说明 |
|---|---|---|
| `phone_shop_goods_category` | `category_no int` + `KEY(site_id,category_no)` | 跨站分类公共键 |
| `phone_shop_goods_brand` | `brand_no int` + `KEY(site_id,brand_no)` | 跨站品牌公共键 |
| `phone_shop_memory_group` | `memory_no int` + `KEY(site_id,memory_no)` | 跨站内存分组公共键（`memory_spec` 按需加 `spec_no`） |
| `phone_shop_goods_attr` | `attr_no int` + `KEY(site_id,attr_no)` | 跨站参数公共键 |

- `*_no` 生成口径与 `goods_no` 一致（如 `maxId+10001` 或主站统一发号），主站建记录时生成，子站副本沿用主站的值。
- 子站自建记录生成各自的 `*_no`，与主站不冲突（不同 no 即不同物）。
- 同步标记：建议各引用表再加 `source_site_id int DEFAULT 0`（0=本站自建，非0=从该主站同步而来），便于「主站同步来的只读、子站自建可改」的区分。

### 4.3 升级与数据迁移

- 新表 `phone_shop_agent`：进 `install.sql` 的 `CREATE TABLE IF NOT EXISTS`，老库升级时由框架 + `SchemaSyncService` 自动建。
- `source` / `goods_no`：已是既有列，无需 ALTER；`SchemaSyncService`（解析 install.sql 幂等补列）已覆盖。
- 老 Excel 导入的子站数据：其 `goods_no`、`source` 已落库，新逻辑直接复用这些值，**不需要迁移脚本**。
- **唯一代码改动写入点**：`DeviceIntakeService:331` `'source'=>'erp'` → `'source'=>$this->site_id`。

## 5. 关键流程

### 5.0 引用数据同步（主站 → 子站，单向）

```
触发一：主站(100005)创建/改名 分类/品牌/内存/参数
  → event('phone_shop_refdata_changed', {type, master_site_id, *_no, payload})
      └─ 监听器：取该主站 status=1 且 subscribe_category=1 的子站
            └─ RefDataSyncService.sync：逐子站按 (site_id, *_no) upsert 同名副本
               (source_site_id=主站；层级 parent 也按 *_no 解析对齐)

触发二：新建代理关系(子站订阅主站)
  → 一次性全量补同步主站现有 分类/品牌/内存/参数 到该子站

规则：单向。子站自建的引用数据只留本站，不回流主站。
```

### 5.1 建品上架 → 铺货（主站 100005）

```
主站 ERP 建品(DeviceIntakeService) → 生成 goods_no、source=100005
  → 商品上架(status=1)
  → event('phone_shop_goods_listed', {goods_id, site_id, goods_no})
      └─ 监听器：若 site_id==100005 → GoodsDistributionService.distribute(goods_id)
            └─ 取 phone_shop_agent 中该主站 status=1 的子站列表
            └─ 逐子站 upsert 副本：同 goods_no、source=100005、
               引用字段经 *_no 翻译为子站自己的 id
                 (分类/品牌/内存/参数：按 *_no 找子站记录；
                  因 5.0 已预同步，正常都能命中；兜底缺失则即时补建)
               售价 = 主站零售价 + 该子站 markup_value、sale_status 跟随主站
```

幂等：子站副本以 `(agent_site_id, goods_no)` 唯一定位，存在则更新，不存在则创建。

### 5.2 上架/下架联动

```
主站 100005 商品 上架/下架
  → event('phone_shop_goods_status_changed', {goods_no, site_id, status})
      └─ 监听器：仅当 site_id==100005 → GoodsSyncService.sync(goods_no, status)
            └─ 找其它站同 goods_no 且状态不一致的副本 → 批量改为同状态
```

> 来自老 `CoreGoodsSyncService` 的 `syncGoodsOnline/Offline`，逻辑保留、改为事件触发、收敛为一个 `sync(goods_no, status)`。

### 5.3 卖出锁定 / 终态联动（一物一码）

```
某站售出该真机(下单锁定 locked / 支付完成 sold)
  → 主站对应 goods 下架并锁定
  → 复用 5.2 联动：其余子站副本立即下架(status=0)，避免超卖
```

> 触发点对齐老 `CoreOrderCreateTrait`、`AfterShopOrderClose`：下单/关单时发同步事件，避免同一台机被两个站重复卖出。

### 5.4 退款 / 回库 → 回上架

```
订单退款/取消，真机回库可售
  → 主站 goods 回到 available 并上架
  → 复用 5.2 联动：子站副本回到上架
```

## 6. 价格规则

- 子站代理售价 = **主站零售价（主站 goods 的销售价）+ 子站 `markup_value`**。
- 子站**不涉及**同行价、成本价、多级会员价 —— 这些是主站内部口径，子站只对用户呈现一个零售展示价。
- `markup_value` 默认 0（同价），子站可在自己后台设为 +100 / +200 等固定值。
- 主站调价时，可在铺货/联动事件里顺带刷新子站副本售价（按各子站 markup 重算）。

## 7. 与老实现的差异（为什么不会再屎山）

| 维度 | 老版本（屎山） | 本次（重做） |
|---|---|---|
| 关系表 | `site.client` + `phone_shop_site_agent` + `phone_shop_goods_proxy` 三张 | 单表 `phone_shop_agent` |
| 加价 | per-goods 的 `goods_proxy.markup_type/value`（固定/百分比） | per-子站一个固定 `markup_value` |
| 同步调用 | 散落在 GoodsService/Order/Listener 直接 `new` 串调 | 统一 `event()` → 监听器 → 单一职责服务 |
| 价格耦合 | 关系判断与价格计算混在一起 | 关系 / 铺货 / 联动三服务分离 |
| 字段 | 新增 `is_proxy` 等冗余列 | 复用 `source`/`goods_no`，仅引用表加 `*_no` 公共键 |
| 跨站分类 | 开关「关闭即失效/丢分类」或全塞 0 号站 | `*_no` 公共键 + 站内隔离副本 + 单向同步，互不影响、不丢数据 |

## 8. 范围边界与待确认

**本次包含**：`source` 语义切换（含 1 处写入改动）、`phone_shop_agent` 表与关系/加价/订阅后台、4 张引用表新增 `*_no` 公共键、`RefDataSyncService` 引用数据单向同步（创建即同步 + 改动同步 + 新订阅全量补同步）、`GoodsDistributionService` 铺货（引用字段经 `*_no` 翻译）、`GoodsSyncService` 联动（上下架 + 卖出锁定 + 退款回上架）、事件与监听器接线、install.sql 与升级兼容。

**已拍板的设计决定**：

- 铺货目标 = `phone_shop_agent` 订阅关系（轻量单表，替代老三件套）。
- 子站价 = 主站零售价 + 子站固定 `markup_value`（默认 0）。
- 引用数据用 `*_no` 公共键、站内隔离副本、主站→子站单向同步；硬开关降级为 `subscribe_category` 软订阅。
- `source` 复用改语义为来源站 ID（只改 `DeviceIntakeService` 1 处写入）。

**仍待你确认的点**：

1. 主站 ID 固定为 `100005` 写常量，还是做成可配置（`MASTER_SITE_ID` 配置项）？建议配置化，避免硬编码。
2. 子站后台是否需要「我代理的主站 + 设置加价 + 订阅开关」管理页？还是关系先由后台/SQL 维护。
3. 主站调价 / 改名时实时重刷所有子站副本售价与展示？（建议要，否则子站数据会过期。）
4. 一物一码下子站副本 SKU 共享同一台真机、库存恒为 1，靠 `goods_no` 联动锁定即可——确认无需子站独立库存。
5. `*_no` 发号方式：各站本地 `maxId+10001`，还是由主站统一发号池？（建议主站统一发号，跨站绝不撞号。）
