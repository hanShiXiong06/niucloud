# 往来对象（counterparty）检索 —— 通用方案与坑位记录

> 适用范围：ERP 里所有"按往来对象搜索"的列表（应收/应付明细、结算记录、往来汇总，以及未来任何带 `counterparty_id` 的业务）。
> 这是全业务高频复用点，新做任何"按往来户搜索"的功能，先读本文。

---

## 一、问题本质（为什么"搜不出来"）

财务等业务表里，**只存了 `counterparty_id` + 一个姓名快照 `counterparty_name`**，并没有存对接人的 username / nickname / 手机号，也没有存所属"主体"的名字。

```
erp_finance_payable / erp_finance_receivable:
  counterparty_id    int     -- 注意：这里的值 = 对接人 member_id（不是主体id）
  counterparty_name  varchar -- 仅一个姓名快照（通常是 nickname 或 name）
  ...无 mobile / username / 主体名 / 主体id
```

所以如果检索只对 `counterparty_name` 做 LIKE：

- 搜**主体名** → 搜不到（记录上没有主体名，只有对接人名）
- 搜**手机号 / username / member_no** → 搜不到（记录上没有这些）
- 只有恰好等于那条姓名快照的关键词才偶尔命中

这就是"往来单位检索不好用"的根因。**记录是快照、可搜索属性在别的表**，是典型的"反范式快照 + 需反查"问题。

## 二、数据模型（三张表的关系，务必记牢）

```
会员 Member (member_id, username, nickname, mobile, member_no, ...)
   │  1
   │  多
ErpCounterpartyMember (member_id ↔ counterparty_id, status)   ← 对接人 ↔ 主体 的关联
   │  多
   │  1
主体 ErpCounterparty (id, name, mobile, contact_name, counterparty_no, ...)   ← "往来单位/主体"

财务表 finance_*.counterparty_id  ==  Member.member_id   ← 关键：财务的 counterparty_id 是"对接人(会员)"级
结算表 settlement.counterparty_id ==  member_id 或 主体id（主体级跨人折账时存主体id）
```

口径要点：
- **财务明细（应收/应付）的 `counterparty_id` 是对接人 member_id**，不是主体 id。
- **一个主体下可能挂多个对接人**；按主体搜要展开成该主体所有 member_id。
- 结算表的 `counterparty_id` 可能是主体 id（主体级折账），检索时要兼容。

## 三、通用解法（已落地）

**先把关键词反解析成一批 `counterparty_id`，再让查询匹配"这批 id 或 姓名快照/单号 LIKE"。** 全程 DB 查询，分页正确。

### 复用方法（已写好，直接调）

`FinanceCounterpartyBalanceService::counterpartyIdsByKeyword(int $siteId, string $keyword): array`

```php
// 关键词 → member_id[]：
// 1) 会员表 LIKE username|nickname|mobile|member_no
// 2) 主体表 LIKE name|mobile|contact_name|counterparty_no → 取该主体下全部对接人 member_id
// 返回去重后的 member_id 列表
```

### 在列表 getPage 里这样用

```php
if (!empty($where['keyword'])) {
    $kw = trim((string)$where['keyword']);
    $cpIds = FinanceCounterpartyBalanceService::counterpartyIdsByKeyword($this->site_id, $kw);
    $query->where(function ($q) use ($kw, $cpIds) {
        $q->whereLike('counterparty_name', '%' . $kw . '%')   // 姓名快照
          ->whereOr('source_no', 'like', '%' . $kw . '%');    // 单号
        if (!empty($cpIds)) {
            $q->whereOr('counterparty_id', 'in', $cpIds);     // 反解析出的对接人
        }
    });
}
```

**已应用：** 应付明细 `FinancePayableService::getPage`、应收明细 `FinanceReceivableService::getPage`、结算记录 `FinanceSettlementService::getPage`。

## 四、关键陷阱（别再踩）

1. **id 空间会撞号**：`Member.member_id` 与 `ErpCounterparty.id` 是两套自增，数值会重叠。
   - 财务明细 `counterparty_id` 是 member_id → 反解析**只能给 member_id**，不能把主体 id 混进去 in 查询（会误命中同号会员）。
   - `counterpartyIdsByKeyword` 已经只返回 member_id（主体只用来展开成其下 member_id），放心用。
   - 结算表若需按主体 id 命中，单独处理，别和 member_id 混在一个 in 里。

2. **必须保留姓名快照 LIKE**：历史记录的 `counterparty_name` 是当时快照，会员后来改名也不影响，所以 `counterparty_name LIKE` 要和 id 反解析**并存**（whereOr），不能只靠 id。

3. **空结果语义**：如果业务要求"按某条件必须过滤"（如经手人筛选），反解析为空时要 `where('id','=',-1)` 强制空；但**关键词检索**不同——关键词反解析为空时仍要让 `counterparty_name/source_no` LIKE 生效，所以是 `whereOr` 形式（见上）。

4. **聚合视图（往来汇总）是另一套**：往来汇总 `getBoard` 是聚合后在前端做 client 端搜索，已实现"深度匹配"(命中行或其下任意对接人)。它的行里带了 `counterparty_name`(对接人名) + `counterparty_mobile`(已 resolve)，但**没有 username**。若要让汇总也支持 username 搜索，需在 getBoard 阶段把会员可搜字段带出来，或改成走后端检索。

## 五、其它可能需要同款处理的地方（自查清单）

凡是"列表里有 `counterparty_id` 且要按往来对象搜"的，都要用本方案：

- [x] 应收明细 / 应付明细 检索
- [x] 结算记录 检索
- [x] 往来汇总（前端深度匹配，口径略不同）
- [ ] AI 工具 `search_counterparty`（已用 memberOptions，本质同理，口径 OK）
- [ ] 资金账户流水 / 账目往来（如需按往来对象搜）
- [ ] 出库单 / 入库单列表（如需按买家/卖家搜）—— 同样只存 counterparty_id 快照时套用
- [ ] 任何新增的"按客户/供应商/对接人搜索"功能

> 经验法则：**看到列表里要搜的对象，其可搜索属性不在本表 → 先反解析成 id 集合，再 `id IN (...) OR 本表快照 LIKE`。** 别直接对快照单字段 LIKE。

## 六、相关经手人检索（同类反查，附记）

经手人也不在财务表上，用的是同样的"反查"思路：
`FinanceCounterpartyBalanceService::deviceIdsByOperator()` —— 经手人 → 操作过的设备 → 过滤这些设备的财务记录。
区别：经手人是"必须过滤"语义，反查为空时强制空结果（`where('id','=',-1)`）。
