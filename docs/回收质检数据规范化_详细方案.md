# 回收质检数据规范化 · 详细解决方案

> 目标:质检模板字段做到「**存 ID、显 label、两者都留**」;数值类(电池健康度)存真实数值;input 类(保修)存文本。核心基本信息(内存/颜色)在质检面板顶部必须渲染出正确文字。
> 约束:开发阶段,**所有修复必须是代码/可重导的数据驱动**,线上更新后能复现出与 dev 完全一致的效果——不接受"只在 dev 库手改一次"的补丁。

---

## 一、现象

质检面板顶部「设备摘要」显示:

| 字段 | 现在显示 | 期望显示 | 性质 |
|---|---|---|---|
| 内存(capacity) | `7` | 真实容量文字(如 `512GB`) | 选项类,显示了 ID |
| 颜色(color) | `1` | 真实颜色文字(如 `深空灰`) | 选项类,显示了 ID |
| 系统版本(system_version) | `—` | 文本或空 | input 类,基本正常 |
| 保修(warranty_info) | `过保` | `过保` | **应为 input** |
| 电池健康度(battery) | `1` | 真实健康度(如 `100`) | **应为数值** |

---

## 二、字段分类与各自根因(逐字段 · file:line)

前缀:前端 `admin/src/addon/hsx_recycle/views/recycle_order/components/`;导入器 `niucloud/addon/hsx_recycle/app/service/admin/check/RecycleCheckCatalogService.php`。

### 类型 A:选项类自定义字段(如 f2 购买渠道)—— 已正确,作为基线
- 渲染:`CheckTemplateSchemaPanel.vue:90-99` el-select `:value="String(option.value)"` → 选中存**选项 value(ID)**。
- 拼 result_items:`useCheckMeta.ts:346-353` 自定义字段走 `optionLabels(field.options, value)` 查表得 label。
- 结果:`value="1"(ID) / labels=["大陆国行"](文字) / option_items=[{value:"1",label:"大陆国行"}]`。**规范,作为全局基线。**

### 类型 B:保留显示字段(capacity / color / system_version)—— 核心 BUG
两处断点:

1. **result_items 不查表**:`useCheckMeta.ts:324-327`
   ```ts
   ['capacity','color','system_version','warranty_info'].forEach((fieldKey) => {
     const value = deviceForm[fieldKey]
     if (!isEmptyValue(value)) appendItem(fieldKey, value, [toStringValue(value)], '')  // labels 硬塞 [String(value)]
   })
   ```
   对比类型 A 的 350 行(`optionLabels` 查表),这里**直接把 value 当 label**,所以 result_items 里 capacity 的 labels=["7"]。

2. **顶部摘要值与选项不同源**:`CheckDeviceDialog.vue:406-423`
   - `formatSummaryFieldValue` **本身会查表**(`labelMap.get(String(value))`)——逻辑是对的;
   - 但 `getTemplateFieldValue(capacity)` 取的是 `deviceForm.capacity`(=`"7"`,来自 `props.device.info.capacity`,见 `:485-486`,疑似拍机堂查询 API 属性码),
   - 而 `getTemplateFieldOptions(capacity)` 取的是**质检模板**该字段的选项;两者 value 编码**不是同一套** → `labelMap.get("7")` 命中不了 → 回退 `String(value)` = `7`。

   **根因:capacity/color 存的"7/1"与模板选项 value 处于两套命名空间**(外部 API 码 vs 模板选项序号)。这是顶部显示 ID 的真正原因,也是"挺复杂"之处。

> ⚠️ 需用真实数据核对一处:`device.info.capacity`/`color` 的"7""1"到底来自(a)质检时在模板里选的选项 value,还是(b)拍机堂查询 API 回填的属性码。决定下面方案选 B-1 还是 B-2。

### 类型 C:input 类(warranty_info 保修)—— 类型基本对,口径待统一
- 导入器已把保修建成 input:`RecycleCheckCatalogService.php:180-187`(`component='input'`、`result_template='保修: {value}'`)。
- input 无选项,value=文本"过保"本就合理;它在 result_items 里 labels=["过保"] 是正常的(没有 ID 可存)。
- 唯一要做的:确认所有保修类检测项都落到 input(目录里"国内保修情况/保修期时长"等仍是 radio 检测项,见 §四 CSV)。

### 类型 D:电池健康度(battery)—— 两个叠加 BUG,显示 1
1. **键名碰撞**:`mapFieldKey()` `:241` 规则 `'battery'=>['电池']`——名字含"电池"的检测项**都**抢 `battery` 保留键。目录里"电池"开头的检测项有:`电池健康度(5602)`、`电池维修、更换状况(5330)`、`电池情况(4871)`、`电池维修情况(2179)`、`电池循环次数(71)`…谁先出现谁占 `battery`。本单是"电池维修、更换状况"抢到了,真正的"电池健康度"被挤到 `f33`。
2. **数值字段被 radio 化**:导入器 `:158` 把所有检测项一律 `component='radio'`、`:168` 选项值按序号 `1,2,3…`。于是占了 `battery` 键的那个 radio 选中第 1 项 → `battery=1` → `电池健康度{value}%` 渲染成"1%"。
- 即便修好碰撞让"电池健康度"占 `battery`,它仍是 radio(选项是"90%≤…≤100%"**区间**),存的还是序号,打印 `{battery}` 还是序号。**要显示真实 100,电池健康度必须建成 `number`**(数值录入 / 查电池 API 回填),即默认模板的做法(`RecycleCheckTemplateService.php:605` battery=number)。

## 三、设计原则(规范基线)

**职责归属(本方案的核心约定):合并/解析全部放后端,前端不介入。**
- 前端质检面板:只负责**采集原始选择**,提交时只交 `custom_fields = {field_key: 选项value(ID) / 数值 / 文本}` 这一份原始数据;**不再在前端拼 result_items、不在前端查 label**。
- 后端:握着模板字段表 `recycle_check_field` + 选项表 `recycle_check_option`,由**唯一解析器** join 出完整、可直接渲染的结果(见 §四 Layer 3),并**落库为权威快照**。
- 前端拿到后端返回的 result_items / 解析后的基本信息,**只做渲染**。打印/ERP/商城同样读后端快照,不自行解析。

| 组件类型 | custom_fields 存什么 | 后端解析产出的 result_items | 渲染(前端/打印/ERP) |
|---|---|---|---|
| radio / checkbox / select(选项类) | 选项 **value(ID)** | `value=ID`、`labels=查表文字`、`option_items=[{value:ID,label:文字}]`、`text=按result_template` | 直接取 labels/text |
| number(电池健康度/循环/快门) | **真实数值** | `value=数值`、无 option_items、`text='电池健康度{value}%'` | 直接取 text |
| input / textarea(保修/系统版本) | **文本** | `value=文本`、无 option_items | 直接取 value |

要点:**存 ID(在 custom_fields)、显 label(后端解析进 result_items)、两者都留**;解析与合并是**后端**的事,前端零参与。

## 四、解决方案(分层 · 全部代码/可重导,dev=prod)

### Layer 1 — CSV 源头打标(脚本,流式处理 75MB)
给 `docs/拍机堂检测目录.csv` 加第 7 列 `组件类型`:
- 默认 `radio`;
- 数值类标 `number`:`电池健康度`、`电池循环次数`、`快门次数`、`电池数量`、`电池管家情况`(数值/次数语义的);
- input 类标 `input`:保修语义的检测项(`国内保修情况`/`保修期时长`/`苹果保修期时长`/`保修情况`…)——若你希望保修只用导入器那个统一 input 字段,则这些直接**不导入**,二选一(§六待你定)。
- 脚本只读写 CSV,不碰库;产出新 CSV 供重新导入。

### Layer 2 — 导入器(`RecycleCheckCatalogService.php`)
1. `:106-112` 解析时读 `$r[6]` → `$it['component']`(空=radio,兼容旧 CSV)。
2. `:158` `component` 用 `$it['component']`,不再写死 radio。
3. `:163-172` 仅当 component 为选项类(radio/checkbox/select)才建选项;number/input 不建序号选项。
4. `:241` `mapFieldKey` 把 `'battery'=>['电池']` 收紧为 `'battery'=>['电池健康度','电池健康']`,让"维修/情况/循环"不抢 `battery` 键(它们正常走 `f{N}`)。
5. 电池健康度命中 `battery` 键 + component=number → 落成数值字段(配 `result_template='电池健康度{value}%'`、可 API 回填)。

### Layer 3 — 后端唯一解析器(本方案重心,前端零参与)
新增一个后端服务方法,例如 `RecycleCheckResolveService::resolve(int $checkTemplateId, array $customFields, array $deviceBasic): array`,职责:
1. 一次性载入该模板的字段(`recycle_check_field`)+ 选项(`recycle_check_option`),建 `field_key → {component, field_name, result_template, unit, options[{value,label}]}` 映射。
2. 遍历 `custom_fields`,按 component 产出每项 result_item:
   - 选项类:`value=ID`、`labels=选项表查得文字`、`option_items=[{value,label}]`、`text=渲染 result_template`;
   - number:`value=数值`、`text='电池健康度{value}%'` 等;
   - input/textarea:`value=文本`。
3. 同时产出**解析后的基本信息**(capacity/color/system_version/battery/warranty 的显示文字),供顶部摘要与打印直接用。
4. **调用时机**:
   - **保存时(`admin/order/RecycleDeviceService.php::completeCheck`)**:用本解析器从 `custom_fields` 重建 `result_items` 并落库——**不再信任前端传来的 result_items**;同时生成 `check_result`/`check_result_seller` 文本。
   - 读取时(`api/recycle_order/RecycleOrderService.php::fillInspectionReportMeta` 及管理端详情)收敛为调用同一解析器,避免两套口径。
   - 把现有 `useCheckMeta.ts` 的 `buildResultItem/buildOptionItems/optionLabels` 逻辑**迁移到 PHP**,作为唯一实现。

### Layer 4 — 前端只采集 + 只渲染(精简,不再合并)
- 提交:质检面板只发 `custom_fields`(及图片/备注等),**删除**前端拼 `check_meta.result_items` 的逻辑(`useCheckMeta.ts:311-356 buildResultItems` 不再用于产出存库结构)。
- 渲染:顶部摘要 `CheckDeviceDialog.vue:formatSummaryFieldValue` 改为**直接取后端解析后的显示文字**(后端返回 basic 显示字段),不再前端 `labelMap` 查表。result 列表直接渲染后端 result_items 的 `labels/text`。
- 命名空间问题(capacity/color 的"7/1")也随之收敛到后端解决:后端解析器统一以"模板选项 value"为准;若来源是外部 API 码,则在**后端**做一次码→模板value 的映射(§六核对点),前端无感。

### Layer 5 — 下游消费者(打印 / ERP / 商城)
- 因 Layer 3 已在保存时落库为权威 result_items + 解析文本,下游**直接读快照文字**即可,无需自带模板上下文、不再解析 ID。
- 具体落点:`RecyclePrinterTemplateService`({capacity}/{color}/{battery} 取解析后文字)、ERP 同步设备快照处。

### Layer 6 — 存量纠正(可复现)
- 用**改后的导入器 + 加列后的 CSV 重新导入**:`importChunk` 在 `offset===0` 会 `clearImported()` 先清后建(`:55-57`),dev/prod 同操作 → 同结果。
- 历史已质检的测试设备 result_items 是快照,dev 阶段重质检覆盖即可;如需批量拉齐,做一个**幂等的"按当前模板重算 check_meta"动作**(同一代码 dev/prod 一致),不写 dev-only SQL。

## 五、dev = prod 可复现保证
- Layer 1 的 CSV 进版本库;Layer 2-5 是代码;Layer 6 用现成的"上传目录→重新导入"流程。
