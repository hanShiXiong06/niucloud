# niucloud-admin 研发流程规范

> 三件套之一：《二开规范_开发文档》讲**怎么写代码**，《二开约束》讲**禁止做什么**，本文讲**怎么协作交付**——从开发、提交、版本、测试到验收、发布的全流程。
> 定位：团队强制流程规约。本文约定的节点与产物为合并/发布的前置条件。
> 适用范围：`niucloud`(后端)、`admin`、`web`、`uni-app`、`site-uniapp` 全部工程。

---

## 〇、总览：一次需求的生命周期

```
需求/任务  →  分支  →  开发(自测)  →  提交(commit)  →  联调  →  发起合并(PR/MR)
   →  代码评审(Review)  →  测试  →  验收(UAT)  →  版本封板  →  发布/安装升级  →  回归
```

每个阶段都有「**进入条件**」和「**完成产物**」，不满足不得进入下一阶段。核心原则：**小步提交、随时可回滚、版本与脚本一一对应、改动只落 addon**（详见《二开约束》）。

---

## 一、开发阶段

### 1.1 开始前（进入条件）

- 需求/任务已明确：知道改哪个插件、是否涉及跨插件契约（回收 ↔ ERP ↔ 商城）、是否动数据库。
- 涉及跨插件或对外接口的，**先对齐契约**（更新/确认 `docs/` 内对接契约文档），再动手。
- 涉及数据库的，**先设计表结构**（含 `site_id`、索引、字段注释），评审通过再写代码。

### 1.2 开发中（怎么开发）

1. **业务一律落 `addon/<插件名>/`**，禁止入侵核心框架（见《二开约束》§一）。
2. 按分层写：Controller 接参 → Service 编排（核心逻辑放 `service/core`）→ Model 取数；状态值用 `XxxDict` 常量，文案走 i18n。
3. **边写边自测**：后端可写最小验证脚本 / 用接口工具打通；前端 `pnpm dev` 实时验证。
4. **数据库变更同步写脚本**：新增 `sql/update_<新版本>.sql` + 维护 `uninstall.sql`，不改历史脚本。
5. 重任务进队列(`Job`)、定时任务进 `schedule.php`，不阻塞请求线程。

### 1.3 完成产物（开发自检）

- 功能可在本地跑通（前端页面 + 后端接口 + 必要的队列/计划任务）。
- 通过《二开约束》§四「提交前自检清单」。
- 关键改动有必要的注释/文档（复杂业务在插件 `docs/` 留一句话说明）。

## 二、Git 提交规范

### 2.1 何时提交（提交时机）

- **完成一个可自洽的最小单元就提交**（一个接口、一个修复、一段可独立回滚的改动），不要攒一大坨。
- **每日至少推送一次**，避免本地长期积压丢失（进行中可用 `checkpoint` 类型，见下）。
- **核心与业务、不同插件的改动分开提交**（一次 commit 只服务一个 scope，便于审计与回滚）。
- 不提交「跑不起来」的半成品到共享分支；确需保存进度用功能分支 + `checkpoint`。

### 2.2 如何提交（提交信息格式）

沿用并固化项目现有的**约定式提交**：

```
type(scope): 简短中文描述

[可选正文：为什么改、影响面、关联需求/issue]
```

- **type 取值**：

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（不改行为） |
| `perf` | 性能优化 |
| `style` | 格式/样式（不影响逻辑） |
| `docs` | 文档 |
| `test` | 测试相关 |
| `chore` | 构建/脚手架/杂项 |
| `checkpoint` | 阶段性快照（进行中，仅限功能分支） |

- **scope 必须是插件 key**（如 `hsx_recycle`、`phone_shop`、`hsx_erp`）；跨插件用主插件名并在正文说明。
- **描述用中文动宾短语**，讲清「做了什么」，例：
  - `feat(phone_shop): 多站代理铺货与联动`
  - `fix(hsx_recycle): 修复手机站点端附件接口 getConfig`
  - `checkpoint(hsx_recycle): 设备录入/质检阶段性快照`

### 2.3 提交红线（禁提）

禁止提交（以 `.gitignore` 为准，新增忽略项同步更新）：`vendor/`、`node_modules/`、`dist/`、`runtime/`、`install.lock`、本地配置、**任何密钥/token/第三方凭证**。密钥若误提交：立即作废该凭证 + 从历史清除 + 通知负责人。

## 三、分支与合并

### 3.1 分支模型

| 分支 | 用途 | 约束 |
|------|------|------|
| `main`/`master`（主干） | 可发布的稳定代码 | 禁止直接推送未评审改动；只接受评审通过的合并 |
| `feat/<插件>-<功能>` | 功能开发 | 从主干切出，完成后发起合并 |
| `fix/<插件>-<问题>` | 缺陷修复 | 同上 |
| `hotfix/<问题>` | 线上紧急修复 | 修复后尽快合回主干并补测试 |

### 3.2 合并流程（PR/MR）

1. 自测 + 自检清单通过后发起合并请求，标题用约定式提交格式，描述写清：改了什么、影响面、是否动库、如何验证、回滚方式。
2. **至少 1 人 Review**；改动触及核心框架（走《二开约束》§1.3 例外流程）的，**强制 2 人 Review**。
3. Review 关注点：是否入侵核心、`site_id` 隔离、分层是否正确、有无魔法数字/硬编码、SQL 升级链、安全（鉴权/事务/幂等）。
4. 合并前确保**升级链可用**（从上一发布版按 `update_*.sql` 顺序能平滑升级）、无冲突、CI（若有）通过。
5. 合并方式团队统一（建议功能分支 squash 合并，保持主干历史清晰）。

## 四、版本管理

### 4.1 插件版本（SemVer）

- 版本号在插件 `info.json` 的 `version`，格式 `主.次.修`：
  - **修订号**：缺陷修复、不改接口/表结构。
  - **次版本**：向后兼容的新功能、加表/加字段（不破坏旧数据）。
  - **主版本**：不兼容变更（删/改字段语义、改接口契约）。
- **每次发布必须升 version**，且与本次 SQL/代码**同一提交**。

### 4.2 数据库版本（升级链）

- 表结构变更**只新增** `sql/update_<新版本>.sql`，**禁止改历史脚本内容**（`install.sql` 维护全新安装最终态，但不可破坏老版本升级链）。
- 脚本**可重复执行**：`CREATE TABLE IF NOT EXISTS`、加列前 `SHOW COLUMNS` 判断；表名用 `{{prefix}}`。
- 新表必须在 `uninstall.sql` 有对应 DROP；`Addon.php` 的 install/uninstall/upgrade 幂等。
- 「version ↔ update 脚本」一一对应，能从任意旧版逐级升到最新。

### 4.3 Tag 与发布对应

- 主干发布打 tag，tag 与插件 `version` 对应；破坏性变更在 `docs/` 公告并通知相关插件负责人。
- 跨插件契约变更：同步更新对应契约文档的版本与字段说明。

## 五、测试规范

### 5.1 自测（开发者，提交前必做）

- **功能正确性**：主流程 + 关键分支（异常入参、空数据、权限不足）。
- **多租户隔离**：用两个 `site_id` 验证数据不串号。
- **联动**：涉及队列/计划任务的，本地起 `php think queue:work`、`php think cron:schedule start` 验证任务真正执行。
- **多端**：uni-app 改动至少验证 H5 + 目标小程序端；admin/web 验证对应端。

### 5.2 测试用例（提测产物）

提测需附**冒烟用例清单**（最小可验证集），至少覆盖：

- 正常主流程跑通；
- 边界与异常（非法入参被 Validate 拦截、未登录被鉴权拦截）；
- 金额/库存/账务类：金额精度、对账一致、重复提交不重复扣减（幂等）；
- 状态机：非法状态流转被拒绝；
- 回滚/卸载：`uninstall.sql` 能干净清理。

### 5.3 联调

- 跨插件/前后端联调前，双方确认接口契约（URL、入参、响应 `code`/结构）。
- 联调环境数据可控、可重置；问题定位先看 `runtime/` 日志与接口返回 `code`。

## 六、验收（UAT）

### 6.1 进入条件

- 测试用例全部通过；自检清单通过；版本号与 SQL 升级链就绪。

### 6.2 验收标准（按维度）

| 维度 | 验收点 |
|------|--------|
| 功能 | 需求点逐条对照通过；主流程与关键异常均符合预期 |
| 数据隔离 | 多站点验证无串号；写入数据 `site_id`/操作人由服务端注入 |
| 兼容/升级 | 从上一版本平滑升级，老数据不丢不坏；可回滚 |
| 安全 | 鉴权到位、敏感操作有审计、无硬编码密钥 |
| 业务正确 | 金额/库存/账务对账一致、幂等；状态流转合法 |
| 多端 | 涉及端均通过（H5/小程序/App/admin/web 视范围而定） |
| 文档 | 契约/设计文档已同步；版本与变更记录完整 |

### 6.3 验收产物

- 验收清单逐项勾选（建议沿用 `docs/` 内「晨间验收清单」这类格式）；
- 遗留问题列表（含严重级别与处理计划）；
- 验收通过 → 版本封板。

## 七、发布与回归

1. **封板**：确认 `info.json` 版本、`sql/update_*.sql`、`uninstall.sql`、`Addon.php` 齐备且对应。
2. **发布前端**：各端 `publish.cjs` 打包，产物进后端 `public/`（addon→admin/web→…），核对资源路径前缀。
3. **安装/升级**：通过插件机制安装或升级（执行升级链 SQL + `Addon::upgrade()`），不手改框架表/菜单。
4. **回归**：发布后跑核心主流程回归；起队列/计划任务确认正常。
5. **回滚预案**：保留上一可用版本与降级/清理脚本；出问题先回滚再定位。

## 八、角色与责任（RACI 简版）

| 阶段 | 开发 | Reviewer | 测试 | 架构/负责人 |
|------|------|----------|------|-------------|
| 表结构/契约设计 | 提案 | 评审 | — | 拍板 |
| 开发+自测 | 主责 | — | — | — |
| 提交+合并 | 发起 | 必审 | — | 核心改动复审 |
| 测试+联调 | 配合 | — | 主责 | — |
| 验收 | 配合 | — | 配合 | 拍板封板 |
| 发布+回归 | 执行 | — | 回归 | 把关 |

## 九、流程红线汇总（违反即打回）

1. 改动入侵核心框架且未走例外流程。
2. 业务查询缺 `site_id` 过滤 / 信任前端传入的 `site_id`。
3. 升 version 但未配套 `update_*.sql`，或破坏了升级链。
4. 一次 commit 混合核心与业务 / scope 未标插件。
5. 提交了密钥、`vendor/`、`dist/`、`node_modules/`。
6. 未经 Review 直接推主干。
7. 提测无冒烟用例 / 验收无清单。
