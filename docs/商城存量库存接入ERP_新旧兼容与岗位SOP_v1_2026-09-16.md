# 商城存量库存接入 ERP：新旧兼容与岗位 SOP

版本：V1 · 2026-09-16

适用范围：回收、ERP、phone_shop 商城之间的存量设备接管，以及接管后的销售、收付款、维修、退货。

文档状态：业务执行方案／上线验收基线。已对照本地代码；不表示全部能力已实现或已部署。第十二节列明缺口。

本次交付：只整理 SOP，不清库、不导入、不修改业务代码、不操作线上数据。

## 一、先统一一句话：原商品保留，逐台接管，旧账不重做

不是把商城所有商品重新导入 ERP，再重新生成一批商城商品。

而是：**盘点实物 → 补齐设备身份 → 核对已有 ERP 记录和成本 → 关联原设备或建立期初 → 验证原商城商品仍可正常销售 → 确认由 ERP 接管。**

同时单独处理旧订单：**补设备关系可以，重做原收付款不可以。**

### 员工只需要先记住这张表

| 眼前是什么情况 | 应该做什么 | 谁负责 | 不应该做什么 |
| --- | --- | --- | --- |
| 旧商城商品，尚未核对完成 | 按原流程经营，登记待核对原因；成交后确认原商品停止销售 | 商城运营、原业务员 | 不凭后六位自动绑定，不凭空建立采购应付 |
| 旧商城商品，身份、成本、库存都已核实 | 从“商城库存对账”复用原 ERP 库存，或确认期初 | 接管操作员，库管及财务提供确认 | 不删除原商品，不重新导入一份 |
| 商品已由 ERP 接管 | 库存和设备成本由 ERP 管；商城负责展示及接单 | 库管、运营、业务员各自操作对应环节 | 不在两边分别改库存，不把同步失败当成“退回旧模式” |
| 培训启用后新收来的整机 | 回收确认进入 ERP，或直接在 ERP 入库，再发布商城 | 回收／采购人员、库管 | 不再导出后重复导入商城建立第二台设备 |
| 旧订单已成交但缺 ERP 设备 | 核对原订单，在原成交上补关联、补出库 | 原业务员、财务、接管操作员 | 不另开销售单，不重复生成应收，不再次收客户的钱 |
| 客户退回机器 | 找原订单，核实实物与原收款，再办退货／退款 | 原业务员牵头，库管收货，财务处理款项 | 不仅把商品重新上架，不删除原账 |

这是一套职责，不是要求增加六个人。小团队可以一人兼任多个角色，但每一步必须能查到具体办理人；涉及金额的确认应由有财务权限的人完成。

## 二、什么叫“接管成功”，什么叫“兼容旧数据”

### 2.1 接管成功必须同时满足

1. 实物确实是这台机器，完整 IMEI／SN 有证据，不只是商品名称或后六位相同。
2. 同一站点、同一设备本次在库周期，只对应一个有效 ERP 库存对象和一个有效商城销售对象。
3. 商城 SKU 与 ERP 设备建立明确关联；不是每次成交再按名称或尾号猜测。
4. 实物数量、ERP 状态、商城可售状态一致，没有尚未处理的占库订单。
5. 原商城商品、图片、分类、售价、链接、原订单保留。接管不擅自替换这些内容。
6. 上架、下架、销售、退货实际作用于这个原商品；重复点击／消息重试不再创建一份。
7. 原采购应付、已付款、原销售应收、已收款没有因接管被重复建立或抹掉。

**仅写入 ERP 关联 ID，或页面提示“关联成功”，不等于上述全部条件已经验收。**

### 2.2 旧数据兼容的边界

- 老商品仍能查询、按原业务销售和办理售后；缺资料不会让整个商城停业。
- 老订单、原支付流水、挂账、部分收款、退款记录继续有效，不能因新功能启用而失效。
- 尚未接管的旧库存与已接管库存明确区分；无法确认的数据不能混成“已核实”。
- 旧账已结清且不再有实物的，保留历史查询，不为了“数据统一”重新造一轮入库、销售和付款。
- 老商品逐批接管，不要求先补齐全部历史资料才能开展新业务；但待核对项必须有责任人、下一步及复核日期，不能永久隐藏。
- 兼容不等于把缺失成本当零、把后六位当完整 IMEI、把旧单改成新单。

### 2.3 库存归谁管，与钱在哪儿记，是两件事

尚未接管的商品，其销售也可能已经在 ERP 形成应收。这不矛盾：该笔应收必须保留并继续处理，不能因为设备未关联就再记一次。

每台设备有库存管理归属；每笔订单有原始成交及结算归属。**商品后来接管，不自动改变既有订单的付款、退款处理路径。**

## 三、岗位责任与交接标准

启用前，店长将下表填入实际姓名。不要写“大家负责”。

| 岗位 | 核心职责 | 交给下一人的结果 | 无权自行决定的事情 |
| --- | --- | --- | --- |
| 店长／业务负责人 | 确认启用范围、人员、例外；处理所有权和重复设备争议 | 启用名单、批次放行、异常裁定记录 | 不能要求用虚假串号／成本绕过校验 |
| 库管／收机人员 | 盘实物，读取完整串号，确认仓库库位和机器好坏；退货验机收回 | “物在哪、是哪台、能否卖”的确认及证据 | 不凭商品标题认机器，不确认钱已收到 |
| 商城运营 | 找到原商品，核对名称、图片、价格、原短码；补商品资料，控制发布 | 原商品与实物的对应，接管后原链接可售验证 | 不猜采购成本，不单独改已接管设备库存 |
| 财务 | 确认真实成本、历史已付／未付、已收／未收；处理款项和账目差异 | 金额依据、原账编号、是否仍欠款 | 不被要求重录全部质检和商品资料，不重复付款 |
| 接管操作员／系统管理员 | 执行预览、确认、结果核对；处理权限、同步失败、批次记录 | 逐台成功／失败结果及关联记录 | 不替业务确认实物，不替财务批准成本，不直接改数据库强行通过 |
| 原销售业务员 | 确认成交、交付人、客户；退货时对接客户并核对原单 | 原订单、实物交接、退货范围及原因 | 不用重新上架代替退货，不把挂账单当未成交单关闭 |

交接规则：前一人未完成的内容留在前一人的待办；下一人只确认自己负责的事实，不从头再填一遍。原业务员离职或不在，由店长指派替代人并保留原交付记录。

## 四、启用前准备：一次做清楚，不要求员工反复选模式

1. **指定站点和启用时间。** 每套独立系统、每个站点单独验收，不跨站批量关联。新收整机从该时间起执行 ERP 入口；老商品是否接管仍以逐台确认结果为准。
2. **确认唯一账务入口。** 已由 ERP 管的应收、应付继续在 ERP 处理；仍在旧账簿的债权债务列交接清单。确需迁入旧账时另做余额核对，不在本次库存接管中重放全部历史付款。
3. **准备接管清单。** 来源是商城候选记录加实物盘点，不把商品总数直接当库存台数。优先处理当前在售、实物在库、资料容易核实的自营单台设备。
4. **排除不属于本批的记录。** 代理货、代卖货、多数量标品、在途、正在维修、被订单占用、已交付未结清、已售历史记录分别进入对应队列，不能一起按期初在库导入。
5. **管理员确认环境。** 两插件配套版本、菜单权限、仓库权限、后台任务运行、同步结果可查询；完成第十三节验收后才放行生产接管。
6. **备份并记录基准。** 保存本批原商品、设备、订单和相关账款的基准记录及受控备份。资料访问按岗位授权，不把客户信息和完整串号公开散发。
7. **安排短时间核对窗口。** 只暂停本批相关设备的新交易；已存在订单先处理。不为处理二十台而停整个商城。

临时接管清单只记录编号、责任人、状态和核对证据，不另做一套长期库存账。目标是把这些信息收进系统工作台；当前尚未完整具备该工作台，见第十二节。

## 五、旧商城库存接管 SOP：从第一台开始怎么做

### 第 1 步：运营选商品，库管确认实物

- 运营选出本批原商品，登记商品／SKU 标识、旧短码、当前上下架状态、价格及是否有相关订单。
- 库管逐台确认实物所在位置、归属、数量。不能仅凭后台“库存 1”认定实物在库。
- 当前确实属于本站、实物在库、单台、无未处理占用的，进入下一步。
- 页面有库存但找不到实物：转“库存差异”，暂停这台销售，由原业务员核查；不创建 ERP 库存。

### 第 2 步：补齐完整串号，保留老短码

- 库管从设备系统、可靠设备读取或可核对的原始凭据取得完整 IMEI／SN，记录核对人和证据。
- 后六位保留作快速检索。它不是独立编号，也不是自动匹配依据。
- 相同尾号可能有多台；型号、颜色、容量、图片用于人工辅助核对，不能代替完整身份。
- 双卡 IMEI1／IMEI2、SN 要明确所属字段。不能因为 A 记录 IMEI1、B 记录 IMEI2 就直接判定为两台新设备；先用实物和原记录确认。
- 如果资料冲突，保留原内容及修正记录，不静默覆盖。补串号不改原订单历史快照。
- 当前没有安全补录入口或字段不能保存完整身份时，交管理员列为系统待补项；员工不直接修改数据库。

**完成标志：原商城商品与这台实物确认对应，完整身份可被对账服务读取。**

### 第 3 步：财务核成本、核原账

分两种情况：

1. **ERP 已有原设备：** 核对原采购和整备成本，原则上复用原资产及成本；商城成本不同不覆盖 ERP。确认确需调价时走正式成本调整，追加差额，不重写已付款事实。
2. **ERP 没有原设备：** 从原采购记录、业务台账及已确认费用核实接管时的真实库存成本。历史已计入的维修费不能再次加一遍。

同时注明：原供应商、原应付记录在哪、已付多少、还欠多少。已付不代表没有成本；期初入库也不代表供应商款已经付清。

成本不清楚：保留“成本待核”，不填售价、不填 0 或 0.01 凑数。真实赠送／确认为零成本的设备另行审批并使用支持该业务的明确入口；当前对账入口要求正数成本，不强行绕过。

### 第 4 步：处理占用，预览匹配结果

当前本地入口：**ERP → 期初建账 → 商城库存对账 → 有库存待关联**。生产是否有该入口需先确认版本及权限。

- 操作员先预览，不直接批量确认。
- 原订单仍有效、机器已交付、已退钱未收货等，不按在库接管；转到第七节旧订单处理。
- 暂停本批新交易并确认未产生新占用，再提交。预览后状态变化必须重新预览。
- 同一实物在 ERP 已有记录但商城没关联时，核对窗口内两侧均不得再次卖出；不能只下架商城却继续让 ERP 出库。

| 预览结果 | 操作员应该执行 | 应产生的结果 |
| --- | --- | --- |
| 可关联原库存 | 库管及财务核对通过后确认关联 | 复用原 ERP 资产、原仓库、原成本、原应付及付款；不新增库存和采购应付 |
| 需确认期初 | 核实 ERP 确无同台有效库存，确认实际仓库、库位、成本、期初日期 | 建立一台已拥有的存量库存并关联原 SKU；不生成新采购应付 |
| 已关联 | 查看对应设备和库存状态，不重复执行 | 原关联保持，不因再次确认增加台数或账款 |
| 需人工核对 | 按原因交给对应责任人 | 保留原记录；修正资料后重新预览，不批量“忽略错误” |

期初日期有实际依据，不随意编造原采购日期。若要补已成交设备，期初时点不得晚于原成交，且应使用已成交核对入口，不将其留成可售库存。

### 第 5 步：确认并逐台看结果

- 首批建议 5 台，覆盖“关联原设备”和“新建期初”；通过后以约 20 台一批推进，异常不拖住已核实设备。
- 当前页面每页 20 条，接口每次最多 50 条；不是一次点击盲扫全部旧商品。
- 每台独立提交：同批有成功也有失败是允许的。记录哪些成功，不能把“批次出现错误”理解为全部没有写入。
- 请求超时、页面断线：先重新查询原商品及关联结果，再决定重试；不要再建采购单、期初单或销售单补偿。

### 第 6 步：运营与财务验收交接

运营、库管核验：

- 还是原商品／SKU，原链接、图片、分类、售价保持；没有新建第二份可售商品。
- ERP 只增加应增加的设备：关联原资产不增加台数，新建期初每台只增加一次。
- 完整身份一致；可售、锁定、维修、已售等状态准确。
- 在受控验收中证明 ERP 上下架及订单占库作用于原商品；不是只看关联字段。

财务核验：

- 原采购应付及已付金额保持；新建期初没有生成采购应付或付款。
- 库存成本来源已确认，没有把售价当成本、把缺失当零。
- 本次未发生销售的接管操作，不新增销售应收和收款。

全部满足才确认“已接管”，记录时间及经办人，恢复该台正常交易。验证未通过，保留核对窗口和明确失败原因，交管理员处理；不能悄悄回退到两边各卖各的。

## 六、补不齐的老商品怎么继续经营

不是所有黄灯都必须停卖，但红灯必须处理。

| 问题 | 允许继续做什么 | 必须限制什么 | 负责人 |
| --- | --- | --- | --- |
| 只有后六位，实物和原商品能人工确认 | 继续明确标识的旧商城流程，安排补完整身份 | 不自动关联 ERP，不假造完整串号 | 库管 |
| 成本暂未找到，货权和实物清楚 | 按店长批准的旧业务流程经营，财务登记待核成本 | 收入不能当作已确认利润；不可建立虚假成本期初 | 财务 |
| 确认是代理／代卖货 | 沿用对应货权及结算流程 | 不转成本站自有库存，不与主站再次创建同一货权 | 业务负责人 |
| ERP 与商城有可能是同一台，但状态矛盾 | 查询原单、核查实物 | 暂停这台新交易，防一台卖两次 | 库管＋原业务员 |
| 完整串号重复／两边指向不同设备 | 核对不同回购周期、误录或重复记录 | 不自动选第一条、不删除有账设备、不自动解绑后重建 | 店长＋管理员 |
| 找不到实物、已售仍在架、退货未收回 | 查找责任人与原订单 | 立即停止这台可售，不以“旧模式”放行 | 原业务员 |

如果旧商品在接管前已卖掉，就从库存候选转为“已成交待核对／旧单归档”，不为了完成接管数量再虚增库存。没有可验证的历史成本，就明确保留历史成本待核；不能承诺无证据也能恢复完整利润。

## 七、老订单的兼容 SOP：与商品接管分开

### 7.1 分类处理

| 老订单情况 | 应执行的处理 | 必须保留的事实 |
| --- | --- | --- |
| 尚未支付、尚未交付 | 先按原单完成交易或合法关闭，释放占用后再决定是否接管 | 原订单、取消原因、真实占库结果 |
| 已挂账交付，ERP 有应收但没有设备 | 原业务员确认设备；在原成交上补设备关联、成本和出库 | 原应收、已收金额、未收金额、原客户及业务日期 |
| 已线上付款，没有待收应收 | 从“已成交待核对”找原成交，不为了核设备新开应收 | 原支付流水和原退款渠道 |
| ERP 已有该设备且仍在库，商城实际已售 | 先暂停该设备再次销售，核实原单后补原次出库 | 原资产、采购、付款；不能生成第二台 |
| ERP 没设备，但历史身份和真实成本可核实 | 受控建立对应期初并补原次出库，最终状态是已售 | 原成交和账款，不把已售设备留在可售库存 |
| 有部分退款、退货、撤回或重复成交 | 交售后核对原单及实物，再补关联 | 原售后及结算链；不直接按普通在库接管 |
| 多年前已结清、无库存也无售后 | 原记录保留查询；需要追溯时再核对 | 原流水和历史记录，不重造全生命周期 |

已存在 ERP 成交记录的入口：**应收详情 → 核对商城设备**，或 **商城库存对账 → 已成交待核对**。后者当前依赖已有 ERP 商城成交记录，并不是所有历史商城订单的全量浏览器；查不到不能说“这单不存在”，应由管理员核查原同步情况。

### 7.2 旧单缺串号／旧快照不完整，不让财务反复试错

目标操作是“补充关联证据”，不是覆盖原订单：

1. 原业务员确认订单与实际设备的对应，提供原交付／采购依据。
2. 库管核实完整身份，财务核实当时成本和已记账情况。
3. 管理员使用受控补充入口，保留原快照，追加补充内容、原因、证据及操作者；补充后重新预览。
4. 只补这次成交的设备关系、成本、出库；不改变原成交金额、已收金额、业务日期，不再次触发收款。
5. 不能证实属于哪台，就留在待核对，不把当前同名商品当作过去卖出的那台。

**当前缺口：** 已有保护会拒绝“原订单身份”与“当前商品身份”不同。因此，给现在的 SKU 补完整串号，不一定能修好过去已保存空／短身份的订单；旧订单成本快照缺失也不能靠改现在的商品成本自动补齐。上述受控补充入口需补齐后使用，不能由员工直接改历史快照。

### 7.3 成交来源保持稳定

原商城订单后来补了 ERP 关联，旧付款回调、重复消息、退款仍须找回同一笔原成交。不能因为当前商品“现在已经关联”就再按另一种来源建一笔销售或应收。该要求必须有回归测试，不仅靠提醒员工。

## 八、之后新增设备的日常 SOP

**回收／采购确认 → ERP 入库 → 必要的整备 → 定价及图片 → 发布商城 → 订单占库 → 成交出库 → 收款／挂账 → 售后。**

- 收机人录一次完整身份。回收已生成 ERP 设备的，不再手工建同台采购；直接 ERP 采购也不能重复引用同一回收记录。
- 库管确认实物。简单业务不增加无必要的逐级验收，复杂维修才启用相应流程。
- 需要维修时明确维修单位、费用、是否已付。真实费用既进入该台成本，也有相应的应付／付款依据；不只在成本上加一个数字。
- 历史维修已含在接管成本中的不能重记；接管后新增维修才追加。例如期初成本 4500 元，此后维修 100 元，总成本应为 4600 元，维修单位的 100 元按实际付款情况处理。
- 运营可以补图片、描述和分类；商品销售价调整按现有授权规则。设备身份、库存、已确认成本不能两边自由覆盖。
- 下单即占用该台库存；未付关闭按规则释放。线上付款或确认挂账后记录同一笔实际成交；商城成交不要求员工在 ERP 再开一次销售单。
- 财务只处理应收／应付及资金核实，不再被迫补设备型号、串号和图片。
- 设备与商城之间的同步失败形成待办；管理员重试原同步，不用再开采购、销售、收付款单推动它。

## 九、退货、退款、重新上架：谁做，做完得到什么

原业务员负责把事情接住；库管证明机器收回了，财务证明钱／债务处理了，运营才决定是否重新上架。

| 情况 | 原单和款项怎么处理 | 库存怎么处理 |
| --- | --- | --- |
| 未付款、未确认挂账、未交付 | 按原单取消／关闭 | 释放原占用；不形成一次销售退货 |
| 已交付挂账，完全未收款 | 办原销售退货，冲减对应未收应收；不是删除原账 | 实物验收后回到待上架 |
| 已收一部分，其余挂账 | 对退货范围冲减未收部分，已收部分生成应退款义务 | 确认实物回库后待上架，退款状态独立跟踪 |
| 线上已付款 | 原商城订单走原支付渠道退款，记录退款结果；不能让 ERP 再重复退一次 | 必须核对实物；当前线上设备流程须满足退款及收回确认条件才恢复可售库存 |
| 线下已付款且 ERP 已记录成交 | 原 ERP 销售退货形成相应退款应付，财务核实后退款 | 验机收回后待上架 |
| 老商城线下订单，没有 ERP 设备或有效退货入口 | 原业务员与财务核实原单，进入旧单售后队列；保留收回、退款证据，由指定管理员受控闭环 | 未核清前不直接改库存重新卖，也不能为了退款虚造设备或新销售单 |
| 一单多台，只退部分 | 按原订单明细处理指定设备和对应金额 | 不释放未退设备；部分金额补偿但不退机器的，不回补库存 |

示例：原成交 5000 元，已收 1000 元，尚欠 4000 元，整台退回且双方确认全额退货：冲减原剩余应收 4000 元，应退已收 1000 元。重新上架本身不产生新应收；以后再次卖出才产生新的成交。

重上架前必须确认：串号是原设备、机器已实际收到、状态可卖、原订单不再占库、款项处理路径明确。已接管设备从 ERP 发布原商品，不能新建第二份商品躲开旧单。

**当前缺口：** 后台“退回处理”对非线上订单引导到 ERP；没有可退 ERP 设备时可能没有可用按钮。完整兼容必须补老订单的售后入口，不能仅写一句“按旧流程处理”。补齐前，异常单集中交管理员与财务处理；该临时队列不代表系统已经完成退款或库存恢复。

## 十、异常处理与每日交班

### 10.1 异常只给明确的人，不给一个模糊“失败”

| 异常 | 第一责任人 | 处理动作 | 何时算完成 |
| --- | --- | --- | --- |
| 缺完整串号 | 库管 | 核实实物、补证据 | 预览读取到完整身份且无冲突 |
| 缺／冲突成本 | 财务 | 查原台账、采购及维修，确认或受控调整 | 成本依据完整，原账无重复 |
| 一个串号对应多条资产 | 店长＋库管 | 分清重复录入还是不同回购周期，管理员核关系 | 本次库存归属明确，历史记录保留 |
| 预览后被下单／售出 | 运营 | 停本台确认，刷新原订单状态 | 转对应订单核对或合法释放后重试 |
| 商城已售、ERP 仍可卖 | 原业务员＋管理员 | 停本台新交易，查询原成交与失败同步 | ERP 关联及出库正确，未重复建账 |
| 付款／退款状态不明 | 财务 | 查原交易号及实际流水，不能凭截图重复打款 | 资金核实并回到同一原单 |
| 确认后页面断线 | 接管操作员 | 查结果、重新预览后重试未完成项 | 每台有确定结果，没有重复设备和账款 |
| 同步失败／队列积压 | 管理员 | 查原事件、处理原因、重试原事件 | 接收侧业务结果验证通过，而不只是“已发送” |
| 开关关闭／ERP 暂不可用 | 管理员＋店长 | 停止新增接管；已接管数据保留责任，不自动改归商城 | 完成受控恢复或交接；已有订单付款回调和资金事实不能丢 |

黄色资料待核可以按既定旧流程经营；红色货权、占用、重复销售、付款疑点必须停止该台或该笔相关操作。系统故障不能要求员工“再点一次付款试试”。

### 10.2 每日交班只看五件事

1. 运营：今天哪些旧商品已卖出／下架，哪些已接管，是否存在两份可售商品。
2. 库管：已接管库存与实物是否相符，哪些退货已收到，哪些维修还未完成。
3. 财务：新增成交、收款、应收、退款能否对应原单；哪些成本未核实。待核成本的利润不作为已确认经营利润。
4. 管理员：同步失败、结果未知、关系冲突是否都有责任人与下一步。不得把“排队中”显示成“已同步”。
5. 店长：只处理未解决例外、超期任务和当日放行，不逐单替员工操作。

批次核对口径：本批总台数 = 已确认接管 + 待处理 + 已退出本批。退出必须注明原因，例如已成交转旧单核对、实物不属本店；不能通过删行让报表变好看。

库存核对要使用同一范围：已接管自营整机中的在库、订单占用、整备、已售分别比较，不能拿商城全部商品数与 ERP 全部资产数强行相等。

## 十一、系统应该怎样让员工看懂

以下是要落地的产品规则，不声称当前已有全部界面：

- 商品上使用“旧商城管理／待核对／ERP 已接管”标识；同步异常另外标红，不改变库存归属。
- 默认只显示型号、串号尾号、售价、可售状态、管理归属、下一步。完整 IMEI、成本依据、内部关联编号在详情按权限查看。
- 接管工作台按原因筛选：待盘点、缺串号、缺成本、可关联、需期初、冲突、已接管；显示总量及本批进度，不能把“本页数量”当全部完成数。
- 每条待办有负责人、原因、下一步、复核日期；正常数据不要求多人重复点击。
- 确认按钮前明确结果，例如“关联原库存：不新增采购应付”“确认期初：增加 1 台库存，不表示已付款”。
- 老订单显示原成交、已收、未收、已退、待退、是否收回设备；跳转到该笔原单，不让财务搜索一堆内部 ID。
- 普通成功用轻提示；资料缺失在对应字段提示；可能重复销售、重复付款、解绑已有账目的操作必须重提示并限制权限。
- 重试仅针对同一操作；重复请求返回原结果。用户可以查到最后成功时间和真实失败原因。

## 十二、对照当前代码：能做什么，还差什么

核对日期：2026-09-16。本节来自本地静态走查；生产部署、实际数据及页面未在本轮验证。

| 能力 | 当前结论 | 上线前处理 |
| --- | --- | --- |
| 在库预览、原资产关联、期初确认 | 本地已有抽屉和服务，包含身份、成本、货权、状态检查 | 使用目标版本完成页面及数据库验收 |
| 不重复建立原采购应付，保留原账 | 关联／期初服务有对应边界和逐台事务 | 对比处理前后的原应付、付款和库存台数 |
| 订单保存串号和来源快照，重试找原成交 | 本地有快照及原成交保护 | 验证补关联前后重复付款／退款通知不重记 |
| 老商品补身份、保留短码及证据 | 完整身份读取已存在，但本次流程需要的统一、可审计补录体验尚不完整 | 补录入口要同时考虑当前资料与历史订单，不能让员工直接改数据库 |
| 老订单缺／不完整快照、缺历史成本 | 严格身份比较会拦截事后变化；当前商品改成本不会修正旧快照 | 补受控历史资料确认／关联机制，保留原快照；这是兼容老数据的必要项 |
| 老线下订单无 ERP 设备时办理退回 | 现有引导依赖可退的 ERP 设备明细，存在操作断点 | 补旧单售后分流与收回确认；不能强迫虚造 ERP 库存 |
| 存量绑定后再次发布原商品 | 对账写入 SKU 关联；发布入口还涉及货源及渠道记录，不能仅凭关联推断闭环 | 必须验证并统一“复用原商品”；拦截重复建品，确保下架后能对原商品再次上架 |
| 成本待核与正式利润区分 | 商城原生成交服务可接收 0 成本并计算差额，仅有库存待核提醒不够 | 补已确认利润／待核成本区分；缺成本的销售不能以全部收入冒充已核实利润 |
| 接管状态、责任人、批次交接和关闭开关后的规则 | 库存关联基础已有，但完整岗位工作台与接管约束未全部确认 | 补必要提示、任务及写入口限制；不能只做一个状态标签 |
| 已接管商品两边并发成交、解绑、删除等边界 | 有订单事务占库及 ERP 销售保护，仍需覆盖所有实际入口 | 对管理员手改库存、旧商品重复建品、接管中成交、关闭联动等逐项回归 |

不能把“已有一个关联按钮”当成完整 SOP 已经交付。后续实现先补影响旧数据、钱、货安全的断点，再改善批量效率；不以增加人员重复录入替代程序应完成的保护。

## 十三、放行前验收清单

这是待执行的验收标准，不是本轮已通过的测试报告。每项留订单／设备标识、处理前后结果、执行人和日期。

| A10 | 商城和 ERP 同时尝试卖同一台 | 只有一笔能获得库存，另一笔明确提示已被占用 |

| A16 | 线上退款成功但实物未收回 | 不可再次出售；实物确认与财务结果均可追溯 |
| A17 | 老线下订单未关联 ERP，客户要求退回 | 有明确可操作的旧单售后入口，不需虚造资产和销售单 |

| A19 | 期初已含旧维修费，接管后再发生新维修 | 旧费用不重算；新费用有单位、应付／付款依据和成本变化 |
| A20 | 同步失败、关闭联动、插件不可用 | 已接管商品不自动降级；原订单资金事实不丢，有明确恢复入口 |
| A21 | 待核成本商品已成交 | 收入和收付款事实保留，正式利润不把缺失成本当零 |
| A22 | 不同站点、自营、代理、多数量商品 | 不越站关联，不把代理或标品当本站一台自有设备 |

先在隔离环境验证上述场景，再由指定人员对小批真实商品做交接验收。涉及真实支付渠道的验收须另获授权；本地断言通过不能代替线上渠道验证。

## 十四、出问题如何停，不把数据越修越乱

- 只暂停异常设备／批次，不清空全站；保留处理前后记录和已成功结果。
- 尚未确认的预览可以退出。已经确认、但未形成新业务的错误关联，由管理员核查后走受控纠错，不让普通用户自行解绑。
- 已产生销售、付款、退款、维修等事实的，按原业务做纠正或反向处理，不删除资产和资金流水掩盖问题。
- 恢复旧代码前要确认其是否认识新关联和订单状态；不能只回滚前端继续收款。
- **上线后已有新交易，不允许直接拿接管前整库备份覆盖生产。** 必须按受影响记录及原单核对恢复，保留之后真实发生的业务。
- 本 SOP 不授权新增表字段或修改框架。实现时优先复用现有能力；确需数据库升级，先列字段、用途、升级和回退方案，再告知用户确认。

## 十六、执行顺序与交付边界

1. 按本 SOP 固定规则、岗位及验收口径，不再往返切换“清库重建”与“全部不管”。
2. 开发补第十二节影响正确性的缺口：老资料补录、旧单售后、原商品复用、接管约束、待核利润。
3. 完成第十三节回归，给出逐项测试记录、需更新文件、是否有数据库升级；不是口头说“应该好了”。
4. 员工用小批旧商品完成真实交接，问题按明确责任处理；验收通过后逐批扩大。
5. 新收整机执行 ERP 入口，旧库存按清单持续接管或正常售完归档；老板看进度和异常，不需要逐台猜怎么做。

成功标准：每台当前设备知道谁管、每笔钱知道来自哪张原单、每个异常知道谁处理；重复同步不会多一台机器、多一笔应收或多一次付款。并非要求把所有无法核实的历史资料伪装成完整数据。
