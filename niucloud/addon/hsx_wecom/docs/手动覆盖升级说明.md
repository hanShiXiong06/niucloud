# 企业微信插件：手动覆盖升级说明

适用：本套 SaaS 已安装并启用 `hsx_wecom`，不走框架“一键升级”，由你手动覆盖代码、执行 SQL、打包前端。核对日期：2026-09-29。

**后续增量：** 如果昨天的服务商结构已安装完整，本次“首次创建应用／回调准备”**没有新增 SQL 表／字段**。除插件代码与管理前端外，回归发现并补齐了本文原已列出的三个员工绑定权限字典；需按第 4 步检查并补缺菜单记录，再按第 5 步给配置管理员授权。文件清单及操作顺序见 [创建应用前回调准备与测试](2026-09-29_创建应用前回调准备与测试.md)。下文建表步骤仅适用于尚缺原服务商结构的环境。

**同一套 SaaS 的客户共用域名、共用平台通道；客户企业授权与员工绑定按站点隔离。不要给每个客户重配平台 Suite，不要把甲方密钥填进平台 SuiteSecret。** 接入步骤见[企业微信服务商接入操作指南](企业微信服务商接入操作指南.md)。

## 本次会改变什么

| 交付 | 作用 | 不会做什么 |
| --- | --- | --- |
| `sql/upgrade_20260929_provider_manual.sql` | 创建缺失的 6 张企微表；只补当前声明中缺失的列和索引 | 不删除/清空表，不覆盖授权、绑定或消息记录，不更新业务金额 |
| `sql/manual_upgrade.php --check` | 使用服务器实际数据库配置，只读检查表、索引、菜单及补偿任务 | 不建表、不发送通知、不改角色 |
| `sql/manual_upgrade.php --register-runtime` | 仅补缺本插件菜单权限与“企业微信消息补偿”任务；清理菜单专用缓存 | 不运行插件升级生命周期，不全量重置菜单/任务，不给所有员工授权 |

这次员工扫码流程复用已有 `wecom_authorization_intent.meta_json`，**没有为扫码再加表或字段**。但旧环境如果尚未具有服务商结构，SQL 会补建这些既有功能所需的表/列/索引，因此必须备份。

6 张表后缀：`wecom_provider_suite`、`wecom_corp_authorization`、`wecom_authorization_intent`、`wecom_callback_event`、`wecom_staff_binding`、`wecom_message_log`。

## 1. 先备份并确认发布范围（你/运维）

1. 备份数据库、当前插件目录、现用前端发布产物，以及环境配置；备份放在网站公开目录之外。
2. 单独安全备份现有 `app.auth_key`，不要重置。它关系到授权密文解密和任务链接校验；也不要把密钥发到群里。
3. 记录当前通知开关、平台通道、客户授权状态和消息积压数，不要为升级清空记录。
4. 安排短维护窗口，避免同时运行两个结构/菜单升级命令。现有队列/计划任务的重启会影响本套系统其他插件，需安排运维窗口。
5. 这份流程针对“已安装插件的升级”。未安装/未购买/未启用插件，不能靠建 6 张表伪造安装与租户权益；先完成正常安装/启用。

本文所有服务器命令均在含 `think`、`app`、`addon` 的 **PHP 根目录 `niucloud`** 执行，不是 `admin` 或 `uni-app` 目录。PHP 命令需使用网站对应版本，并使用现有运行账户。

## 2. 覆盖插件后端与前端源码（你/运维）

1. 覆盖交付的 `niucloud/addon/hsx_wecom/`；不要覆盖服务器 `.env`、`vendor`、上传图片、运行日志及数据库文件。
2. 管理前端有两份位置：插件分发源 `niucloud/addon/hsx_wecom/admin/` 与实际打包源 `admin/src/addon/hsx_wecom/`。把交付的整个插件 `admin/` 子目录同步到实际打包源（不删除其他本地自定义文件），包括 `api/index.ts`、`utils/binding-session.ts`、`views/config/index.vue`、`views/config/components/ConnectionGuide.vue` 和 `views/config/components/StaffBindingDialog.vue`。漏传新增组件会导致构建缺模块。只覆盖插件分发源再打包，不一定会自动复制到实际源码。
3. 管理小程序如果也包含本次交付的入口/导航修复，按交付文件清单单独更新 `site-uniapp` 并发布；**只打包 PC 后台不会更新已经发布的小程序**。已有跳转修复范围见[手机企微跳转修复与测试](2026-09-29_手机企微跳转修复与测试.md)。

先做语法/离线一致性检查（不访问数据库）：

```bash
php -l addon/hsx_wecom/sql/manual_upgrade.php
php addon/hsx_wecom/sql/build_manual_upgrade.php --check
php addon/hsx_wecom/tests/manual_upgrade_smoke.php
```

预期：最后两项输出 `PASS`。它们证明交付 SQL 与 `WecomSchema`、安装 SQL 一致，以及补缺菜单规则通过离线测试；不是线上安装或微信真机验收。

## 3. 手动执行增量 SQL（你/运维）

打开 [upgrade_20260929_provider_manual.sql](../sql/upgrade_20260929_provider_manual.sql)，只改文件开头这一行：

```sql
SET @wecom_prefix = 'ns_';
```

把 `ns_` 改为这个服务器应用真实使用的前缀，如 `saas_` 或 `phone_`。**数据库名和表前缀不是一回事，不要根据库名猜前缀。** 用当前环境配置及数据库现有表核对。

在 phpMyAdmin/数据库客户端中：

1. 先选对本套 SaaS 正在连接的数据库。
2. 核对 SQL 第一段输出的 `target_database`、`table_prefix`。
3. 导入/执行完整文件，使用同一连接；文件中的 `SET` 变量不能跨不同连接拆开执行。
4. 任何语句报错，立即停止并记录原始错误，不要忽略错误继续发布。MySQL 命令行不要使用 `--force`。
5. 成功后继续执行第 4 步只读检查，不把“最后一行执行成功”当成全部语句成功。

SQL 不需要存储过程权限，使用 `PREPARE` 和 `information_schema` 判断是否缺失。执行账户需要查询、建表、增加列/索引等相应权限。

**可重复执行的含义：** 表/列/同名索引已有就跳过，不覆盖数据。它不会自动纠正现有列类型、修改错误的同名索引、合并重复授权。若历史重复数据使唯一索引无法创建，会报错而不会擅自删数据；需要单独确认处理。

MySQL DDL 常会隐式提交，不能靠 `ROLLBACK` 整体撤销。中途失败可能已经补齐一部分结构；修正原因后可重跑，不要删除已存在的表重新来一遍。选错数据库/选错合法前缀不会被脚本自动猜出来，所以第 1、2 步必须人工确认。

## 4. 补齐菜单与消息补偿任务（你/运维）

先运行默认只读检查：

```bash
php addon/hsx_wecom/sql/manual_upgrade.php --check
```

它会显示实际库名、前缀、缺失列/索引、缺失菜单键和任务状态，不打印 SuiteSecret、授权码等秘密。缺失时退出码为 `1`，先看具体哪一项，不要盲目重装。

结构完整后，如果提示菜单/任务缺失，显式执行：

```bash
php addon/hsx_wecom/sql/manual_upgrade.php --register-runtime
php addon/hsx_wecom/sql/manual_upgrade.php --check
```

该动作只补缺当前插件字典中的菜单和计划任务，复用框架已有模型/注册服务，不猜系统表结构；重跑不重复添加。既有菜单如被停用、软删除、改过接口，工具会保留并提示/停止，不会强行覆盖。既有补偿任务若被停用，也不会擅自启用。

为什么不能只有 SQL？因为直接覆盖不会执行 `Addon::upgrade()`，所以不会自动注册本插件的定时补偿任务；仅有接口文件也不会自动生成管理员接口权限。

**不要用全局“重置菜单/重置计划任务”代替本步骤。** 框架全局重置计划任务会清空重建系统任务，不属于本插件升级的必要操作。

## 5. 为配置管理员授予新增权限（甲方站点管理员）

重新登录后台后，在 `/site/setting/auth/role` 找到负责企业微信配置的角色，按需勾选“企业微信 → 协同配置”下的权限：

- 查看绑定进度：`hsx_wecom_staff_bind_status`。
- 确认员工身份：`hsx_wecom_staff_bind_confirm`。
- 撤销绑定入口：`hsx_wecom_staff_bind_cancel`。

保留其原有“员工授权绑定”“员工绑定”“发送测试通知”等必要权限。**只授权给负责配置的管理员，不要为了员工扫码而给普通员工后台配置权限。** 普通员工继续保持自己的业务角色。

脚本补菜单并不等于给所有既有角色自动追加权限。若前端按钮出现但接口提示无权限，先核对这一步和当前登录站点，不要关闭权限校验。

## 6. 打包发布并刷新长驻进程（你/运维）

1. 在 `admin` 按现有生产打包流程构建和发布。先确认本套项目 `package.json` 的 build 是否包含发布动作，保留旧产物备用；不要顺手升级全部 npm 依赖。
2. 用宝塔/Supervisor/现有运维方式重载网站 PHP 服务（使 OPcache 使用新代码），刷新已在使用的队列和计划任务进程。不要并行再起一套相同消费者。
3. 本项目源码确认的状态命令（在 PHP 根目录）：

```bash
php think cron:schedule status
php think queue:listen status
```

如果该服务器确实由项目 Workerman 命令管理、不是被别的进程管理器托管，运维确认后可以用现有命令重启：

```bash
php think cron:schedule restart -m d
php think queue:listen restart -m d
```

只重启实际在使用的消费者；队列配置关闭时，不需要为了这次升级新启一个队列。`queue.state` 开启时要有队列消费者；关闭时普通消息仍依赖正常运行的“企业微信消息补偿”定时任务。调度器启动时读取任务列表，因此新增任务后必须刷新调度进程。

“发送测试通知”是即时执行，**测试成功不代表队列/补偿任务正常**。不要执行全量缓存清空、Redis `FLUSHALL` 或删除整个 `runtime` 目录。工具已清理菜单专用缓存，其他发布缓存按服务器现有、明确范围的流程处理。

## 7. 接入与验收（你 + 甲方管理员 + 一名员工）

| 操作 | 谁来做 | 通过标准 |
| --- | --- | --- |
| `/admin/setting/hsx-wecom/provider` 核对共享通道 | 平台管理员 | 原凭据仍可读取状态，SuiteTicket/验证正常；不为每个租户换通道 |
| `/site/hsx_wecom/config` 核对授权 | 甲方管理员 | 当前站点对应正确的甲方企业；老的正常绑定没有被清空 |
| 生成一名测试员工的专属扫码入口并完成确认 | 甲方管理员 + 员工本人 | 身份正确、状态明确；其他员工不可占用绑定 |
| 发一条测试通知 | 甲方管理员 + 员工本人 | 员工实际收到，点击能进管理首页；不是只看发送日志成功 |
| 分配一笔受控测试工单 | 业务管理员 + 员工本人 | 普通队列/补偿发送正常，点击进入正确业务，有符合角色的操作权限 |

验收不做真实打款、删单或重复重试历史消息。测试人员、企业、站点、设备、结果和时间记录在操作指南末尾的验收表中；真实手机企业微信仍需现场验证。

## 出错与回退

- `表不存在`：先核对应用真实库/前缀，再执行增量 SQL；不要只在另一个库中建同名表。
- 唯一索引报重复：保留数据和错误，停止升级；本交付不会擅自决定删哪条授权。
- 权限不够：数据库 DDL 权限交给运维处理；站点接口权限由甲方管理员按第 5 步处理。
- 菜单没出现：确认插件安装/启用、租户使用权限、运行目录、菜单注册结果及重新登录；不要把普通员工升级为超级管理员。
- 已有任务停用：先问负责人停用原因；工具保留原状态，不替你改变投递策略。
- 需要回退代码：恢复备份的插件/前端产物并刷新相应进程。结构是增量添加，一般先保留，不提供破坏性的 `DROP` 回退脚本；旧代码是否可继续用仍需对应版本验证。
- 需要数据库恢复：维护窗口中由运维从备份恢复，并核对升级后新增的授权/消息等记录。不能直接拿升级前备份覆盖已有新业务却声称无损。

## 交付自检说明

`build_manual_upgrade.php` 从当前 `WecomSchema` 收集结构，与 `install.sql` 对照后生成 SQL；`--check` 比较交付文件，防止手工 SQL 漂移。它不会加载框架或连接数据库。

本轮验证：

- PHP 语法检查通过；离线合同测试 **143 项通过**，覆盖 6 表、96 列、29 个索引及菜单补缺保护。
- 在 `/tmp` 专用数据目录、独立 socket、关闭网络的 **MySQL 9.3.0 临时实例**中执行 **59 项检查通过**：新建、重复执行、6 张极简旧表补列/索引、保留原行、改前缀、`NO_BACKSLASH_ESCAPES`、非法前缀及未选择数据库保护。测试后关闭临时实例。
- 临时实例测试入口：`tests/manual_upgrade_mysql.php --socket=/tmp/hsx-wecom-sql-临时目录/mysql.sock`。此脚本拒绝默认 socket/TCP/其他数据目录，不能拿线上连接参数去运行。

**没有对你的线上库执行 SQL，没有连接现有业务数据库，也没有向客户企业微信发送通知。** 目标服务器可能使用不同 MySQL 版本、SQL 权限和既有表结构，因此目标环境的备份确认、只读检查与真机业务验收仍必须按本说明执行。
