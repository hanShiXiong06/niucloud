# 上新通知单会员试发

## 已确认的根因

线上微信模板是“新商品上架提醒”，字段为 `number1` 上架商品数、`time2` 上架时间、`thing3` 品牌、`thing4` 备注、`thing5` 供应商。旧插件错误地发送商品名称、变动类型、说明、价格和提醒时间，导致微信返回 `47003 / data.number1.value`。即使同为 `thing3`，原先发送的“说明”也不是微信需要的“品牌”。

修正的是插件内字段映射和业务变量，不删除或重新申请原微信模板，不改模板 ID，不修改订阅记录，不做数据库升级，也不需要重新发布小程序。

## 先用一个文件试发

文件：`tools/phone_shop_notice_probe.php`。

将这个文件上传到线上后端根目录，即与 `think`、`.env`、`vendor` 同级的位置。只通过服务器终端执行，不要放到 `public`，不要通过浏览器访问。

本次站点为 `100005`，会员为 `75`。命令中的 PHP 应使用网站实际运行的 PHP 版本。

```sh
cd /www/wwwroot/gl.hsxbk.top/niucloud
php phone_shop_notice_probe.php --site-id=100005 --member-id=75
```

默认只检查配置、会员的小程序身份、有效订阅和消息内容，不发微信、不修改订阅记录。

新版脚本输出 `probe_version: 1.2.0`。线上业务代码尚未更新时，用已经核实的上新模板字段试发：

```sh
php phone_shop_notice_probe.php --site-id=100005 --member-id=75 --arrival-template --send
```

脚本先读取微信的真实模板，核对标题、字段编号和含义，全部一致后才试发一条。通知中的上架商品数为 `0`，品牌/供应商明确标注测试，备注是“通知通道测试，不代表实际上新”。微信消息标题固定为模板的“新商品上架提醒”，不能通过发送数据改标题。

点击通知进入已有商品列表页。此脚本不走队列，不持久修改线上模板配置，不依赖本次后端修复包。`mapping_mode: arrival_template_test_only` 表示仅本次测试采用修正映射，不代表正式后台已经更新。去掉 `--send` 可只核对，不发消息。

## 如何看结果

- `wechat_accepted`：微信已受理，请到该会员的微信服务通知中查看；不代表已阅读。
- `wechat_rejected`：查看 `send_result.reason`。例如 `43101` 是微信拒绝、取消或一次性额度不足等情况，不能仅凭历史订阅记录保证送达。
- `blocked`：查看 `blocked_reasons`，如没有本站小程序 OpenID、没有有效订阅、模板未配置等；未发起消息发送。
- `result_unknown`：网络结果不确定，不自动重发。
- `duplicate_blocked`：之前已经受理或结果不明，本次没有重复发送。

将终端输出反馈即可。脚本不打印密钥、访问令牌或完整 OpenID。

## 微信返回 47003 时

`47003` 表示消息字段或格式被微信拒绝，不是发送成功，也不能据此认定订阅授权额度足够。线上已确认旧字段映射不匹配；修正后若仍报错，继续以微信返回的具体字段为准。

覆盖更新同一个 `phone_shop_notice_probe.php` 即可，不需要先替换线上业务服务。想检查正式后台目前是否仍使用旧映射，执行：

```sh
php phone_shop_notice_probe.php --site-id=100005 --member-id=75 --check-template
```

脚本读取微信当前应用的模板列表，核对实际字段及微信返回的枚举限制。字段不匹配时直接停止，输出 `template_check.missing_fields`、`unexpected_fields`、`invalid_enums`。如果明确加 `--send` 试发后微信仍拒绝，会在 `send_result` 中保留 `wechat_errcode`、微信指明的 `invalid_field` 和 `wechat_request_id`（微信提供时）。仅提取这些诊断项，不原样打印可能包含身份或凭据的 `errmsg`。

字段核对通过只表示字段名称和已返回的枚举规则匹配，不保证微信剩余额度充足。

实际发送的数据与 `message_preview` 一致，不会将 `date5` 猜测改成 `time5`。旧的明确失败回执允许修复后人工再试；原有成功、发送中或结果不明的回执继续阻止重复发送，不需要清理回执目录。

正式业务通知的具体错误字段提示位于 `app/service/core/goods/CoreGoodsNoticeService.php`；这个文件可随后端业务修复一起部署。单文件诊断无需提前更新它。

试发回执保存在 `runtime/phone_shop_notice_probe/`。已受理或结果不明的同站点、会员、应用及模板不重复发送。不要删除回执后盲目重试；明确失败的请求在修复原因后可以重新执行。回执文件不是业务订阅表，不修改客户订阅状态。

## 保存通知记录报 update_time 不存在

插件安装 SQL 中，`phone_shop_goods_subscription_match` 只有 `create_time` 和 `notify_time`，没有 `update_time`。原模型继承全局自动时间戳设置，创建后再次 `save()` 时，ThinkORM 会将 `update_time` 加入 UPDATE，导致缺列错误。模型现已用 `protected $updateTime = false;` 关闭该字段；不需要给表加列，不影响订阅表和导入任务表正常记录更新时间。

如果其他业务代码已经更新，本次只需补充上传 `app/model/goods/GoodsSubscriptionMatch.php`，再正常重启实际通知队列和刷新网站 PHP 代码缓存。注意这个错误可能发生在微信已受理、回写发送结果时；不能据此判断消息没有发送。不要清空留痕或批量重发，历史发送中及结果不明记录本次不自动处理。

`tests/phone_shop_notice_timestamp_smoke.php` 使用真实 ThinkORM 模型和 MySQL SQL 生成器，对照安装 SQL 校验写入字段，不连接数据库、不发微信；同时复现旧设置报错，并验证其他模型保留自动更新时间。

此处的本地隔离测试不等于线上发送或手机收件验收。2026-09-23 21:50:27 用户线上单会员测试返回 `wechat_accepted / wechat_errcode=0`；已确认微信受理测试通知，但正式批量发送和手机收件尚未验收。
