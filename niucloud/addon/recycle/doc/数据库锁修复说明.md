# 数据库锁问题修复说明

## 问题分析

原代码存在以下导致数据库锁的问题:

1. **长事务锁表**: HTTP响应保存和大量数据插入在同一个事务中,导致锁持有时间过长
2. **批量插入无分批**: 一次性插入大量数据,可能导致长时间锁表
3. **循环查询更新**: 在事务内循环查询和更新型号表,增加锁竞争
4. **连接未正确关闭**: 长时间运行的脚本可能导致数据库连接泄漏

## 优化方案

### 1. 缩小事务范围
- 将HTTP响应保存移出大事务
- 每批数据使用独立的小事务
- 减少锁持有时间

### 2. 分批插入数据
- 每批插入100条数据
- 批次间添加小延迟(10ms),释放数据库压力
- 添加详细的日志记录

### 3. 优化型号表更新
- 一次性查询所有需要更新的型号
- 减少数据库往返次数
- 使用批量更新替代循环更新

### 4. 添加数据库连接管理
- 设置合理的连接超时参数(10分钟)
- 执行完成后显式关闭连接
- 添加自动重连机制
- 添加死锁重试机制(最多3次,指数退避)

## 使用方法

### 正常使用
代码已自动优化,无需修改调用方式。执行爬虫任务时会自动:
- 设置数据库连接超时
- 分批插入数据
- 使用小事务
- 自动重试死锁
- 执行完成后关闭连接

### 监控数据库锁
如果怀疑有数据库锁问题,可以运行诊断脚本:

```php
use addon\recycle\app\service\admin\quotation\DatabaseLockMonitor;

// 运行完整检查
$report = DatabaseLockMonitor::runFullCheck();

// 如果需要终止阻塞的进程
DatabaseLockMonitor::killProcess(17); // 17是进程ID
```

### 命令行监控
也可以在MySQL命令行中手动检查:

```sql
-- 查看当前锁等待
SELECT * FROM sys.innodb_lock_waits;

-- 查看长时间运行的事务
SELECT
    trx_id,
    trx_state,
    trx_started,
    trx_mysql_thread_id,
    trx_query,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) as duration_seconds
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30
ORDER BY trx_started;

-- 查看活跃进程
SHOW FULL PROCESSLIST;

-- 终止阻塞的进程
KILL 17;  -- 将17替换为实际的进程ID
```

## 性能参数调优建议

### 1. 调整批量大小
如果数据量非常大,可以在 `QuotationDataService.php` 中调整批量大小:

```php
$chunkSize = 100; // 默认100条,可以根���实际情况调整为50-200
```

### 2. 调整延迟时间
批次间的延迟时间可以根据数据库负载调整:

```php
usleep(10000); // 默认10毫秒,可以调整为5000-50000
```

### 3. 调整重试次数
如果死锁频繁,可以增加重试次数:

```php
DatabaseHelper::executeWithRetry($callback, 5, 200); // 重试5次,初始延迟200ms
```

## 日志监控

优化后的代码会记录详细的日志,可以通过日志监控执行情况:

## 数据库配置建议

在 `config/database.php` 中添加以下配置:

```php
'connections' => [
    'mysql' => [
        // ... 其他配置

        // 连接池配置
        'pool' => [
            'max_connections' => 10,      // 最大连接数
            'min_connections' => 1,       // 最小连接数
            'wait_timeout' => 3.0,        // 获取连接超时时间
        ],

        // 连接超时设置
        'options' => [
            \PDO::ATTR_TIMEOUT => 10,     // 连接超时10秒
        ],

        // 断线重连
        'break_reconnect' => true,        // 开启断线重连
    ],
],
```

## 预期效果

优化后应该能够:
1. **消除长时间锁表**: 事务持有锁的时间从可能的数分钟降低到秒级
2. **提高并发性**: 小事务允许其他查询更快地获取锁
3. **减少死锁**: 重试机制能够自动处理临时性的死锁
4. **防止连接泄漏**: 显式关闭连接确保资源正确释放
5. **更好的监控**: 详细的日志帮助快速定位问题

## 问题排查

如果优化后仍然出现锁问题:

### 1. 运行诊断
```php
DatabaseLockMonitor::runFullCheck();
```

### 2. 检查日志
查看是否有重试失败的记录,如果频繁失败可能需要进一步优化

### 3. 调整参数
- 减小批量大小(如改为50条)
- 增加批次延迟(如改为50ms)
- 增加重试次数

### 4. 数据库优化
- 检查是否缺少索引
- 检查表是否需要优化(OPTIMIZE TABLE)
- 考虑增加数据库服务器资源
