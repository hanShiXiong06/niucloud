# 跑腿业务集成指南

## 概述

本文档说明了如何在原有的家政服务系统中集成跑腿业务功能，使其能够：
1. 支持多包裹订单（每个包裹有不同的服务类型和价格）
2. 与原系统完全兼容，享受优惠券等优惠
3. 需要收货地址（骑手配送目的地）
4. 每个包裹有独立的取件码（用于取件识别）

## 跑腿业务逻辑

### 业务流程
```
用户下单
  ↓
填写包裹信息
  - 服务类型（邮政｜小件、中通｜大件等）
  - 取件码（用于骑手取件）
  - 价格
  ↓
选择收货地址（骑手送到哪里）
  ↓
选择取件时间
  ↓
支付
  ↓
骑手接单
  ↓
骑手根据取件码取件
  ↓
骑手送到用户指定地址
```

### 关键概念
- **取件码**：用于骑手在快递点/驿站取件的凭证（如快递单号、提货码）
- **收货地址**：骑手取件后要送达的目的地
- **服务类型**：不同快递公司和包裹大小（邮政｜小件、顺丰｜大件等）

### 关键字段说明

  - `sku_name`: 服务类型名称（如"邮政｜小件"）

  - `price`: 该包裹的价格
- `total_price`: 所有包裹的总价

## 工作流程

### 计算流程（calculate）

```
1. 前端发送包含 type: "errand" 的数据
2. setParam() - 保存参数
3. 检测到跑腿业务，跳过地址选择
4. confirm() - 查询主商品信息（使用 sku_id）
5. getGoodsData() - 获取商品数据
   - 跳过状态和数量检查
   - 使用会员价计算（如果有会员等级）
   - 不使用城市策略价
6. handleErrandBusinessGoods() - 处理多包裹
   - 遍历 items 数组
   - 累加所有包裹价格
   - 更新商品数据
7. calculateDiscount() - 计算优惠
   - 基于总金额计算优惠券折扣
   - 优惠会按比例分摊到各个包裹
8. 返回计算结果给前端
```

### 创建流程（create）

```
1. 获取缓存的订单数据
2. 构建订单主数据
   - 跑腿业务不填充地址
   - 添加 is_errand 标识
3. 遍历商品数据创建订单项
   - 如果是跑腿业务：
     * 遍历 errand_items
     * 为每个包裹创建一个订单项
     * 保存 pickup_code
   - 如果是普通业务：
     * 创建单个订单项
4. 事务中创建订单和订单项
5. 使用优惠券（如果有）
6. 返回订单 ID
```

## 优惠支持

跑腿业务完全支持原系统的优惠功能：

1. **会员折扣**: 如果商品设置了会员折扣，会员下单时自动享受折扣价
2. **优惠券**: 可以使用满足条件的优惠券
3. **次卡**: 如果有次卡，也可以使用次卡下单

优惠计算基于：
- 主商品的 `sku_id` 和商品信息
- 所有包裹的总金额
- 优惠会自动分摊到各个订单项

## 数据库字段

### home_service_order 表
**必须添加以下字段：**

```sql
ALTER TABLE `home_service_order` 
ADD COLUMN `is_errand` TINYINT(1) DEFAULT 0 COMMENT '是否为跑腿业务' AFTER `is_auto_refund`,
ADD COLUMN `errand_items` TEXT NULL COMMENT '跑腿包裹信息JSON' AFTER `is_errand`;
```

字段说明：
- `is_errand`: TINYINT(1) - 是否为跑腿业务（0=否，1=是）
- `errand_items`: TEXT - 跑腿包裹信息的完整 JSON 数据

`errand_items` JSON 格式示例：
```json
[
  {
    "sku_id": 1,
    "sku_name": "邮政｜小件",
    "pickup_code": "111",
    "price": "2.00"
  },
  {
    "sku_id": 2,
    "sku_name": "邮政｜中件",
    "pickup_code": "222",
    "price": "3.00"
  }
]
```

### home_service_order_item 表
**建议添加字段：**

```sql
ALTER TABLE `home_service_order_item` 
ADD COLUMN `pickup_code` VARCHAR(100) NULL COMMENT '取件码或快递单号' AFTER `sku_name`;
```

字段说明：
- `pickup_code`: VARCHAR(100) - 取件码或快递单号（每个订单项独立保存）

### 为什么要保存 errand_items JSON？

1. **完整性保留**：保存前端提交的原始数据，便于追溯和问题排查
2. **数据冗余**：虽然订单项表也有详细信息，但 JSON 格式更便于快速查看所有包裹
3. **灵活扩展**：未来如果需要添加更多包裹属性，不需要修改表结构
4. **前端展示**：前端可以直接读取这个 JSON 显示所有包裹信息，不需要额外查询
5. **数据一致性**：保证原始提交数据和处理后的数据都有记录

### 数据存储策略

- **Order 表**：保存完整的 `errand_items` JSON（原始数据）
- **OrderItem 表**：保存每个包裹的独立记录（规范化数据）+ `pickup_code`
- **优势**：既有原始数据便于查看，又有规范化数据便于统计和查询

## 测试要点

1. **单包裹订单**: 测试只有一个包裹的情况
2. **多包裹订单**: 测试多个包裹的情况（2-5个包裹）
3. **会员折扣**: 测试会员价格是否正确计算
4. **优惠券**: 测试优惠券是否能正常使用和分摊
5. **价格计算**: 确认总价、优惠、实付金额都正确
6. **订单创建**: 确认订单和订单项都正确创建
7. **取件码**: 确认取件码正确保存到订单项

## 注意事项

1. **兼容性**: 所有修改都保持了向后兼容，不影响原有的家政服务业务
2. **数据校验**: 前端已做基本校验，后端会进一步校验数据完整性
3. **价格计算**: 跑腿业务使用前端传递的价格，不使用城市策略价格
4. **优惠分摊**: 优惠金额会按照各包裹的价格比例自动分摊
5. **事务处理**: 订单创建使用数据库事务，保证数据一致性

## 常见问题

### Q: 为什么需要传递 sku_id 和 num？
A: 这两个字段是为了与原系统兼容，用于查询商品信息和计算优惠。

### Q: 优惠券如何分摊到各个包裹？
A: 系统会根据各包裹的价格比例，自动将优惠金额分摊到每个订单项。

### Q: 跑腿业务需要地址吗？
A: **需要！** 跑腿业务需要收货地址，因为骑手需要知道把包裹送到哪里。每个包裹有取件码（用于取件），收货地址用于配送。

### Q: 如何扩展支持更多跑腿业务类型？
A: 只需要在商品管理中添加新的 SKU（如"顺丰｜小件"、"中通｜大件"等），前端会自动显示。
