# ERP 功能重构方案 · 设备流转主线与模式感知

> 版本 v1 · 2026-06 · 主导：技术侧
> 配套阅读：《ERP_V1 产品与技术规格》《插件独立与集成架构》《二手机流转·操作事件脊柱·KPI架构方案》
> 一句话：把 ERP 从"按功能切成 6 个平级菜单"重构成"一条按设备流转组织的主线"，并让它能感知中台是否接入、自动调整形态——既像一个顺手的产品，又不破坏独立可用。

---

## 1. 为什么要重构

ERP 是这套系统的"账与货"中枢，使用频率最高、最该顺手。但当前形态有三个产品级问题：

1. **按"功能"建菜单，不按"流程"组织。** 一台机器的真实路径是：入库 → 判整备 →〔整备〕→ 交中台拍照定价 → 可售 → 售出。可现在它被切成「入库工作台 / 整备工作台 / 设备库存 / 销售定价」四个平级菜单，店员要在菜单间来回跳才能把一台机器往下推。
2. **功能重叠、入口含糊。** 「设备库存」里又有"手工建档入库、确认入库"，与「入库工作台」职责重叠；用户分不清该从哪进。
3. **联合模式下"销售定价"冗余且误导。** 中台的职责就是拍照 + 定销售参考价；ERP 与中台打通后，定价应由中台完成，ERP 不该再出现一个"销售定价"入口让人以为要在这里定。

目标：**主线唯一、动作就地、形态随模式自适应。**

---

## 2. 设计原则（产品思维）

1. **一条主线**：以"设备流转"为中心组织界面，用户在一个工作台顺着阶段把机器推到底，而不是在菜单间找功能。
2. **动作就地**：每台设备在当前阶段，只暴露"此刻该做的那一个主动作"（确认入库 / 发起整备 / 完工 / 上架…），次要操作收进"更多"。
3. **模式感知**：ERP 能判断中台是否接入，并据此改变形态——
   - 接入中台：拍照、销售定价交给中台，ERP 隐藏自身定价入口，只显示"已交中台·进度 + 参考价"。
   - 独立运行：ERP 保留自身的销售（参考）定价路径，全流程自洽。
4. **独立可用不被破坏**：所有"协作态"（待拍照、中台进度、中台参考价）都是**旁路信息**，中台不在时它们为空，ERP 主状态机照常运转。
5. **参考价 ≠ 成交价**：ERP 价、中台价都是**参考价**；真实成交价只在销售环节产生。系统不强求"唯一价"，而是记录每个价的来源与阶段。
6. **契约解耦**：跨插件只发标准事件、只读自己的表；要展示别人的状态就订阅事件、在自己表里存镜像。

## 3. 用户与日常任务（Job To Be Done）

| 角色 | 每天主要在做 | 关心什么 |
|---|---|---|
| 入库员 | 收货、核来货价/型号/成色、确认入库 | 今天有哪些待入库、确认要几步 |
| 整备员 | 接整备单、整备、完工 | 我手上有哪些待整备/整备中 |
| 运营（中台） | 拍照、定销售参考价 | 哪些已交中台待拍照、待定价 |
| 销售 | 把可售机器卖出、记成交 | 哪些可售、卖了多少（成交价） |
| 财务 | 成本、对账 | 单机成本、账实是否一致 |
| 店长 | 看周转、毛利、卡点 | 货卡在哪个阶段、积压多少 |

**洞察**：除财务/对账外，所有角色的日常都是"在设备流转的某一段上推进设备"。所以主线工作台 + 阶段筛选，天然贴合所有人的日常。

## 4. 目标信息架构（前后对比）

**现状（6 个平级 + 账实校验）**

```
二手机 ERP
├─ 账实校验
├─ 往来单位
├─ 仓库与库位
├─ 入库工作台
├─ 整备工作台
├─ 设备库存
└─ 销售定价
```

**重构后（主线唯一 + 配置/对账归组）**

```
二手机 ERP
├─ 设备流转          ← 主工作台(唯一主线,含全部阶段与就地动作)
├─ 销售定价          ← 仅"独立模式"显示;接入中台时自动隐藏
├─ 基础配置
│   ├─ 仓库与库位
│   └─ 往来单位
└─ 对账校验          ← 财务角色
```

顶层从 6 个平铺 → 4 个、主线唯一。「入库工作台 / 整备工作台 / 设备库存」三者合并进「设备流转」；「手工建档入库」作为流转页上的一个"新增"动作，不再单列。

## 5. 核心：设备流转工作台

整个重构的"心脏"。一个页面，列出全部设备，顶部按阶段分页签筛选，每行就地给出当前阶段的主动作。

### 5.1 阶段分页签（与标准生命周期阶段对齐）

```
待入库 │ 待整备 │ 整备中 │ 已交中台 │ 可售 │ 已售 │ 全部
```

> "已交中台"页签仅在接入中台时出现；独立模式下该段为"待销售定价"。

### 5.2 阶段 → 主动作 映射

| 阶段(ERP) | 标准阶段 | 行内主动作 | 次动作(更多) |
|---|---|---|---|
| 待入库 pending_in | 入库 | 确认入库 | 驳回、修正重提、详情 |
| 在库·待整备 in_stock(需整备) | 整备 | 发起整备 | 跳过整备、详情 |
| 整备中 refurbishing | 整备 | 整备完工 | 取消整备、改负责人、详情 |
| 已交中台 *(委托标记)* | 待拍照/拍照/待定价 | 查看中台进度 | 详情、催办 |
| 待销售定价 pending_pricing *(独立模式)* | 定价 | 销售定价 | 详情 |
| 可售 available_for_sale | 可售 | 上架/出货 | 调价(参考)、详情 |
| 已售 sold | 售出 | 查看成交 | 详情 |

要点：
- **"已交中台"不是 ERP 的核心状态**，而是一个旁路"委托标记"（见 §7）。它对齐标准阶段里的"待拍照/拍照/待定价"，但 ERP 自己不细分这三步——细分由中台负责。
- 接入中台时，"待销售定价"这一行不出现（定价不在 ERP 做）。

### 5.3 列设计（信息密度按"店长一眼看懂"取舍）

设备(型号+IMEI/SN) │ 成色 │ 当前阶段(标签) │ 在库天数 │ 来货价 │ 参考售价(来源) │ 目标仓/库位 │ 主动作

- "参考售价(来源)"标注来源：`门店预估` / `中台 ¥X` —— 让人知道这是参考、谁定的。
- "在库天数"暴露积压，服务周转 KPI。

### 5.4 批量与空态

- 支持按阶段批量推进（批量确认入库、批量发起整备）。
- 每个阶段页签空时给明确空态 + 下一步引导（沿用回收侧已统一的 AsyncState/空态规范）。

## 6. 模式感知（中台在 / 不在）

ERP 启动时探测中台是否接入（沿用现有的"插件是否安装/事件是否有应答"判断，与定价弹窗仓库探测同套机制）。

| 能力 | 独立模式(无中台) | 联合模式(有中台) |
|---|---|---|
| 拍照 | 无此环节 | 中台负责 |
| 销售定价 | ERP 自己定参考价（保留「销售定价」菜单与 pending_pricing 流转） | 中台负责；ERP 隐藏定价入口，入库后进"已交中台" |
| 入库后去向 | 在库 → 待销售定价 → 可售 | 在库 →〔整备〕→ 已交中台 →(中台定价回写)→ 可售 |
| 价格展示 | 来货价 + ERP 参考售价 | 来货价 + 中台回写的参考售价 |

**关键**：模式切换只影响"展示与入口"，不改 ERP 核心状态机；中台事件缺失时一切旁路信息为空，ERP 独立闭环。

---

## 7. 状态对齐：为什么"待拍照"不进 ERP 核心状态机

- 对**单独的 ERP**，"待拍照"没有意义——它没有拍照能力。把"待拍照"塞进 ERP 核心状态机，等于让 ERP 依赖中台，破坏独立性。
- 因此：**"待拍照/拍照/待定价"属于标准阶段词表 + 中台**（中台天生有 `wait_photo → ... → priced`）。ERP 只用一个**轻量"委托标记"**（如 `delegated_to_platform` 布尔/旁路态）表达"我把它交出去了"，并在流转页显示成"已交中台"。
- 流转：入库(无整备)或整备完工 → 打"已交中台"标记 + 发 `erp.asset.ready_for_photo.v1`；中台 `device_asset.price.completed.v1` 回来 → 清标记 + 写入中台参考价 + 转"可售"。
- 收益：ERP 核心状态机不认识拍照，单跑正常；联合时用一个标记呼应标准阶段，足够且不耦合。

> 这是"核心归核心、协作归协作"原则在状态层面的落地。

---

## 8. 价格模型：参考价时间线，成交价唯一真实

- **来货价(ERP)**：入库时门店填，单机成本基准。
- **ERP 参考售价**：独立模式下门店预估的卖价——参考。
- **中台参考售价**：拍照后运营定的卖价——参考；通过事件回写到 ERP 的"参考售价"字段（不覆盖来货价）。
- **实际成交价**：只在销售环节(未来 shop/销售模块)产生，是唯一真实价。

建模：把价格当作**带来源的时间线**（谁、哪个阶段、定了多少），与"操作事件脊柱"同源。界面展示"最新参考价 + 来源标注"；只有成交事件产生的价标记为"实际成交价"。**系统不选"唯一为准"的价，而是让每个价各归其位。**

## 9. 分阶段落地（每阶段独立可交付、可验收、低风险）

- **P1 · 合并主线**：新建「设备流转」工作台，把入库/整备/库存三个工作台的列表与动作并进来（阶段页签 + 就地主动作）。旧菜单先保留、灰度，验收后再下线。*纯前端聚合 + 复用既有接口为主。*
- **P2 · 模式感知**：探测中台接入；联合模式隐藏「销售定价」、入库后进"已交中台"、显示中台进度与参考价；独立模式维持原样。引入"委托标记"旁路态。
- **P3 · 价格来源标注**：参考售价标来源（门店/中台），中台回写写入参考字段；为未来成交价留位。
- **P4 · 配置归组 + 旧菜单下线**：仓库/往来单位/对账归到「基础配置/对账」；确认无回归后移除已合并的旧入口。

每个阶段都不破坏 ERP 独立运行，且可单独回滚。

---

## 10. 边界红线（始终遵守）

- 不引用回收/中台的 PHP 类、模型、数据表；跨插件只发标准事件、只读自己的表。
- 不碰 niucloud 核心框架；ERP 重构只在 `addon/hsx_erp` 内完成。
- 状态/价格的"协作信息"一律旁路化，中台缺席时为空，不影响核心。
- 已确认的库存/成本只追加反向流水，不物理删除（沿用 V1 规格）。

---

## 11. 验收要点

1. 独立安装 ERP：无中台时，设备流转走 在库→待销售定价→可售→已售，「销售定价」可用，全程无"已交中台/待拍照"字样。
2. 联合安装：入库(无整备)后设备进入"已交中台"，「销售定价」菜单消失；中台定价回来后自动转"可售"并显示中台参考价。
3. 需整备设备：入库后进"待整备/整备中"，完工后才进"已交中台"，不提前进拍照。
4. 顶层菜单从 6 → 4，主线唯一；店员完成一台机器全流程无需跳菜单。
5. 价格处处标注来源；无任何界面把参考价当作"实际成交价"。
