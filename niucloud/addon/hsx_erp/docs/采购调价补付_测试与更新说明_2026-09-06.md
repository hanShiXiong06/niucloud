# 回收／采购调价与差额补付：测试及更新说明

日期：2026-09-06。范围：ERP 管理端、后台管理小程序、ERP 与回收插件的采购调价／付款回写。

## 交付结果

继续使用「库存设备 → 成本调整 → 回收／采购调价」和原来的「应付款 → 付款」入口，不要求另找一个补款模块。

例：原采购价 4600，已付 4600，协商补价 100：

| 时点 | 当前应付总额 | 累计已付／折账 | 剩余待付 | 本次资金流水 |
| --- | ---: | ---: | ---: | ---: |
| 调价前 | 4600 | 4600 | 0 | 不变 |
| 保存调价后 | 4700 | 4600 | 100 | 0 |
| 财务先补 50 | 4700 | 4650 | 50 | 50 |
| 财务再补 50 | 4700 | 4700 | 0 | 50 |

原 4600 的结算与流水保留。调价写独立的成本调整台账，但不另生成重复采购应付，不自动转账。原应付重新具备待付余额；PC 与移动端付款界面显示总额、已付、待付、本次付款，并可查看补付历史、最近调价原因。

成本调整输入框仍是「设备总成本」。已有整备费用不会被当作客户采购款：例如设备总成本 4800，需另补采购价 100，输入 4900。本次采购应付只增加差额 100。两端已增加说明，移动端默认选择回收／采购调价。

## 数据库与边界

- **本次没有新增表、字段、升级 SQL，也没有执行数据库结构变更。**
- 复用现有 `erp_payable` 的当前应付和累计结算、`erp_asset_ledger.extra_json` 的调价快照、回收设备与付款／日志表。
- 回收设备 `final_price` 跟随真实采购本金变化；`pay_amount` 保存累计已结算；每条付款记录的 `amount` 只记录本次结算金额。
- ERP 和本地回收插件在同一数据库事务中确认调价；缺少回执、归属不明确、两边原价格／已付金额不一致时拒绝保存。结算回写沿用 ERP 可重试发件箱；按站点、设备、结算单号幂等处理。
- 已经完成的回收订单补价后可显示部分付款，但不倒退业务完结状态，也不重写原完成时间。
- 同一调价请求重复提交不再次加价；同一请求换金额／设备／类型会被拒绝。结算重复通知不增加流水，旧事件不能倒退累计金额。
- 本次不是银行自动付款功能。财务仍按现有方式转款，再确认付款。

以下仍会明确拦截，并非无条件放开所有调价：

1. 降价后低于已付金额，需要收回退差款。本版不新增采购退差款工作流，不会把原付款抹掉或者假装已退款。
2. 已售、退货等不允许调整采购成本的设备，沿用原业务状态限制。
3. 历史整单应付已经有结算、又无法确定单台实际已付金额时，不按比例猜测后开放补款；需先核对设备级原账。
4. 回收／ERP 关联或历史付款不一致时先核账。不能关闭 ERP 后换回收入口再次支付同一笔款。

## 实测结果

### 本地真实数据库事务测试：55 个断言通过

脚本：`niucloud/addon/hsx_erp/tests/purchase_price_adjustment_database_integration.php`。

只允许显式开启且数据库地址为 localhost／127.0.0.1，运行前检查涉及表支持 InnoDB 事务。仅创建新的测试记录，最后回滚并验证原记录、附加流水／台账／回收日志不存在。没有改已有客户订单，没有触发外部转账、通知派发或生产操作。

已验证：

- 4600 已付清后增加 100，ERP 与回收价格、已付、剩余金额正确；原应付 ID 不变。
- 调价只生成调整记录，不增加资金流水。
- 同请求重试，包括移动端／PC 提交的目标成本形式，不重复调价。
- 同请求不同金额、过期成本快照被拒绝。
- 调用实际应付明细查询服务，返回 4700／4600／100，并含调价金额和原因。
- 调用实际 ERP 付款服务，分两次各补 50；从实际发件箱读取事件交给回收消费者。
- ERP 与回收累计已付依次为 4650、4700；每次回收付款记录仅 50；账户仅减少 100。
- 实际应付查询能够读到两条补付历史。
- 重复回写不再插入付款记录，原 4600 付款记录未改变。
- 全额付清后继续付款被拒绝；低于已付的降价被拒绝。
- 模拟回收调价监听缺失，ERP／回收均未保存半成品。
- 再次加价仍使用原应付；旧结算重放不覆盖新价。
- 同设备在一个结算事件里出现多份采购快照时拒绝处理，避免覆盖混算。

## 手动更新与验证顺序

1. 备份相应文件。此功能依赖同一版本的「付款归属与切换保护」服务，不能只更新一两个 Service 文件。若上一版未部署，先对照回收插件文档 `回收ERP付款归属与切换保护_测试和更新说明_2026-09-06.md` 核对依赖。
2. 在短暂维护窗口暂停相关调价／付款操作，同批更新 ERP 与回收的 11 个后端文件；不需要执行 SQL。
3. 按部署环境刷新应用事件缓存、PHP OPcache，并重启常驻队列，使调价监听与结算消费者使用同一版代码。不要删除运行中的业务资料或数据库文件。
4. PC 管理端重新打包发布；后台管理小程序重新打包体验／审核发布。客户销售端小程序无需因本次功能单独更新。
5. 选取测试设备走「调价 → 原应付补付 → 两边核对」。至少检查总额、已付、待付、调价记录、本次流水、原付款记录，核对无重复支出再恢复使用。

如需回退：先暂停新增调价和付款，不能直接把旧的“已付后不能调价／只处理全额回写”代码覆盖回去。应先核对新产生的部分付款和未消费事件，确认旧版兼容后再回退对应代码；不要删除已经形成的真实财务流水。
