# 应付与结算契约 · 财务插件接入预留

> 版本 v1 · 2026-06 · 主导：技术侧 · 状态：**契约预留，暂不实现**
> 配套阅读：《插件独立与集成架构》《ERP_V1 产品与技术规格》《二手机流转·操作事件脊柱·KPI架构方案》
> 目的：把"应付 / 应收 / 结算（现金·折账）/ 财务边界"的目标语义先定死。**现在不改代码**，等财务插件落地时按此接入，避免返工。

---

## 1. 为什么要先定这份契约

折账这类需求暴露了一个根问题：**当前"打款"把两件事揉在了一起**——既表示"我欠客户多少（应付）"，又表示"我用现金把它付掉了（结算）"。一旦引入折账，这两件事必须拆开，否则财务做不了净额冲抵。

提前把语义定好，财务插件一来就能直接接，不用回头改回收/销售的事件。

---

## 2. 一个例子说清折账

- 客户 A 给我一台机（回收）值 4000 → **我应付 A 4000**。
- A 又从我这买一台机值 5000 → **A 应收（欠我）5000**。
- 折账：不必"我给 A 4000、A 给我 5000"，而是 **A 净付我 1000**，那 4000 与 5000 中的 4000 对冲平掉。

**关键**：`应付 A 4000` 来自**回收**，`应收 A 5000` 来自**销售**。只有**财务层**能同时看到同一往来单位 A 的应收与应付，所以**折账只能在财务插件做**。

---

## 3. 核心模型：业务出"事实"，财务做"结算"

把"打款"拆成两层语义：

1. **应付 / 应收（业务事实，由业务插件产出）**
   - 回收确认 → 产生「应付客户 X」（往来单位=客户，金额=回收价）。
   - 销售成交 → 产生「应收客户 X」（往来单位=客户，金额=售价）。

2. **结算（由财务处理，带"方式"）**
   - 现金打款（给客户转钱）
   - **折账**（拿同一往来单位的应收冲抵应付，净额结算）
   - 混合（部分现金 + 部分折账）

> "打款"只是结算方式之一（现金）。折账是另一种。**结算永远针对"应付/应收"这些事实，且以往来单位为锚。**

---

## 4. 事件契约（预留，财务插件落地时实现）

以下事件名 / payload 为**目标契约**，遵循 `.vN` 版本化 + `event_id` 幂等 + 往来单位为锚的统一约定。

### 4.1 应付产生（回收 → 财务）

- 事件：`finance.payable.created.v1`
- 触发：回收确认回收 / 定价确认
- payload（要点）：`counterparty`(往来单位)、`amount`、`source`(回收单/设备身份)、`occurred_at`

### 4.2 应收产生（销售 → 财务）

- 事件：`finance.receivable.created.v1`
- 触发：销售成交
- payload（要点）：`counterparty`、`amount`、`source`(销售单/设备身份)、`occurred_at`

### 4.3 结算完成（财务 → 业务/ERP）

- 事件：`finance.settlement.completed.v1`
- 触发：财务对一/多条应付应收做结算
- payload（要点）：
  - `counterparty`
  - `method`：`cash`(现金) / `offset`(折账) / `mixed`(混合)
  - `cash_amount`、`offset_amount`
  - `linked`：被结算的应付/应收清单（折账时给出"应付 X 冲抵应收 Y"的明细）
  - `operator`、`occurred_at`、`event_id`
- **折账 = `method=offset` 的结算**：用同一往来单位的应收抵应付。

> 业务/ERP 订阅结算事件，更新各自的"结算状态/付款留痕"展示；不自己算钱。

---

## 5. 两种模式（与"模式感知"一致）

| 能力 | 独立模式（无财务插件） | 集成模式（有财务插件） |
|---|---|---|
| 应付/应收 | 回收/销售自己记一笔，简单 | 回收/销售发 `payable/receivable.created` 事件 |
| 结算 | 回收"打款" = 直接现金结清，无折账 | 财务统一结算，可现金 / 折账 / 混合 |
| 回收"打款"动作 | 保留：现金结清 | 退化为"已由财务结算"的状态展示 |
| 折账 | 不支持（也不需要） | 财务做净额冲抵 |

---

## 6. 现状与迁移路径

- **现状（财务插件未落地）**：维持回收的现金打款 + 事件同步到 ERP 记账。**不动**，避免拆掉现有可用流程与打款 KPI。
- **迁移（财务插件落地时）**：
  1. 回收"确认回收/定价" → 增发 `finance.payable.created.v1`。
  2. 回收"打款" → 改/增发 `finance.settlement.completed.v1(method=cash)`；集成模式下该动作交财务。
  3. 财务实现 `offset` 折账：按往来单位净额冲抵应付↔应收。
  4. 打款 KPI 口径由"现金打款"升级为"结算完成"（含折账），保持可考核。
- **兼容**：迁移期保留旧"打款"语义，新事件并行灰度，验证后再切换。

---

## 7. 边界红线

- **财务是独立插件**：负责往来单位、应收、应付、收付款、折账；ERP 只出"成本/利润/进销存事实"。
- **折账只在财务**：业务插件不做净额冲抵（看不全往来单位两侧）。
- **往来单位为锚**：应付、应收、结算、折账全部挂在往来单位上对齐。
- **事件驱动、不跨插件读表**；`.vN` + `event_id` 幂等。

---

## 8. 下一步

本契约**暂不实现**，作为财务插件的接入基准。财务插件启动时：先按 §4 落 `payable/receivable/settlement` 三个事件，再实现 §4.3 的 `offset` 折账，最后按 §6 迁移回收"打款"语义。

## 9. 打款即折账入口(回收侧)— 设计已定，待商城应收落地后实施

> 背景：财务已合并进 ERP 的"财务中心"。打款是"财务把钱给客户"的动作，发生在**回收**插件，正是做折账最自然的时机。
> 红线不变：回收**不读写**财务表，只通过"一问一答"事件与财务中心交互；ERP/财务缺席时优雅降级为普通现金全额打款。

### 9.1 一句话
回收打款时，先查这个客户的往来账（他是否也欠我钱），能抵就抵，**只打净额现金**。

### 9.2 两个解耦接口（财务侧已实现）

1. **查往来账（只读）** — 事件 `GetFinanceCounterpartyBalance`
   - 入参：`{site_id, counterparty_id}`
   - 出参：`{payable(我欠他), receivable(他欠我), offsetable(可折账=min), can_offset, net(>0我净付/<0我净收), net_direction}`
   - 站在我方视角，回收看到的 `payable` 为正即"我欠他"，`offsetable>0` 即可折让。
   - 同口径 admin 接口（便于测试）：`GET erp/finance/counterparty_balance?counterparty_id=`

2. **折账结算指令（写）** — 事件 `RequestFinanceSettlement`
   - 入参：`{counterparty_id, remark}`
   - 行为：把该客户**全部未结**应付/应收折账冲抵、余额走现金净额，经**唯一结算服务** `FinanceSettlementService::settleAllByCounterparty()` 执行（与财务中心手动折账同一条路，绝不重复记账）。
   - 出参：`{ok, summary{offset_amount, cash_amount, cash_direction, method}, settlement_no}`

### 9.3 回收侧打款流程（待实施）

1. 打开打款页 → 发 `GetFinanceCounterpartyBalance` 查账（class_exists 守卫；无财务则跳过）。
2. 若 `can_offset`：提示"本次应付 X；该客户还欠你 Y → 可折账 min(X,Y)，**实际只需打款 net**"。
3. 操作人确认折账打款 → 发 `RequestFinanceSettlement`；成功后回收记打款"实付 net（折账抵了 offsetable）"。
4. 财务中心两侧账随之结清，并回发 `finance.settlement.completed.v1` 供各方更新展示。

### 9.4 待你拍板的三点
- **打款 KPI 口径**：折账后现金=净额。KPI 按"现金净额"还是"应付总额"统计？
- **结算唯一出口**：回收打款与财务中心折账都只走 `FinanceSettlementService`（已如此设计）。
- **前置依赖**：需商城产出"应收"事件；在此之前回收打款=普通全额现金，无折账。

### 9.5 当前进度
- 财务侧两接口（查账事件 + 折账指令事件 + 同口径 admin 接口）**已实现**。
- 回收侧打款 UI/触发**未接**——与商城应收来源、应付生产者一起接，避免半套上线。

## 10. 商城对接契约(应收来源)— 现在定死，商城二次开发照此做

> 商城目前是通用电商，需二次开发后才接。**先把契约定死**，二次开发朝这个目标做，做完即可接，不返工。

### 10.1 往来单位锚(命门，先定)
折账按"往来单位"对齐两侧。个人客户场景：

- **往来单位锚 = member_id(会员ID)**。
- 回收侧：应付的 `counterparty_id = 回收客户的 member_id`(**已实现**)。
- 商城侧：应收的 `counterparty_id` 必须 = **同一个买家的 member_id**。
- 只有两侧 member_id 一致，老王"卖机的应付"和"买机的应收"才挂在同一往来单位上，才折得起来。
- (企业/同行往来用 erp_counterparty，是另一套，不在此 C 端折账范围。)

### 10.2 应收事件(商城 → 财务)
- 通道：`FinanceReceivableCreated`，契约名 `finance.receivable.created.v1`
- 触发：**订单支付完成/履约完成**(以订单为最小颗粒度，一单一笔；多机一单则金额为整单)
- payload：
  - `event_id`：幂等键，建议 `mall_receivable_{order_id}`
  - `site_id`
  - `counterparty_id`：买家 member_id(与回收同锚)
  - `counterparty_name`：买家名(快照)
  - `amount`：订单应收金额
  - `source_type`：`mall_order`
  - `source_no`：订单号(回收侧要据此显示"关联了哪个订单")
  - `source_device_id`：若该订单卖的是有串号的整机，带上设备ID(可精确到机)
  - `occurred_at`
- 财务侧监听已就位(`ReceivableCreatedListener`)，幂等落库，无需改财务代码。

### 10.3 多订单合并 / 可追溯(数据已支持)
- 每笔应收带 `source_no`(订单号)、可带 `source_device_id`(机)。回收侧"查待结应收"接口逐笔返回，天然能列出 A/B/C 订单。
- 一次结算可选多笔应收，结算明细表逐笔记录核销金额/折账/现金。"A+B+C=1万，再付1000"可算可列。
- 回收侧打款页展示多订单合并、净额——属 §9.3 待实施 UI，等商城应收能产出后接。

### 10.4 二次开发自检清单(商城侧)
1. 订单能确定唯一买家，且买家 = 平台 member(拿得到 member_id)。
2. 有明确的"订单完成"时机可挂事件。
3. 订单号、金额稳定可取；整机订单能关联到设备身份(可选但推荐)。
4. 在订单完成处 `event('FinanceReceivableCreated', payload)`，故障隔离(失败不影响下单)。
做到这四点，应收就接通了，折账闭环成立。
