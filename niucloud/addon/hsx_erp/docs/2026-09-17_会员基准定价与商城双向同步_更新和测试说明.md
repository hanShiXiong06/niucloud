# ERP 与商城双向改价、会员自动加价：使用、更新和测试说明

日期：2026-09-17

状态：本地功能已实现；价格规则、真实本地数据库联动和隔离页面验收通过。没有部署线上，没有进行真实支付或微信小程序真机成交测试。

## 一、这次确认的唯一价格口径

员工只填一个价格：**基准售价 = 最低销售价格 = 本站最高等级会员价格（同行价）**。

它不是采购成本，也不是加价后的普通售价。开启自动加价后，ERP 的拍照定价、商品新增/编辑、列表改价、商城交接共用这个口径。

例如只有 V1 时：

| 身份 | 规则 | 基准 2000 元时实际售价 |
| --- | --- | --- |
| V1 | 基准，不加价 | 2000 元 |
| 普通客户（无会员等级） | 固定加 200 元 | 2200 元 |

有 V1、V2、V3 时，以成长值门槛最高的等级为基准，而不是按数据库 ID 或等级创建顺序判断。例如 V3=2000、V2=2050、V1=2100、普通=2200。

所有加价都从同一个基准算，不是在上次普通售价上继续加。重复保存 2000 元不会变成 2400、2600 元。

## 二、管理员如何配置

入口：**手机商城 → 会员加价规则**。

页面地址：`/site/phone_shop/goods/price_rules`。

1. 在本站会员等级里确认已启用的等级。只有 V1 时选择 V1 为基准。
2. 打开“自动加价”（默认关闭）。
3. 分别设置普通客户、其他会员等级的加价；基准等级固定不加价。
4. 可以选择固定金额或百分比。例如 +200 元，或 +10%。
5. 需要分价段时展开“按基准价区间设置”：区间含下限、不含上限，上限留空表示不限；未命中区间使用默认加价。
6. 保存后使用“已保存规则试算”检查结果，再通知员工按一个基准价录入。

区间示例：1000～3000 元 +200，3000 元以上 +300；2000→2200，3000→3300。

保护规则：

- 同一身份的区间不允许重叠。
- 不允许负数、无效数值或超出金额范围。
- 保存具体商品时，不允许普通客户价格低于会员，或高等级会员反而更贵；会明确指出冲突身份。
- 修改/停用会员等级导致已选基准不再有效时，会要求重新配置，不猜测替换。
- 配置加载失败时禁止保存，避免把空白默认规则覆盖真实配置。
- “保存规则”是独立权限；定价人员可以读取规则和试算，不需要拿到修改规则的权限。

**保存规则不会批量重算历史商品**，也不会追改已经成交的订单。新建、之后的改价按当时的规则执行。关闭开关后恢复手动定价，已保存的商品价格不会自动撤销。

## 三、员工操作

### ERP 拍照定价 / 库存改价

只填写“基准售价”，页面显示普通客户及会员价格预览。保存时后端重新计算，不依赖前端预览是否及时返回。

已有同站商城关联商品时，同步普通售价、会员价和交接货源价格；未建品的交接货源也更新，避免运营后续拿到旧价。

### 商城新增、编辑、列表改价

开启规则后显示基准售价和自动计算结果，手动会员价入口会提示价格已由规则管理。多规格分别维护各自基准。

已绑定 ERP 设备时，改价同时更新 ERP 的同行基准及普通售价。

没有明确基准的旧商品，不把普通售价自动当作最低价；要求先确认基准，避免重复加价。主动清空价格会报必填错误，不会悄悄沿用旧价。

### 商城交接 / 资料后补

复用上一轮“先上架，运营后补”链路。价格按统一服务计算，不在交接时另算一套。

“先上架”模式继续由 ERP 定价，运营完善照片说明、颜色、电池、保修等细节，不允许在交接表单偷偷改掉 ERP 已确认的价格；需要改价用标准价格入口。

### 批量导入

批量导入走同一个商品新增服务：

- 开启自动加价：优先把导入文件“同行价”作为基准；同行价留空时用“售价”作为基准。
- 未开启：保持原本的普通售价与手动同行会员价。
- 模板与导入弹窗已提示这一区别。不要把已加价的普通售价当作基准重复导入。
- 规则以导入任务实际执行时的本站配置为准；不要在同一批导入运行中来回切换定价规则。

从站跟随仍保持既有代理加价逻辑；主站自己的会员定价快照不会拷贝为从站基准。本次没有改造成跨站统一会员等级定价。

## 四、双向同步的安全边界

同步必须同时满足：**同站点、已有 ERP 资产关联、完整 IMEI/SN 一致、设备在库**。不靠后六位串号猜机器，不新增采购单或库存资产。

| 情况 | 结果 |
| --- | --- |
| ERP 调整基准价 | 商城商品和交接货源更新，会员价格重算 |
| 商城调整基准价 | ERP 同行基准及普通售价更新，记录设备流水 |
| 同样价格重复保存 | 不累计加价，不重复改变订单金额 |
| 串号不一致、关联资产不存在 | 提示具体原因，当前价格事务回滚 |
| ERP 配套监听器未响应 | 不显示假成功，要求更新配套插件 |
| 设备已离库 / 已售 | 阻止库存售价回写，不改变已有订单 |
| 营销活动中的商品调价 | 阻止修改，要求先结束活动 |
| 活动商品只保存未变化的价格 | 保留原活动销售价 |
| 代理商品错误关联 ERP | 阻止修改来源站点资产 |
| 自动加价关闭 | 不批量撤销价格，后续按手动规则执行 |

不修改采购成本、应收应付、已支付金额、订单价格、库存数量和商品上下架状态。价格同步不等于重新上架。

## 五、数据库与框架边界

本次**没有新增表、字段或 SQL 升级文件，没有改公共框架**。

复用：

- 站点配置保存开关和加价规则。
- 商城现有 `member_level.level_no` 区分本站等级。
- SKU 现有 `member_price` 保存各等级售价。
- SKU 现有 `device_snapshot._tier_pricing` 保存基准价，不覆盖质检快照。
- ERP 现有 `estimate_sale_price` 保存同行基准，`retail_price` 保存普通售价。

现有商城会员等级初始化机制保持不变；本功能不是给缺少基础会员等级字段的旧安装包做数据库迁移。

两个插件通过插件事件对接；没有在公共支付、会员模型或框架路由中硬编码业务逻辑。

1. 备份本次将替换的文件和当前站点配置；确认线上两个插件是配套版本。

6. 在测试站点设置 V1 基准、普通 +200：分别从 ERP 和商城改一台测试设备，检查两个后台、小程序身份价和交接货源一致。
7. 再启用目标站点。不要在真实客户未确认的情况下用真实订单测试支付。

已有规则关闭但商品保留自动计算的价格，是有意设计；关闭不是历史价格回滚。
