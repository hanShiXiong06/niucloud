# hsx_query_phone 功能规划

## 一、产品定位

`hsx_query_phone` 是一个独立的查机应用，面向 IMEI / SN / 序列号查询场景。

核心目标：

- 支持 3023 查询通道
- 支持爱查查询通道
- 查询通道由后台开启和指定，用户端不提供渠道切换
- 支持后台配置查询服务和售价
- 用户端支持花钱查和积分查
- 支持可配置短时间缓存，默认 24 小时
- 查询成功扣余额/积分，查询失败自动原路退回
- 查询结束后通过 niucloud notice 发送结果通知
- 后台清晰展示查询记录、成本、收入、利润和失败原因

本应用不负责充值套餐、充值赠送、微信支付和会员折扣，这些交给 niucloud 现有会员充值模块。

## 二、关键取舍

| 功能 | 是否做 | 说明 |
|---|---:|---|
| 3023 查询 | 做 | 作为第一供应商之一 |
| 爱查查询 | 做 | 作为第二供应商之一 |
| 前台切换渠道 | 不做 | 用户只看到后台当前启用渠道下的查询项目 |
| 查询缓存 | 做短缓存 | 默认 24 小时，可按服务配置是否启用 |
| 花钱查 | 做 | 调用 niucloud 框架支付组件，用户在弹窗内选择余额、微信等支付方式 |
| 积分查 | 做 | 已有用户在使用积分，直接校验积分并查询 |
| 微信支付 | 不做 | 用户先去会员充值，查询时扣余额 |
| 充值入口 | 做 | 只做跳转入口，不做充值业务 |
| 会员等级折扣 | 不做 | 与充值赠送让利重复，第一版不叠加 |
| 邀请送积分 | 不做 | 框架没有现成能力，先不开发 |
| 查询失败退款 | 做 | 接口失败必须原路退回余额或积分 |
| 成本/利润统计 | 做 | 后台必须能看懂每笔成本、现金收益和积分折算收益 |

## 四、用户端流程

### 正常查询

```text
选择查询服务
↓
输入 IMEI / SN / 序列号
↓
系统显示价格和当前余额
↓
选择花钱查或积分查
↓
花钱查：调用框架支付组件；积分查：检查积分
↓
支付成功或积分扣除成功
↓
优先检查 24 小时缓存
↓
缓存命中：直接生成本次查询记录并返回结果
↓
缓存未命中：调用 3023 / 爱查接口
↓
接口成功：保存报告，展示结果
↓
发送查询完成通知
↓
接口失败：保存失败记录，原路退回余额或积分
↓
发送查询失败通知
```

### 余额不足

```text
点击查询
↓
余额不足
↓
弹窗提示当前余额和本次查询价格
↓
如果后台开启充值入口，显示“去充值”
↓
跳转 niucloud 会员充值首页
```

### 查询记录筛选

用户端查询记录页沿用现有 `history.vue` 交互：

| 筛选项 | 说明 |
|---|---|
| 关键词搜索 | 搜索序列号 / IMEI |
| 分类筛选 | 选择全部分类或某个查询项目分类 |
| 时间筛选 | 全部时间 / 最近7天 / 最近30天 / 最近90天 |
| 加载方式 | 下拉刷新、触底加载更多 |
| 记录点击 | 进入查询详情页 |

## 六、支付与缓存规则

### 支付方式

第一版前台支持两种查询方式：

| 查询方式 | 说明 |
|---|---|
| 花钱查 | 先创建查询支付单，再调用 niucloud 框架支付组件，由组件内选择余额、微信等支付方式 |
| 积分查 | 不调用支付组件，直接检查并扣除会员积分，积分不足时提示积分不足 |

后台配置：

| 配置项 | 字段建议 | 默认值 | 说明 |
|---|---|---|---|
| 开启花钱查 | `money_pay_status` | 1 | 关闭后用户端不显示花钱查 |
| 开启积分查 | `point_pay_status` | 1 | 关闭后用户端不显示积分查 |
| 积分兑换比例 | `point_exchange_rate` | 100 | 例如 100 积分 = 1 元 |
| 积分支付说明 | `point_pay_desc` | 100积分=1元 | 用户端展示文案 |

查询服务配置：

| 字段 | 说明 |
|---|---|
| `support_money_pay` | 是否支持花钱查 |
| `support_point_pay` | 是否支持积分查 |
| `point_price` | 积分价格，默认按售价乘兑换比例 |

高成本查询服务可以关闭积分支付，避免积分消耗覆盖不了第三方接口成本。

### 短缓存规则

缓存只做短时间防重复查询，默认 24 小时。

| 规则 | 说明 |
|---|---|
| 缓存维度 | `site_id + query_code + service_id` |
| 默认缓存时间 | 24 小时 |
| 是否可关闭 | 全局可关，单个服务也可关 |
| 缓存来源 | 只使用成功查询结果 |
| 失败结果 | 不缓存 |
| 命中缓存是否生成记录 | 生成新的查询记录 |
| 命中缓存是否扣用户费用 | 建议仍按服务售价扣费 |
| 命中缓存第三方成本 | 记为 0 |
| 命中缓存利润 | 用户支付金额 - 0 |

为什么缓存命中仍然扣费：用户购买的是查询报告服务，不是第三方接口调用本身；短缓存可以降低接口成本，同时避免同一用户或不同用户短时间重复查询造成成本浪费。

后台必须标识 `from_cache`，让运营知道这笔订单是否来自缓存。

## 七、渠道展示与通知规则

### 前台渠道规则

用户端不展示 3023 / 爱查切换入口。

| 规则 | 说明 |
|---|---|
| 渠道选择 | 后台配置当前启用渠道 |
| 用户端展示 | 只展示当前渠道下已启用的查询服务 |
| 多渠道同时启用 | 后台可以启用多个渠道，但用户端默认只展示当前默认渠道 |
| 服务名称 | 用户端展示业务名称，例如“苹果高级验机”，不强调供应商名称 |
| 后台记录 | 后台必须记录实际供应商，便于成本和失败率统计 |

如果后续要做“备用渠道”，也只在后台自动切换，不给用户手动选择。

### 查询结束通知

查询完成后使用 niucloud 框架 notice 能力发送通知。

| 通知类型 | 触发时机 | 内容 |
|---|---|---|
| 查询成功通知 | 实时查询成功或缓存命中成功 | 查询项目、查询码、支付方式、查看详情入口 |
| 查询失败通知 | 第三方接口失败并完成退款 | 查询项目、查询码、失败原因、退款结果 |

通知发送原则：

- 查询成功后再发成功通知
- 查询失败且退款完成后再发失败通知
- 缓存命中也算查询成功，需要发送成功通知
- 通知里不展示第三方原始响应，只给用户查看报告入口
- 后台记录通知发送状态，便于排查用户没收到通知的问题

建议在查询记录表增加：

| 字段 | 说明 |
|---|---|
| `notice_status` | 通知状态：未发送 / 已发送 / 发送失败 |
| `notice_time` | 通知发送时间 |
| `notice_error` | 通知失败原因 |

## 八、后台必须好筛选、好看懂

后台要让运营一眼看懂：

- 今天查了多少次
- 成功多少次
- 失败多少次
- 用户实际支付多少
- 第三方成本多少
- 实际盈利多少
- 多少订单来自缓存
- 通知是否发送成功
- 哪个供应商失败率高
- 哪个查询服务最赚钱

### 统计卡片

| 指标 | 说明 |
|---|---|
| 总查询数 | 当前筛选条件下的查询总次数 |
| 成功查询数 | 状态为成功的记录 |
| 失败查询数 | 状态为失败/已退款的记录 |
| 成功率 | 成功数 / 总查询数 |
| 用户实付金额 | 花钱查成功订单的实付总额 |
| 积分消耗 | 成功订单扣除的积分总额 |
| 积分折算金额 | 按积分兑换比例折算的金额 |
| 第三方成本 | 成功查询的接口成本总额 |
| 现金毛利润 | 花钱查实付金额 - 花钱查订单对应成本 |
| 积分估算利润 | 积分折算金额 - 积分支付订单对应成本 |
| 缓存命中数 | 来自 24 小时缓存的成功订单数量 |
| 通知失败数 | 查询结束后 notice 发送失败的数量 |
| 退款金额 | 查询失败后退回的余额总额 |
| 退回积分 | 查询失败后退回的积分总额 |

## 十二、开发顺序建议

1. 新建 `hsx_query_phone` 应用骨架
2. 建表：配置、供应商、查询服务、查询记录
3. 后台基础设置：充值入口、花钱查、积分查、24 小时缓存、默认渠道、通知开关配置
4. 后台供应商配置：3023、爱查、默认渠道
5. 后台查询服务配置：售价、积分价、成本、供应商映射、缓存开关
6. 用户端查询首页：只展示后台默认渠道的查询服务、输入查询码、余额/积分展示、充值入口
7. 花钱查接入框架支付组件，积分查直接扣积分
8. 24 小时缓存命中逻辑
9. 3023 / 爱查供应商适配器
10. 查询成功保存报告
11. 查询失败自动原路退款
12. 查询结束后调用框架 notice 发送成功/失败通知
13. 后台查询记录：筛选、统计卡片、详情弹窗、通知状态
14. 后台数据统计：按日期、供应商、服务、支付方式、缓存来源汇总收益、成本、利润

## 十三、第一版验收标准

- 后台能配置 3023 和爱查
- 后台能指定用户端默认查询渠道
- 后台能配置查询服务售价、积分价和成本价
- 用户端能输入 IMEI / SN 查询
- 用户端不能手动切换 3023 / 爱查渠道
- 用户端支持花钱查和积分查
- 花钱查能调用框架支付组件弹窗选择余额、微信等支付方式
- 积分不足时能提示用户积分不足
- 24 小时内相同查询可命中缓存
- 缓存命中必须生成本次查询记录，并标记 `from_cache`
- 查询成功后记录现金收入、积分消耗、成本、利润
- 查询失败后自动原路退余额或积分
- 查询结束后通过框架 notice 发送成功或失败通知
- 后台能按时间、会员、供应商、服务、状态、支付方式、缓存来源、通知状态筛选
- 后台详情能看到标准化结果和第三方原始响应
