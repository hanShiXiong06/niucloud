# 设备退回批量处理闭环与测试

日期：2026-09-18。范围：`hsx_recycle` 插件。本次没有新增表、字段或 SQL，没有改框架，没有修改线上数据，也没有批量清理历史记录。

## 一、业务口径

“退回未完成 16 台”表示当前站点仍在有效退回流程中的 **设备台数**，不是 16 个订单。按设备去重，不受概览顶部日期影响。

- 待寄回：已经申请退回，但尚未登记发货。
- 待签收：商家已经发出，尚未完成。
- 已完成：人工确认客户已签收，或发出满 72 小时自动完成。
- 已取消、已删除、失效关联、其他站点设备不计入未完成台数。

计算复用现有 `CoreRecycleWorkloadService` 的有效设备口径。此次没有连接生产库逐笔核实用户所见的 16 台，也没有直接把这些记录设置为完成。

## 二、操作 SOP

1. 在回收概览点击“退回未完成”，直接进入退回工作台的“未完成”页签。
2. 勾选待寄回单据，点击“批量退回发货”。每单分别录入快递公司、运单号；也可统一选择物流车或客户自取。
3. 核实设备已实际发出后提交。界面逐单显示成功、失败原因，不合适的状态会跳过；失败项可修改后重试，成功项不重复执行。
4. 此时设备仍计入未完成。客户收到后，勾选单据并点击“批量确认客户签收”，核实确认后完成。
5. 按用户确认的规则，保留发出满 72 小时自动完成。未发货单不自动完成。
6. 如果设备仍在商家手中、不再需要退回，可在“更多”中取消退回，必须填写原因；设备恢复回收处理，已有付款事实不被覆盖。

批量发货只登记已经发出的事实，不自动购买运单、不合并不同客户包裹。需要系统快递报价和下单时，继续使用单笔发货工作台。

## 三、72 小时规则

- 起点：确认退回发货时，事务内记录的 `update_at`，不是申请退回的 `create_at`。
- 快递、物流车和自取统一使用 72 小时；原有物流车次日完成分支已统一为该规则。
- 正常运行的既有定时任务每 30 分钟检查一次，因此不是精确在第 72 小时零秒执行。队列或定时任务暂停时会延迟。
- 自动完成写入“发出满72小时自动完成（非物流签收确认）”；人工操作写入“确认客户已签收”，在详情“处理记录”中可查看。
- 定时任务与人工操作共用事务和单据锁，重复执行不会重置时间、重复打印或重复完成。
- 未做历史时间回填。已有异常关联不会被强行修复或强行完成，处理失败会保留原因。

## 四、本次修复与边界

- 修复待寄回状态 `0` 被当成空值、状态页签参数传错、日期筛选未生效的问题。
- 修复统计接口数组及数字状态解析错误；统计读取失败显示“—”及重试入口，不冒充 0 台。
- 修复外层响应成功、内层业务失败时页面误报成功的问题。
- 设备、退回单、设备关联在同一个事务中更新；部分失败回滚当前单，不影响其他已成功单。
- 严格检查当前设备归属，避免旧退回单覆盖另一笔单据；新建单据检查重复设备及无效设备。
- 批量仅提交物流时，不会清空客户地址、姓名和原退回原因。
- 完成单保留记录，不提供删除；仅取消单可以按既有权限软删除。
- 去掉尚无实际功能却显示成功的批量导出、批量删除和详情打印占位入口；真正配置过的打印场景继续保留。
- 批量操作复用原来的单笔接口及权限，不新增权限绕过。管理员仍需具备确认发货、更新退回状态等原权限。
- 退回完成不代表退款、付款，也不改写既有资金记录。
