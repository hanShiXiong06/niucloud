# 预约取件通知：牛云原生 notice 接入

通知键：`hsx_recycle_pickup_update`。仅影响回收预约取件通知，不改变既有下单、签收、打款等通知。本次未改框架文件，未新增表、字段或执行历史迁移。

> **当前状态：小程序固定模板定义已接入牛云原生列表；本站获取、客户授权和实机接收仍需验收。**
> 小程序复用本仓库回收插件已有的公共模板编号 `30171`，选择订单编号、订单状态、温馨提示三个字段，使用独立通知键。当前账号服务类目、模板是否仍可申请及字段是否获准，以微信实际获取结果为准，不把仓库定义当作官方当前可用性保证。公众号公共模板仍待匹配，保持关闭即可，不影响已就绪的小程序渠道。管理员无需填写模板 ID 或字段映射。

## 一、谁负责什么

| 项目 | 唯一来源 | 负责人 / 操作位置 |
| --- | --- | --- |
| 公共模板编号、关键词、字段映射 | 插件固定字典 `PickupNoticeTemplate::WEAPP/WECHAT` | 开发方核实后随插件交付 |
| 本站私有模板 ID | 框架 `sys_notice.*_template_id` | 管理员在渠道消息模板页「获取模板」，框架自动保存 |
| 小程序 / 公众号开关 | 框架 `sys_notice.is_weapp/is_wechat` | 管理员在「设置 → 消息管理」操作 |
| 客户接收资格 | 当前小程序订阅 / 当前公众号关注与会员绑定 | 客户主动授权，遵守账号权限和微信规则 |
| 通知执行记录 | 框架 `sys_notice_log` | 系统通知记录 / 快递配置内只读筛选抽屉 |
| 业务事件防重、未发送及交给框架的结果 | 既有 `recycle_notice_log` | 回收订单通知历史 |

独立模板 ID / 字段映射编辑页和保存接口已经移除。不再使用旧的 `HSX_RECYCLE_PICKUP_NOTICE` 映射配置，也不会自动删除它或迁移历史记录。

## 二、正确操作顺序

1. **部署人员更新常量字典。** 本版已固定小程序公共模板 `30171` 及关键词 `[1, 2, 4]`；对应 `character_string1` 订单编号、`phrase2` 订单状态、`thing4` 温馨提示。该定义参考本插件已有 `recycle_order_add`，不复用其通知开关或私有模板 ID，不改变原下单通知。
2. **管理员通过框架获取模板。** 小程序入口 `/site/channel/weapp/message`，找到「回收预约取件状态通知」并点击「重新获取」，由框架向微信申请本站模板；不是手工输入私有模板 ID。公众号入口 `/site/channel/wechat/message` 本版不注册取件模板，无需配置或开启。
3. **管理员开启框架消息开关。** 入口 `/site/setting/notice/template`。获取模板不等于启用通知；只打开确实要使用且已就绪的渠道。
4. **客户主动授权。** 小程序需要主动订阅且有可用次数；后台开关不能代替客户授权。一次订阅不保证能收到后续全部状态变化。
5. **验收执行与真实接收。** 用获准测试订单触发一次状态变化，查看框架日志、订单通知历史；客户手机实际收到并能进入本人订单后才算完成验收。

**获取失败怎么办：** 保留框架显示的微信错误原因，由部署人员核对当前小程序的服务类目、账号权限和模板可用性，不让管理员猜编号。模板行出现只说明插件字典已注册；获取成功也只说明获得了本站私有模板，不代表客户已收到。未就绪期间仍以订单页和人工联系兜底。其他业务通知不受本项影响。

模板只展示订单编号、取件状态和简短提示；承运公司、预约时间、快递员姓名 / 电话等完整安排在本人订单详情中查看，不把完整安排硬塞进短文本字段。

## 三、只读状态 API 与权限

仅保留：

```text
GET hsx_recycle/pickup_notice/config
```

原 `PUT` 保存接口已移除。读取沿用 `AdminCheckToken + AdminCheckRole + AdminLog`，插件读取权限为 `pickup_notice_config_info`。渠道模板获取、消息开关和框架日志需各自的框架权限；不得绕过权限调用。

GET 返回：

- `notice_key`、`switch_managed_by_notice=true`。
- `management.notice/records/weapp/wechat`：框架管理入口。
- `catalog_sync_supported`、`catalog_sync_message`：是否已具备固定公共模板及可读原因。
- 每渠道 `enabled`：框架开关当前状态。
- 每渠道 `catalog_ready`：插件固定公共模板定义是否就绪。
- 每渠道 `template_ready`：固定定义就绪且框架已获得本站私有模板 ID。
- 每渠道 `ready`：模板就绪且框架渠道开关开启。
- 每渠道 `missing`、`authorization_note`：缺项和客户授权要求。

`ready=true` 仅是本地配置就绪，不证明账号模板有效、授权次数充足、微信受理、客户收到或已读。小程序 `catalog_ready=true` 只说明插件已有固定定义；公众号固定定义仍为空，`catalog_ready/template_ready/ready` 均为 false。应分别判断各渠道，不要求同时启用两种渠道。

## 四、业务调用与原生链路

在预约状态落库、业务事务提交后调用：

```php
(new CoreRecyclePickupNotifyService())->notify($siteId, $orderId, [
    'state' => 'confirmed',
    'carrier_name' => $carrierName,
    'pickup_time' => $pickupTime,
    'courier_name' => $courierName,
    'courier_phone' => $courierPhone,
    'tracking_no' => $trackingNo,
    'message' => $message,
    'attempt_id' => $stableAttemptId,
]);
```

支持 `confirmed/assigned/failed/cancelled/picked_up`；受理中不冒充预约成功。`attempt_id` 或 `provider_order_no` 是每次预约的稳定身份，以区分同订单的新旧预约尝试。

实际发送统一经过：

```text
CoreRecyclePickupNotifyService
  → NoticeService::send(site_id, notice_key, business_data)
  → 框架 Notice 任务
  → 插件 NoticeData / PickupUpdate：提供 vars 和 to
  → 框架 Notice 渠道监听
  → 框架模板发送器与 sys_notice_log
```

`PickupUpdate` 按 `site_id + order_id` 重读订单及真实会员，不信任外部载荷指定的会员、订单号或状态文案。跳转仍为该会员自己的回收订单详情。所有变量与渠道字段定义由插件常量维护，客户没有可编辑映射。

每个业务事件只交给框架一次，不再按渠道手工直发，不注册第二个发送监听，不保留直接调用微信消息接口的适配器。是否发送、模板 ID 和渠道分发都由框架处理。所有已开启渠道必须配置就绪；当前有开启但未就绪的渠道时先记录明确失败，不擅自忽略配置或宣称部分送达。

## 五、防重和结果边界

复用现有 `recycle_notice_log.scene` 存事件指纹，在订单行锁内抢占 pending 记录，提交后再调用框架。承运商、状态、时段、快递员、运单及预约尝试身份相同的回放不重复提交；仅自由描述或回调时间变化不产生新通知。

pending、失败、跳过、已交给框架等既有事件记录均不自动重发。没有启用渠道时记录跳过；公共模板未核实、站点模板未取得等记录原因；通知失败不回滚预约，不重复创建取件单。配置修好也不自动补发旧事件，本次未提供历史补发或人工重发。

订单通知新增代码状态 `4`：**已交给通知框架**。使用既有状态字段，无需 SQL。它只说明框架调用/任务提交完成，不是“微信已受理”“发送成功”或“客户已读”。

当前框架通用任务没有可靠返回每渠道微信业务回执：小程序驱动未向调用方返回结果、任务返回值也不是送达凭证。插件不修改这一框架实现，也不把 true 或任务 ID 翻译成发送成功。回收日志保留 `send_accepted=null`、`customer_read=null`，需要真实手机验收。

## 六、如何查记录

- 回收快递页 → **取件通知执行记录**：复用框架 `GET notice/log` / `getNoticeLog`，固定筛选本通知键，按当前站点权限读取。
- 系统 → **消息发送记录**：`/site/setting/notice/records`，查看同一份框架记录。
- 回收订单 → **通知记录**：查看未启用、缺项、异常、跳过或已交给框架的业务说明。

只读抽屉展示时间、渠道、订单、框架记录状态及执行说明。原生小程序日志的变量位于 `params.vars`，公众号位于 `params`，两种都支持。日志存在、旧布尔标记、HTTP 200、点击标记均不升级为已送达，统一明确 **送达未确认**。存在旧失败说明时保留展示，但不据此保证未送达。

无权限、读取失败、响应异常时显示明确错误并清空旧列表；晚返回请求不覆盖新分页或重新填充已关闭抽屉。这里没有发送、重试或配置写入操作。

管理员异常企业微信推送不在本轮范围；不能称为已通知负责人。客户仍可查看订单安排，必要时业务人员人工联系。
