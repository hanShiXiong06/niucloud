# 上门取件接入与使用手册

版本：2026-09-29。本手册适用于回收插件「第三方服务 → 上门取件服务」，页面路径 `/site/third_party/express_order`。本次不新增数据库表或字段，不修改框架文件。

> 当前通知状态：已改用牛云原生 notice 链路，取消独立模板管理。小程序复用回收插件已有公共编号 `30171`，固定订单编号、订单状态、温馨提示三个字段，可到牛云原生模板页获取并开启。当前账号类目、模板是否允许获取，以真实微信响应为准；尚未完成真实客户接收验收。公众号模板仍待匹配，保持关闭即可。站点管理员无需手填模板 ID 或字段映射。

## 1. 这项服务做什么

客户在小程序提交回收单，按页面要求填写寄件地址、选择预约时间。后台按照本站管理员预先设置的快递公司和产品发起上门取件。客户不用选择快递100、易速等技术渠道，也不用选择快递公司。

这是上门取件服务，不是电子面单。无需为了本功能购买打印机。各站点使用自己的账号并自行与服务商结算；平台不统一垫付或代充值。

易速继续保留。快递100本轮提供受控配置；快递鸟、各快递公司直连尚未验收实现，不作为可用选项承诺。

## 2. 谁负责、在哪操作

| 角色 | 页面 / 平台 | 负责的动作 | 交付结果 |
| --- | --- | --- | --- |
| 本站管理员 | 快递100企业管理后台、客户经理 | 开通正确寄件模式，确认产品、价格、结算、寄付/到付及手机寄递要求 | 本站正式账号、开通说明、费用规则 |
| 本站管理员 | 本站「上门取件服务」 | 选择渠道、公司、产品、付款方，保存配置 | 新预约按本站规则执行 |
| 开发 / 部署人员 | 插件代码字典、服务器、微信公众平台 | 核实通知公共模板及固定字段；配置公开回调、验证框架链路 | 模板是否开放明确，异常可查询 |
| 本站管理员 | 渠道「消息模板」、系统「消息管理」 | 通过框架获取本站小程序模板，再开关「回收预约取件状态通知」 | 不填写模板编号或字段映射；只有框架一处管理 |
| 客户 | 回收小程序订单页 | 提交回收单，确认地址、预约时间，按意愿同意订阅 | 查看安排和后续状态 |
| 业务 / 客服 | 「预约与运单记录」、回收订单 | 处理失败及结果未知、联系服务商、协助自行寄件 | 不重复叫件，客户有明确下一步 |

账号权限由本站管理员负责，技术参数由部署人员负责，不能要求终端客户填写密钥或产品代码。

## 3. 开通前准备清单

1. 注册快递100企业账号，联系该账号的客户经理。明确申请「上门取件 / 寄件接口」，不是仅查询物流。
2. 确认使用线上支付还是线下支付，二者产品契约不同，不能混用凭证或请求参数。
3. 确认账号允许的承运商、业务类型及线路。手机含电池，保价、禁限寄、赔付要求须以服务商真实规则为准，不自行承诺。
4. 确认计费规则：首续重、实际计费重、偏远附加费、保价、取消及退款规则。报价是预估，最终费用以服务商账单为准。
5. 准备正式 Key / Secret；联调时另外申请沙箱账号。
6. 部署人员准备本站公开 HTTPS 域名及回调；通知需要本站实际使用的小程序账号。小程序公共模板已写入插件固定字典，管理员从框架获取时由微信校验本站权限。公众号模板仍待匹配，本版不要求开启。

可以把以下内容发给客户经理：

> 我们需要手机回收上门取件，每站点独立账号结算。请确认本账号的寄件模式、承运商、具体产品、寄付/到付和计费规则，提供寄件 Key/Secret 获取入口、沙箱开通及回调指引。如有多个合作通道，请提供 channelSw。另请说明手机寄递、保价和异常件处理要求。

## 4. 每项配置怎么填

| 页面字段 | 从哪里取得 / 如何填写 | 不应怎么做 |
| --- | --- | --- |
| 授权 Key | 快递100企业管理后台 → 我的信息 → 企业信息；见下方凭证指引 | 不用其他站点 Key |
| Secret | 对应寄件产品的企业管理后台；找不到联系客户经理 | 不猜值、不用其他查询产品参数代替 |
| 服务模式 | 按客户经理确认的寄件模式选线上或线下 | 不凭付款习惯猜模式 |
| 运行环境 | 沙箱用沙箱凭证，正式用正式凭证 | 不把沙箱成功当正式开通 |
| 上门取件公司 | 直接下拉选择；系统自动带公司编码和名称 | 不手输中文冒充接口编码 |
| 寄件产品 | 根据当前模式和公司从参考目录选择 | 不自己编写「顺丰标快」等字符串 |
| 运费付款方 | 管理员明确选择；线上仅寄付，线下圆通/中通也不支持到付 | 不让系统静默改付款方 |
| 合作渠道 ID | 只有商务提供 channelSw 时填写，否则留空 | 不填写公司编码或猜数字 |
| 回调地址 | `https://本站域名/api/recycle/express/kuaidi100_push` | 不填 localhost、内网、record_id |
| 超时 | 默认 30 秒，允许 3–60 秒 | 超时不是“确定没下单” |

`******` 是已保存凭证的掩码，保持不变表示保留；页面不会展示真实密钥。更换账号后旧单仍须原账号处理，需保留原凭证，不能直接作废。

### 产品目录到底是什么

本页目录依据官方文档，由插件维护。页面显示核对日期及官方原文入口。

- 线上模式：9 家公司、13 个明确产品可选，包括顺丰标快 / 特快、京东特惠送等。
- 线下模式：官方列出的 9 家公司；文档没有逐公司的特约产品清单，仅提供官方默认「标准快递」。需要特约产品时，由服务商给出书面参数，开发/部署人员再更新目录。
- 智选涉及自动改派，中通快运和壹米滴答涉及支付同步能力；当前适配未完成，目录显示限制，不允许选中启用。
- 「重新读取目录」只是重读当前插件字典，不是抓取官方新文档，也不是查询本站已开通权限。
- 后端也校验模式、公司、产品组合，不能绕过下拉提交任意字符串。更换模式或公司后清空产品，要求重新确认，不自动改付款方。
- 既有订单的查询、回调、取消沿原快照处理，不用新目录阻拦旧订单。

**官方支持 ≠ 本站账号已开通 ≠ 当前线路有运力 ≠ 快递员已取件。**

已查公开寄件文档未找到“当前账号已开通产品清单”接口。price / batchPrice 是按给定公司、产品和收寄地址查价，不是授权目录。不能用一个查价成功提示覆盖上述所有状态。本页「检查配置」不调用这两个接口。

## 5. 通知如何使用框架 notice

日常操作只有系统「消息管理」中的开关，找到「回收预约取件状态通知」。入口：`/site/setting/notice/template`。

完整顺序是：**开发方固定模板字典 → 管理员在框架获取模板 → 消息管理开启 → 客户主动授权 → 验证手机接收及框架执行日志**。

1. 部署人员更新插件固定字典。本版小程序参考原有下单通知定义，公共编号 `30171`、关键词 `[1, 2, 4]`，展示订单编号、订单状态、温馨提示；使用独立通知键，不改变既有下单通知。账号服务类目和模板当前可用性仍以微信实际响应为准。
2. 管理员进入「渠道 → 微信小程序 → 消息模板」（`/site/channel/weapp/message`），找到「回收预约取件状态通知」并点击「重新获取」。公众号对应页面本版不注册取件模板，无需开启公众号渠道。
3. 框架自动保存当前账号的私有模板 ID，管理员无需复制填写、无需配置字段映射。
4. 在系统消息管理开启需要的渠道，然后返回快递页刷新只读通知状态。获取模板和打开开关都不是发送通知。
5. 客户主动订阅小程序消息；使用获准测试订单验收手机实际收到、点击进入本人订单。一次订阅不保证覆盖后续全部状态变化，客户仍可随时在订单内查看完整安排。

**模板列表出现不等于微信已受理或客户已收到。** 获取失败时，按框架返回的微信错误原因，由部署人员核对小程序类目、账号权限和模板可用性，不需要管理员猜编号或填写映射。小程序通知可单独开启；公众号仍待匹配，保持关闭不会阻断已就绪的小程序渠道。已有下单、打款等其他通知不因此停用。未通过通知验收时，以订单页和人工联系兜底。

通知卡片只提供订单编号、取件状态和简短提示；公司、时间、快递员及电话等完整信息在本人订单中查看，避免短字段超长或缺失信息误导客户。

代码通过 `NoticeService::send()` 统一发送，`NoticeData` 钩子提供订单变量和收件人；字段映射是插件常量，开关和私有模板 ID 是框架配置。不再读取或保存独立通知映射，也不再直接调用微信发送接口。

### 失败在哪里查

- 本页「取件通知执行记录」：只读框架同一份通知日志，展示渠道、订单和执行说明，不声称取得微信受理回执。
- 「系统通知记录」：统一渠道记录，入口 `/site/setting/notice/records`；插件抽屉只是按通知键筛选展示，并非另建日志表。
- 回收订单通知历史：本业务幂等记录及未启用原因。

通知可能因未订阅、授权次数不足、未绑定、模板参数不符或账号配置异常而失败。框架执行返回值和日志不等于微信受理、送达或已读，统一显示「送达未确认」；订单通知中的「已交给通知框架」也不是发送成功。通知失败不回滚回收单、不重复创建预约。未开启渠道、公共模板未就绪等原因保留在回收通知历史。

## 6. 从配置到上线的验收 SOP

| 顺序 | 操作 | 通过标准 |
| --- | --- | --- |
| 1 | 管理员停用新预约，保存账号和取件规则草稿 | 不影响旧单，无新预约外发 |
| 2 | 部署人员补齐目录选择和回调；开发方核实固定通知模板 | 页面缺项清楚，正确模式/付款组合可保存；通知未开放必须说明 |
| 3 | 检查已保存配置 | 仅证明格式及必填完整，不创建快递订单 |
| 4 | 使用专属沙箱联调 | 下单、状态回调、异常、查询和取消可追踪；无需真实揽收 |
| 5 | 管理员确认正式开通、余额、计费及收寄线路 | 取得正式账号可用依据 |
| 6 | 经授权创建一笔正式验收预约 | 真实受理公司/产品/付款方正确，单号及状态回传 |
| 7 | 通过框架获取小程序取件模板并启用，再验证客户通知及手机订单页 | 微信实际允许获取；客户实际收到；本人订单链接正确；未实测不得标为通知验收通过 |
| 8 | 需要取消时验收取消及费用 | 取消请求、取消成功、退款结果分别核对 |
| 9 | 开放正式业务并交接客服 | 管理员知道异常入口，客户有下一步 |

正式寄件可能产生费用。不得用任意客户地址进行“自动实单测试”。本次开发测试没有替你创建真实预约或发送客户消息。

## 7. 客户看到什么，工作人员怎么兜底

| 结果 | 提示原则 | 工作人员动作 |
| --- | --- | --- |
| 已受理 | 公司、产品、时段按真实返回展示；受理不是已揽收 | 等待快递员安排和后续回调 |
| 已安排 | 展示真实快递员姓名 / 电话 | 客户可联系，核对是否仍需寄件 |
| 明确失败 | 保留回收单，展示原因及自行寄件入口 | 先确认没有有效预约，再协助重约或自行寄件 |
| 结果未知 | 提醒先核实，不说“失败可重试” | 在本地预约记录和原服务商后台核查，避免重复叫件 |
| 取消处理中 | 不说已取消或已退款 | 等待回调/查询确认，再决定是否重约 |
| 已取消 / 已取件 | 展示终态；晚到冲突需人工核实 | 不让旧回调覆盖新事实 |
| 通知失败 | 客户仍可看订单安排 | 根据通知结果处理，不能为补消息重复下单 |

快递公司的短信不代替本站消息。当前没有自动通知管理员的企业微信扩展；管理员主动看异常记录，不宣称已经通知到负责人。

## 8. 更新与回滚边界

本轮没有新增 SQL。发布时同步回收插件的后端、admin 安装源及运行时前端源码，重新打包后台。新增组件、监听和目录文件也必须包含，不能只替换 express_order.vue。

代码更新后按框架既有插件部署流程刷新路由/事件缓存；不清空数据库、不删除旧运单。先在本地/测试站验收目录 GET、通知配置 GET、保存草稿和无效组合拒绝，再开放真实站点。

独立通知模板保存接口已移除，仅保留只读状态接口。前后端必须同批更新；旧页面的模板保存操作不再支持，不应继续使用。无需手工迁移或清空历史通知配置。小程序固定模板随本版部署后，仍需在框架获取本站模板并开启消息；公众号模板暂不开放。

需要回退时先停用新预约，恢复成套前后端代码；原订单仍沿原渠道处理。不要删除原账号凭证，不要为回退清空订单或通知记录。
