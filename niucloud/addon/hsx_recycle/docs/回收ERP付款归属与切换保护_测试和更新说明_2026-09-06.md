## 管理员看到的规则

| 情况 | 如何处理 |
| --- | --- |
| ERP 已安装但选择回收独立处理 | 生效后新建的设备走回收，保留本地付款入口 |
| 已有设备归 ERP，之后关闭联动 | 仍由 ERP 入库、付款、回写；不能再次在回收付款 |
| 已有设备归回收，之后开启联动 | 原有责任不变，不自动把旧账迁到 ERP |
| 同一订单包含两种责任 | 原本按设备付款的订单可选择本地设备；ERP 设备禁选并提供 ERP 入口 |
| 混合订单为整单模式，或模式不明 | 暂停整单付款，提示逐台核对，不强制修改原流程模式 |
| 查询失败、映射不唯一、付款金额冲突 | 明确暂停原因，不把“查不到”当作“没有付过款” |
| ERP 没有应答同步查询 | 显示状态未知，不再伪装成已入库 |
| 设备导出页同步状态查询失败 | 常驻警告并提供“刷新并重试”；确认前暂停单台、批量和补仓同步 |
| 回收显示已付，ERP 仍有待付款 | 普通付款被拦截，先核对旧账；不能用开关绕过 |

切换时间按设备现有 `create_at` 判断，保存后下一秒起生效，避免同秒已创建设备被误迁。反复切换记录时间线，重复保存相同设置不会制造新切换。

没有保存过独立配置的老站点仍兼容原安装规则，并明确显示“尚未单独配置”。这样更新代码不会突然把原来 ERP 在管的旧账放回本地。管理员应在上线后确认一次设置。

## 如何避免两边重复付款

1. 当前开关只是新业务规则，实际付款使用订单和设备归属。
2. 归属在既有 `recycle_device_log` 留痕；重试不重复记同一种责任，相反责任日志不会“最后一条覆盖”。日志显示中文责任说明。
3. 回收付款最终写入前锁订单及设备，核对已付款状态、金额、时间及 ERP 真实资产/应付。旧版移动端绕过不了后端检查。
4. ERP 原生单笔、批量付款及折账也在结算写入前向回收核对来源旧账，不能只防回收页面的入口。
5. 普通采购的来源订单 ID 不再被当成设备 ID。使用设备快照或能确证的采购明细；不通过相同 IMEI 猜测关联。
6. ERP 确认回写、销售和销售退货复用精确设备身份。部分结算正确确认接收，但不提前把设备记为全部结清。
7. 可靠通知使用既有 Inbox/Outbox。增加处理租约和原子领取，过期任务可补偿；重试到顶的记录不会挡住后续任务。补偿不新增实际转账。

### 历史已付补账与新付款不同

历史付款事实核销有独立内部入口，不允许请求参数携带一个 `bypass` 就跳过检查。必须逐设备核对回收真实已付金额，扣除 ERP 已核销金额；同时采用财务当前锁定应付快照，避免普通查询旧快照造成多补记。

来源记录显示已付但缺少金额时，延续现有规则以最终回收价格作为历史已付事实。无法确证金额、来源缺失或多个有效采购应付冲突时，仍须核对，不猜金额、不按整单随意分摊。

## 明确的边界

- 已发生的重复转账、遗漏付款及矛盾旧账，没有擅自冲正、退款或补付，需要财务先核对真实流水。
- 不提供一键把未付旧设备从一个系统迁到另一个系统。改变责任必须同时处理旧应付、付款和库存，不能靠开关或普通“重新同步”隐式迁移。
- 现有 ERP 事件失败可重试；归属未知、仓库缺失等未成功派发的设备须按提示修复并使用已有重同步入口，不承诺所有失败自动消失。
- 本版设置只提供回收独立/自有 ERP 两种实际可用模式。第三方 ERP 可沿事件契约扩展，但尚未接入具体厂商，不显示虚假的可用开关。
- 未执行生产发布、真实资金支付、浏览器完整端到端与数据库并发压力测试；上线前仍须完成上面的测试订单验收。
