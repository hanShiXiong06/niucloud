# 平台型号共享方案

状态：基于当前回收和 ERP 代码的设计建议，尚未实施型号库改造，未迁移、删除或回填业务数据。

## 结论

公共型号只存一份，由 SaaS admin 管理。各站点直接查询公共型号，同时可以添加仅本站可见的私有型号。
回收和 ERP 使用同一套型号查询契约、同一个统一型号 ID，不再各自导入整份型号库。
站点不用先点「同步」才能选型号；平台发布后，新查询即可找到。

## 三类数据足够

1. **公共底库**：品牌、系列、型号、标准规格、来源标识，归属平台 `owner_site_id=0`。
2. **私有补充**：站点缺型号时新增，归属当前站点；可以挂在公共品牌或系列下，不允许挂到别人的私有节点下。
3. **站点偏好**：别名、是否隐藏、排序、常用标记、模板绑定等。只有实际设置过才保存，不复制完整公共记录。

订单、库存、SN/IMEI、设备图片、成交价格、质检结果仍然严格属于业务站点。
订单中的型号名、质检模板版本等历史快照需要保留，这是业务凭据，不是需要清除的型号库冗余。

## ID 和自动匹配

统一型号 ID 由公共服务生成；外部数据只作为来源映射。
来源键至少包含「来源命名空间 + 节点类型 + 来源 ID」，同一来源的相同型号可以去重，两个不同来源的同名型号不能仅凭数字 ID 合并。
若两插件使用了不同的来源命名空间，先确认对应关系，再做映射，不能只比较 ID。

设备桥返回 `SM-G9910` 等稳定硬件标识，不把数据库 ID 打进安装包。
链路：读机 → 服务解析硬件标识 → 返回可见的统一型号 → 获取本站生效的模板和字段映射 → 员工核对后保存。
匹配优先级：本站人工绑定 → 平台已确认映射 → 搜索候选；模糊或冲突时让员工选择，不默默套错模板。
本站一次手工绑定可以供本站后续同型号使用，但不会直接污染平台映射。
原始识别值与人工校正值保留来源，USB 序列号不自动承诺等同厂家保修 SN。

## 权限与更新

- 读取统一限制为「已发布公共记录或当前站点私有记录」。列表、详情、搜索、父子节点、数量、模板和别名接口遵守同一规则。
- 站点只能新增、修改自己的私有记录和偏好；公共底库由平台管理员发布，站点不能通过请求参数写入零站点。
- 公共节点停用后不再供新单选用，已有订单仍可按历史关联展示；不直接物理删除已使用节点。
- 私有节点不得改变公共节点本身的类型。型号可选性以明确节点类型和可见的合法子节点规则判断，不能受其他站点私有节点影响。
- 默认只发布公共底库，不自动把站点私有型号收进公共库。确有需要时由平台单独审核。
- 查询直接读公共存储；缓存按公共版本与站点版本区分，公共内容变更只失效缓存，不广播复制整库。
- 树按需展开、搜索分页；索引覆盖归属、父节点、状态和来源键。硬件标识走精确映射，不每次加载整棵树。

## 代码归属

建议抽成薄的公共型号能力（例如 `hsx_catalog`），UI 仍只有一个 SaaS「型号中心」，不是要求员工多开一个业务系统。
公共服务只负责型号、来源映射和可见性，回收和 ERP 各保留质检、签收、库存、财务规则。
不能把公共底库继续绑在可独立卸载的 ERP 或回收插件上，否则卸载其中一个可能破坏另一个。
若最终复用已有表，必须先确认该表的安装、卸载所有权；不能只搬几个 PHP 类就宣布完成解耦。

查询采用明确的服务契约：`searchModels(context, keyword)`、`children(context, parentId)`、`getModel(context, id)`、`resolveHardware(context, identity)`。
事件用于发布后的 `CatalogChanged` 通知和缓存失效，不把每次同步事件变成各站点复制数据。
消费插件未安装时不注册它的适配器；公共型号能力缺失时给出明确安装要求，不静默返回错误型号。

## 实施顺序与验收

1. 定公共型号服务、归属字段和平台管理入口，列出精确新增字段、索引及 SQL 后再实施。
2. 接入回收的树、搜索、快速新增、模板绑定和桥识别，验证两个站点隔离。
3. ERP 接入同一模型服务，新业务共享统一引用，保留各自的业务字段和历史凭据。
4. 检查插件独立安装、升级及卸载边界，再逐步开放其他插件消费。

验收：平台新加一个型号，两站点的回收和 ERP 都能直接选；站点 A 新增私有型号，B 的所有查询都看不到；A 的别名和模板不改变 B；修改公共名称不改变旧订单快照；一个消费插件卸载不删公共底库。

历史型号是否合并、旧 ID 如何映射，须另行确认，不包含本次下载配置与设备桥发布。没有执行历史迁移，也没有把现有业务主键改成来源 ID。
