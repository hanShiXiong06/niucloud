# 签收打印电池缺失：修复与测试

## 问题与原因

代下单/签收时已经保存电池健康度，但首次自动打印显示 `-`，之后手动补打可能正常。

代码和本地数据验证结果：

1. 签收摘要会将电池保存到 `info.check_meta.battery`，新增设备自动打印在保存提交后触发，并非简单的“打印早于保存”。
2. 设备模型的 JSON 字段默认返回对象。原打印服务只接受数组或 JSON 文本，遇到对象便返回空数组，连带丢失电池及其他仅存在 `info` 中的摘要。
3. 完整质检结果文字生成后，原代码还能从“电池健康度 xx%”中提取数值兜底。因此补打正常并不代表第一次取数没有问题。若只是补打、没有任何后续数据更新，还需用同一设备的打印任务快照核对；本次没有取得线上客户的前后快照。

## 修复范围

业务代码仅修改：

`niucloud/addon/hsx_recycle/app/service/admin/printer/RecyclePrinterTemplateService.php`

复用插件现有 `DeviceReadingArchive::decode()`，将 `info` 和 `check_meta` 的对象、数组、JSON 文本统一解析。保留原有结构化数据优先、质检文字兜底的取值顺序；未录入仍显示 `-`，数值 `0` 不当成缺失。

没有修改框架、前端或数据库结构，没有历史数据回填，没有调整打印触发时间和重复打印保护。

## 手动更新与验收

1. 替换上述打印模板服务 PHP 文件即可，无需重新打包前端，也不执行 SQL。
2. 如果服务器关闭了 PHP 文件自动重新校验，按原部署流程刷新 PHP OPcache。
3. 新录入一台测试设备，填写电池健康度（例如 96），检查首次标签。
4. 在不修改该设备的情况下手动补打，确认两张标签电池值一致；未填写电池的设备继续显示 `-`。
5. 不会自动重发已经打印过的任务；旧标签需要工作人员按实际需要补打。
