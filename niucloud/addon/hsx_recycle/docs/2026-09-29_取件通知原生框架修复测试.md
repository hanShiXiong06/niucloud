# 取件通知原生框架修复与测试

日期：2026-09-29。仅涉及回收插件预约取件通知，不修改其他业务通知。

## 结论与发布限制

**本轮完成发送入口、固定模板字典和原生管理列表的代码整改；本地原生接口已返回取件通知，真实微信获取及手机接收尚未验收。**

原实现只有 `NoticeData` 注册，实际由插件直接调用微信接口；模板字段需要管理员手工映射，公共模板编号为空。这不等于完整接入框架“获取模板”。

现在改为插件固定字典、框架私有模板和开关、`NoticeService::send → NoticeData → Notice`、框架通知日志。已移除独立模板编辑及保存接口，删除插件微信直发适配器。

对照 `shop`、`phone_shop`、`hsx_phone_query` 后，确认列表必须有相同业务 key 的渠道字典，仅注册 NoticeData 不够。现沿用回收插件原有 `recycle_order_add` 的公共编号 `30171` 及既有字段定义，另选 `[1,2,4]`：订单编号、订单状态、温馨提示。以独立业务 key 注册，不覆盖原下单通知；不借用付款、退款或审核模板。

**剩余验收：** 该历史公共编号在当前微信账号的类目与权限下能否获取，须以微信真实接口响应为准。本地代码存在不等于微信当前可用。公众号 `WECHAT` 仍未配置公共模板，保持关闭；不影响已就绪的小程序渠道。不要把本报告当成微信已发送、客户已收到的证明。

## 实现边界

- 保留预约成功、派员、失败、取消、已取件五种业务触发，统一通知键 `hsx_recycle_pickup_update`。
- 通知发生在业务状态持久化之后；通知异常不回滚快递预约。
- 按站点和订单重查真实会员，忽略外部指定的收件人、订单号和状态文案。
- 订单锁内建立事件指纹，框架提交在事务外；相同回调不重复提交，失败或结果未知也不自动重发。
- 所有已开启渠道须就绪，未开启记录跳过，缺模板记录原因，不悄悄忽略配置。
- 新日志状态 `4=已交给通知框架`，使用既有 `tinyint` 状态字段，无需 SQL。该状态不表示微信已受理、客户收到或已读。
- 没有框架文件修改，没有新增表或字段，没有清理或迁移旧配置/历史通知。

## 本地只读核验

使用本地 PHP 应用及本地数据库，分别查询站点 `100005`、`100000`：

1. 直接调用页面使用的 `WeappTemplateService::getList()`，两站点均返回「回收预约取件状态通知」，业务 key 为 `hsx_recycle_pickup_update`。
2. 两站点均返回 `support_type=["weapp"]`、`tid="30171"`、`kid_list=[1,2,4]`。确认渠道列表不再过滤该记录，原生页面会按其通用逻辑提供开关及重新获取入口。
3. 两站点均未获取该业务的私有模板，开关为 `0`。因此只是列表入口就绪，不能宣称已经可发送。
4. 只进行了原生列表查询，没有调用获取/删除微信模板、修改开关或发送通知。此前核验的本地两站点缺少小程序凭据，不代表线上没有配置。

本轮未进行更新后浏览器视觉验收；SFC 编译与离线交互检查不能代替真实页面和微信接收验收。此前报告中的浏览器观测属于旧实现。
