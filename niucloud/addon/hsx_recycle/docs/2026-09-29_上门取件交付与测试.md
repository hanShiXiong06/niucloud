# 上门取件第一阶段：交付、升级与测试

日期：2026-09-29  
交付状态：本地代码与离线测试完成；未部署线上，未触发真实叫件、取消、扣费或客户通知。

## 一、现在完成了什么

本阶段落地快递100，保留易速原渠道，不把所有第三方服务一起重构。

- 站点管理员配置自己的快递100账号、服务模式、承运公司（如顺丰）、产品和付款方式。客户不选择渠道或承运公司。
- 回收单先保存，再发起取件。预约失败不会丢失回收单，也不会要求客户重复下回收单。
- 预约请求先在本地留下记录，再请求渠道。同站点相同请求不会重复叫件。
- 小程序显示确认中、预约成功、取件员安排、实际运单、取消、失败与待核实。
- 明确失败或已取消且无冲突时，可在原回收订单补填实际寄件公司和单号；未知结果不能直接自行寄件。
- 回调验签、重复回调去重、乱序防倒退、冲突阻断、自动查询核实。
- 小程序/公众号通知独立配置与记录。通知失败不回滚预约；微信受理不等于客户已读。
- 后台运单记录展示原渠道、状态、异常、取件员、预约时间、费用待核对。
- 本站收货地址沿用现有回收地址配置；客户台数门槛保留，但不再把预约资格宣传为“包邮”。

客户主要路径：

填写回收信息 → 确认固定快递及费用说明 → 提交回收单 → 查看取件卡片 → 快递取件 → 原回收流程继续。

## 二、异常时谁做什么

| 情况 | 客户看到 / 可以做 | 管理员处理 |
| --- | --- | --- |
| 接口受理，尚未确认 | 正在确认取件安排，不重复叫件 | 等待回调或查询原预约 |
| 已确认，取件员未返回 | 预约成功，待分配取件员 | 不填虚构姓名/电话 |
| 已安排取件员 | 快递名称、预约时段、联系人及拨号入口 | 以渠道实际安排为准，不承诺准点 |
| 明确拒绝 | 回收单保留，可自行寄件并补实际运单 | 查看失败原因，必要时协助 |
| 请求超时 / 结果未知 | 待核实，暂不可补另一张运单 | 查渠道原单；不得直接再次叫件 |
| 未知且无渠道订单/任务号 | 等待门店核实 | 确认渠道确实未预约后，使用“核实未预约”，填写依据并二次确认 |
| 已取消后又收到揽收信息 | 状态冲突，请联系门店 | 核实真实履约，不能直接放行另一张寄件单 |
| 通知失败 | 仍可在小程序订单详情查看真实状态 | 在现有回收通知记录中检查模板/绑定/授权原因 |
| 费用未核对 | 不展示虚构“已支付”结论 | 查渠道账单登记费用；取消不自动认定已退款 |

“核实未预约”不是强制清空状态按钮：有渠道订单、任务编号、运单或冲突时不开放。该操作只登记核实结果并允许自行寄件，不自动重新预约。

## 三、配置入口与分工

### 平台维护人员

1. 更新下面文件并打包对应前端，后端先上线。
2. 注册本次新增权限和计划任务，确认任务进程/队列进程正常。
3. 确认公网 HTTPS 回调可到达，不被登录校验、网关或防火墙拦截。
4. 协助站点开通真实模板。不要把账号 Key、Secret 放入客户小程序代码。

### 站点管理员

入口：`/site/third_party/express_order`。

1. 选择快递100，填写本站账号 Key / Secret。
2. 选择账号实际开通的线上支付或线下支付产品，以及正式/测试环境。测试环境也必须有匹配的测试账号，不是免费模拟按钮。
3. 配置承运公司、官方产品名称、寄付/到付及可选渠道 ID。
4. 配置本站默认收货地址；检查预约台数门槛。
5. 回调地址填写：`https://本站域名/api/recycle/express/kuaidi100_push`，不手填 record_id，系统逐单附加。
6. 配置预约通知的小程序/公众号真实模板 ID 和字段映射；默认关闭，缺模板不能启用。
7. 核实账号权限、承运范围、余额/结算条件后，做一笔经授权的真实验收，再向客户开放。

配置健康检查只验证格式，不证明快递100已经授权、可用或余额充足。线上模式当前仅支持寄付；线下到付也受具体承运商限制。最终运费以渠道账单为准。

运单入口：`/site/express/order_record`。可以查看异常原因、状态、取件员和核对费用。快递100取件不需要面单打印机。

### 客户

选上门取件 → 确认寄件地址、时间和费用说明 → 可自愿订阅通知 → 提交。后续从原回收订单查看安排、联系取件员、刷新核实，或在明确失败后补填自行寄件单号。没有提供渠道选择器。

## 四、数据库与框架边界

- **没有新增表或字段，无 ALTER / CREATE TABLE 升级 SQL。**
- 复用现有快递记录的 `api_response / status_history`、回收订单 `delivery_data`、配置及通知日志表。
- **没有修改框架文件。** 业务代码、字典、页面、测试均在 hsx_recycle 插件；admin 与 uni-app 运行目录为该插件镜像。
- 覆盖文件仍不等于完成升级：本次新增 3 个权限和 1 个计划任务，需要写入现有菜单/计划任务表。
- 不清库、不改历史订单、不回填旧数据。原易速单保留原处理路径。
- 同一站点更换默认渠道只影响新单。已有单查询/取消用原记录的渠道、模式和账号指纹。若直接替换原账号凭证，旧单会提示恢复原账号，而不是拿新账号误操作。
- 使用 MySQL 同连接命名锁控制同一预约并发。离线测试验证调用边界，但实际数据库锁权限、并发行为仍需部署环境验收。

先上传插件脚本 `scripts/register_pickup_upgrade.php`。按顺序执行：


- help 不加载应用；默认预览连接数据库但不写入。

- 新任务默认启用，每 5 分钟最多核实 20 条快递100预约。注册命令自身不请求渠道，但之后任务进程可能查询原预约并触发状态通知。
- 不并发执行；已有停用项保留，需要管理员确认是否启用。
- 为需要的员工角色授予预约通知配置、核实未预约权限；脚本不代替角色授权。
- 用当前项目既有方式清理路由/字典缓存，重载 PHP 常驻进程及计划任务/队列工作进程。
- 开发时仅验证脚本语法、help、真实框架方法签名及字典加载；没有连接真实数据库执行预览或 apply。

覆盖重点：

- 先提交回收事务、再叫件；先保存预约占位、再发HTTP。

## 七、仍需真实环境验收（未完成，不冒充通过）

| 验收项 | 谁确认 | 通过标准 |
| --- | --- | --- |
| 实际部署库/锁与权限 | 维护人员 | 无缺表字段、同单并发只产生一张渠道预约 |
| 正式账号与固定顺丰产品 | 站点管理员 | 渠道真实受理且产品/结算方一致 |
| 公网回调 | 维护人员 | 正确签名更新原单，伪造签名不更新 |
| 揽收信息 | 运营 | 取件员姓名电话按渠道实返展示，缺失显示待分配 |
| 小程序订阅与点击 | 站点管理员/测试客户 | 主动授权后微信受理，手机实际收到并进入本人订单 |
| 公众号通知（若启用） | 站点管理员/测试客户 | 模板、关注/绑定正确，手机实际收到 |
| 原单失败后补寄 | 运营 | 原订单不重复创建，补实际运单，未知状态不放行 |
| 原易速存量单 | 运营 | 切换后仍从原渠道查询/取消，不误调快递100 |
| 费用与取消退款 | 财务 | 以真实账单核对，不因本地取消显示已退款 |

一次小程序订阅不代表无限发送；后续状态消息可能因次数不足被拒绝，应看日志。自动核实任务不是即时承诺，按批次/退避查询；缺失 taskId 无法按当前接口安全查询时，等待回调或人工核实。
