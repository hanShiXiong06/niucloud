# 移动订单多设备模板串用：修复与测试

## 问题与根因

入口：移动管理端回收订单详情 `addon/hsx_recycle/pages/order/detail`。

原代码在 `loadOptionLabels()` 中只取 `order.devices[0]` 获取质检模板，并把映射保存为一个页面级 `optionLabelMap`。随后每台设备的容量、颜色、系统、保修都使用这份映射。

例如同一订单第一台是安卓设备，第二台是 iPhone，两者容量均保存为选项 `2`。原逻辑会把 iPhone 的 `2` 也解释成安卓模板的“12G+1T”；颜色同样会串用。这是已确认的前端展示错误，不能因此直接改写原始设备数据。

设备详情弹窗也存在切换时不清空旧字典、慢响应覆盖新设备的问题，本轮一并修复。

## 修复范围

- 按“设备 ID + 自身模板 ID”隔离映射，不再按订单第一台设备解释其他设备。
- 模板来源优先取设备 `check_template_id`，其次取同设备 `info.check_meta.template_id`。
- 未记录模板编号时，逐设备请求 `check_template/schema?device_id=...`；不能把所有 `template=0` 的设备共用一个缓存。
- 后端明确返回未匹配或全局默认来源时，不把该模板作为当前设备的选项字典；解析失败保留原值，不借其他设备的文字。
- 一次加载内，相同的明确模板编号只请求一次；最多 4 个请求并行。新加载不复用上一轮失败或过期结果。
- 刷新订单、切换设备或关闭弹窗时清除旧映射，并忽略迟到响应。弹窗的成本权限/日志读取也受同一设备请求版本约束，未改变成本调整业务规则。
- 不修改数据库、历史记录、付款状态或框架；本轮只修复显示与异步读取。

## 业务文件清单

均在移动管理端插件源码 `site-uniapp/src/addon/hsx_recycle/`：

1. `hooks/useDeviceOptionLabels.ts`：新增统一的逐设备解析逻辑。
2. `pages/order/detail.vue`：多设备列表改为独立字典，防止旧订单响应覆盖。
3. `pages/order/components/DeviceDetailPopup.vue`：复用同一解析逻辑，修复切换残留和请求乱序。

三个文件需配套更新。**与上一次打印 PHP 修复不同，本次需要重新构建并发布移动管理端 H5 / 管理小程序；仅更新 PHP 不会更新已发布的页面。** 本地开发模式可通过热更新后刷新页面验证。

开发回归脚本：`niucloud/addon/hsx_recycle/scripts/verify_order_device_labels.cjs`。

## 已执行的测试

在项目根目录执行：

```sh
node niucloud/addon/hsx_recycle/scripts/verify_order_device_labels.cjs
```

共 17 组检查通过：

1. 同订单混合机型，iPhone 不使用首台安卓的容量、颜色字典。
2. 相同明确模板复用请求，不同模板独立解析。
3. 无模板编号时逐设备解析，不共用编号 0 的缓存。
4. 支持同设备 meta 的模板编号及 JSON 字符串 info。
5. 后端返回未匹配或全局默认来源时保留原值。
6. 单台加载失败不污染其他设备，刷新可恢复。
7. 明确请求的模板 ID 与返回 ID 不一致时不误用。
8. 同设备更换模板，旧慢响应不能覆盖新映射。
9. 清空/切换后忽略迟到结果。
10. 数组、文字、空值处理，不改变原始设备对象。
11. 订单详情响应乱序保护。
12. 设备弹窗切换机器不沿用旧模板。
13. 弹窗详情响应乱序保护。
14. 9 台不同模板设备按最多 4 并发完成解析。
15. 新 Hook 的 TypeScript 严格类型检查。
16. H5 页面与弹窗的脚本、模板、样式定向编译。
17. 微信小程序页面与弹窗的脚本、模板、样式定向编译。

测试先在原代码上复现“期望 iPhone 模板的 256GB，实际得到安卓模板的 12G+1T”，修复后通过。这里的容量、颜色是隔离测试样本，不据此断言订单 2527 中某台实际设备的配置。
