# 上门取件第二轮完善与测试

> **历史测试记录，请勿按旧通知接入步骤操作。** 本文保留当时的实现与测试数字；独立模板 ID / 字段映射管理和直发回执方案已由后续原生 notice 修复替代。当前操作以《预约取件通知配置与验证.md》及 [取件通知原生框架修复测试](2026-09-29_取件通知原生框架修复测试.md) 为准。当前公共模板仍待开发方核实，不能把本文旧测试通过理解为通知已经可获取或已接通。

日期：2026-09-29。范围：第一版快递100链路的可靠性、配置体验、客户刷新反馈。没有扩大为快递鸟/直连接入。

## 1. 本轮解决的问题

| 原问题 | 处理后 |
| --- | --- |
| 渠道创建响应不完整，但已经返回任务编号；异常后编号丢失，无法继续核实 | 保持“结果待核实”，同时保存已有任务/订单/运单编号；仍复用原预约，不再次叫件 |
| 查询返回空数据，被误判为渠道已受理 | 空结果、缺少状态视为查询未完成，不改变原预约事实；定时任务按原退避规则继续处理 |
| 普通回执 taskId 为空，可能清掉原查询编号 | 空值保留原编号 |
| 客户刷新遇到节流、缺编号或渠道异常，看不出发生了什么 | 分别提示已核实、需稍候、等待回调、暂未取得最新状态；显示剩余刷新间隔 |
| 预约记录已保存，但订单展示未同步；刷新节流时不能修正 | 即使节流或查询失败，仍按已经保存的预约事实更新原订单展示，不改回收业务/付款状态 |
| 冲突状态仍残留“预约成功”等标题 | 统一“取件记录待人工核实”，明确联系门店，不允许补另一张运单 |
| 已改为自行寄件，仍显示原预约取件时间 | 不再显示旧预约时段，保留实际新运单 |
| 配置草稿与已保存配置混在一起，“检查”会重载并覆盖草稿 | 区分已保存渠道与草稿，未保存先提示；检查不覆盖编辑内容，刷新和离页要求确认放弃 |
| 初次读取配置失败后可能直接保存默认值 | 成功读取前禁止保存；保存成功但回读失败时单独提示核实 |
| 通知缺模板/字段重复，提交后才报错 | 增加前置校验，明确不代表已经授权或实际送达 |

## 2. 不变的业务边界

- 客户不选择服务商/承运商/产品/付款方，仍由站点配置控制。
- 请求超时不等于预约失败，仍禁止自动重下或直接自行另叫快递。
- 回收订单、预约记录、通知结果分开，不把刷新成功当成预约成功或通知送达。
- 没有修改数据库结构，不新增表或字段，不处理历史回填。
- 本轮没有新增框架改动；改动仅在 hsx_recycle 插件及对应 admin/uni-app 镜像。
- 不修改 ERP 成本、回收价格、付款记录或回收业务状态。

## 3. 验证方法与限制

使用真实业务类配合内存模型、渠道/消息替身，验证数据合并、权限、幂等和页面交互。没有运行真实叫件、取消、扣费、客户消息或生产配置保存。

本机管理端 127.0.0.1:5175 可以打开，但其开发配置仍请求线上 gl.hsxbk.top；浏览器只到达登录页，未登录、未保存配置，随后已关闭测试页。不能据此宣称真实浏览器全链路验收完成。

新增的 projection 测试直接执行 RecyclePickupService，覆盖：跨站/他人订单拒绝、状态更新、节流反馈、无任务编号不查询、查询失败保留已知事实、不泄漏原始异常、原单补寄、重复补寄拒绝、晚到旧回调不覆盖实际新运单、不改价格与付款字段。

新增的 configuration 测试执行配置页脚本，覆盖：草稿与已保存渠道隔离、检查不重载、刷新/离页取消保护、读取失败防覆盖、保存成功但回读失败单独提示、凭证掩码保留、寄付/到付不自动修改、通知模板映射校验。
