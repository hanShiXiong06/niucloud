# 设备读取与原始档案：测试及升级说明

日期：2026-09-07  
范围：回收录入、设备编辑、质检、外部设备查询、回收同步 ERP、ERP 库存详情。  
数据库：没有新增表、字段或迁移 SQL，不做历史数据补录。

## 一、用户能看到什么

1. 点击“读取本地设备”，保留服务返回的完整设备快照，同时提取串号、容量、系统、电池等业务字段。
2. 优先使用稳定的硬件型号标识进行分类匹配。不能唯一匹配的字段留给管理员确认，不猜测颜色，不按选项下标代入颜色。
3. 自动值与人工填写值分开处理：更换质检模板时重新匹配自动值；已人工确认的字段不被自动回填覆盖。
4. 设备编辑、质检和详情中的原始档案默认折叠。需要追溯时，再展开查看“本地读取”“型号匹配”“外部查询”，不把原文拼成长备注。
5. 保存设备后，原始采集记录不随摘要修改而被覆盖。新增保修等查询可以追加，查询时间和来源随记录保留。
6. 回收同步 ERP 时带入健康度、循环次数、系统和保修信息，库存详情可查看采集档案。内部档案不随商品质检数据发布到商城。

### 电池字段的准确含义

| 服务字段 | 当前处理 | 本次用户样例 |
| --- | --- | --- |
| `battery.health_percent` | 优先作为电池健康度 | 100% |
| `battery.calculated_health_percent` | 原文保留；缺少有效报告健康度时才作为估算回退，业务值上限为 100% | 原文 100.5% |
| `battery.level_percent` | 当前剩余电量，保留在原始档案，不冒充健康度 | 98% |
| `battery.cycle_count` | 独立的循环次数，0 也是有效值 | 212 次 |

没有有效读数时保持未知，不把未知当作 0。业务健康度、循环次数仍允许人工确认调整；原始档案保持原值，便于核对。

## 二、保存与校验规则

- 使用回收设备现有 `info.device_readings` JSON 保存档案；ERP 使用现有 `qc_report` 和 `spec_json`，不新增数据库结构。
- 原始采集数据、提取结果、分类匹配记录、外部查询记录分别保存。
- 保存原始采集记录时校验 IMEI、IMEI2、SN 与当前设备的对应关系，防止把另一台设备的数据挂过来。
- 外部查询只接受查询记录 ID，后端从本站查询台账读取结果，不直接相信前端传回的查询原文；同时校验站点和设备串号。
- 相同外部查询记录不会反复追加。缓存命中保留原始查询时间和记录关联，不通过反复命中延长结果的实际有效期。
- 查询失败或没有明确保修状态时，不再自动写成“未激活”。切换设备后返回的旧查询结果不回填到新设备。
- 原始快照超过 128KB、完整档案超过 1MB 时明确报错，不静默截断。
- 原文采用纯文本展示，不执行原文中的 HTML。关闭折叠区域时不渲染长 JSON。

已有设备以前没有保存的原始数据无法凭空恢复。本次保证之后读取、提交、编辑和同步的链路，不批量改写历史记录。

### 浏览器真实设备检查

在本地管理端“代下单”中实际调用了已连接的 iPhone Air：

- 成功匹配标准机型，容量回填为 256G。
- 健康度显示 100%，没有把计算健康度或剩余电量当成健康度。
- 服务没有给出明确颜色名称时，颜色保持待确认，没有自动猜选。
- 原始档案默认折叠；展开后可以查看独立的原始返回和提取结果。
- 录入窗口及折叠区在约 1280×720 的浏览器视口中检查正常。
- 本次实时读数时间晚于用户提供的样例，电量和循环次数可以变化，判断依据是同一次采集中的对应字段。
- 检查完成后取消了录入，未用真实设备创建订单。

### 测试边界

- 数据库测试使用独立测试站点 `900000022` 和事务；结束后回滚并检查没有遗留测试业务数据。
- 没有调用收费保修接口，没有真实付款，没有向外部发送通知。
- 外部查询的落库、关联及防串数据使用本地构造的查询台账验证；真实查询供应商的在线可用性不在本次验证结论内。
- 没有部署线上，没有修改线上数据，没有升级依赖。

## 五、更新及验收顺序

1. 按上面的文件清单更新回收、ERP 后端；不需要执行 SQL。
2. 更新管理端源码和插件镜像，重新构建管理端并发布完整构建产物。仅更新 PHP 无法获得新的读取映射和折叠档案界面。
3. 按现有部署方式刷新 PHP 缓存；如果有常驻队列加载本次改动的类，应重启相关队列进程。
4. 读取一台设备，核对健康度、循环次数、IMEI/SN、机型及容量；未明确匹配的颜色应由人确认。
5. 提交后重新打开设备，确认原始档案仍在，且未拼进人工备注；修改人工摘要后再次打开，原文仍保持不变。
6. 使用已配置的查询通道查询保修，保存后确认查询记录存在；没有明确状态时应保持未知，不应变成“未激活”。
7. 按正常回收确认流程同步 ERP，在库存详情核对业务数据和折叠档案。商城公开质检数据不应包含内部原始档案。

当前工作区的 `niucloud/public/admin/index.html` 另有构建产物入口变化，未作为本次手工修复文件处理；不要单独上传入口 HTML，应发布同一次完整构建的 HTML 和 assets。
